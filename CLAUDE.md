# Summonarr

Self-hosted media request aggregator. Users browse TMDB (trending / popular / discover / upcoming), request movies and TV, vote, and file issues. Admins approve requests and auto-fulfill via Radarr/Sonarr. The app ingests Plex and Jellyfin libraries + play history so users see availability, active sessions, and watch activity in one place. There is no public README — this file is the canonical project brief.

## Stack

- **Next.js 16.3.2** (App Router). AGENTS.md is not a suggestion — **read [node_modules/next/dist/docs/](node_modules/next/dist/docs/) before touching framework code**.
- **TypeScript** strict, path alias `@/*` → `./src/*`
- **Prisma 7.8** + **PostgreSQL 17**, schema-first. No `prisma/migrations/` directory — changes are applied via `prisma db push`.
- **Custom session auth** — a `jose`-signed (HS256) session JWT, not NextAuth (the project migrated off it; there is no `next-auth` dependency and no `auth.config.ts`). Session lifecycle lives in [src/lib/session-jwt.ts](src/lib/session-jwt.ts) (sign/verify), [src/lib/session-refresh.ts](src/lib/session-refresh.ts) (`verifyAndRefreshSession`: DB revocation, `sessionsRevokedAt`/`passwordChangedAt` cutoffs, role rotation, the sign-in deadline — guardrail 6c), [src/lib/session-cookie.ts](src/lib/session-cookie.ts), and [src/lib/auth.ts](src/lib/auth.ts) (`auth()` — JWT-only read). A custom `AuthSession` table backs per-device tracking + revocation. Providers: local credentials, Plex OAuth, Jellyfin (standard + QuickConnect), OIDC (`openid-client`).
- **Tailwind v4** — **no `tailwind.config.js`**. Theme lives inline in [src/app/globals.css](src/app/globals.css) under `@theme inline` with oklch variables and `.dark` class-based dark mode.
- **UI**: [src/components/ui/](src/components/ui/) — `@base-ui/react` (Radix-style) primitives scaffolded via the `shadcn` CLI, composed with the in-repo `@/lib/cva` and `@/lib/tw-merge` reimplementations (the `class-variance-authority` and `tailwind-merge` npm packages are **not** installed — these are hand-written equivalents; the merger's group table — named utilities AND a matrix of arbitrary `[…]`/`(…)` values — is CI-audited against the installed Tailwind, see guardrail 39).
- **Client state**: plain `useState` + URL `searchParams`. No Zustand, Jotai, Redux, or TanStack Query.
- **Data fetching**: REST API routes + `fetch` on the client, or server components calling Prisma directly. No tRPC. No server actions.
- **Package manager**: npm (see `package-lock.json`). No `packageManager` field, no `.nvmrc`.

## Core architecture

**Sync orchestrator** — [src/app/api/sync/route.ts](src/app/api/sync/route.ts)
- External-cron entry point, Bearer-authed via `CRON_SECRET` (or admin session).
- Runs the download-policy sync + the Plex and Jellyfin library fetch+write arms *concurrently* via `Promise.allSettled` — and each of those two arms is itself a fan-out over every configured server instance (`getSyncableMediaInstances`, guardrail 35). The Radarr and Sonarr wanted/available refreshes run earlier and are **sequential to each other** (HD+4K fetches parallelize *within* each); there is no separate TMDB "job" here beyond an expired-`TmdbCache` purge near the end.
- One shared `stillPending` snapshot is reused across both sources' marking passes. The "now available" notification fire-exactly-once guarantee is an atomic claim (`claimAvailableNotificationWinners`, an `UPDATE … RETURNING` compare-and-swap on `notifiedAvailable`) — not a plain update — so an item appearing in both libraries in the same run notifies once.
- Parallel Plex+Jellyfin sync, shared `stillPending` snapshot, `recentOnly` for Jellyfin, and batch tx timeouts landed together (the original commit hash cited here, `3dcbd79`, is not reachable in the current squashed history — see the audit note).

**Sync modes**
- **Full sync** — atomic `deleteMany` + repopulate inside one `$transaction`. The orchestrator `/api/sync` route does **not** read the body — it always does a full library replace. Multi-server nuance (guardrail 35): every delete is `serverInstance`-scoped, and only the instances whose fetch *succeeded* are replaced — a failed instance's rows are deliberately left intact rather than wiped. The `{ "full": true }` body flag is parsed only by the per-source routes `/api/sync/plex` and `/api/sync/jellyfin` (the admin "Resync" button), where `recentOnly = rawBody.full !== true`.
- **recentOnly** (default for Jellyfin) — incremental insert-only, bounded by a 2-hour `MinDateLastSaved` window (`RECENT_WINDOW_MS`). Intentionally wider than `SYNC_INTERVAL=3600s` so one missed run is survivable.

**Batch writes** — [src/lib/cron-auth.ts](src/lib/cron-auth.ts)
- `batchCreateMany(tx, rows)` chunks inserts into `CREATE_MANY_BATCH = 5_000`.
- `BATCH_TX_TIMEOUT = 30_000` — always pass this to `prisma.$transaction(..., { timeout: BATCH_TX_TIMEOUT })` for library-sized writes.

**`isCronAuthorized`** — same file. Accepts an admin session *or* `Authorization: Bearer ${CRON_SECRET}`. Every sync/cron route funnels through this — touch carefully.

**arrFetch** — [src/lib/arr.ts](src/lib/arr.ts)
- Shared Radarr/Sonarr HTTP client. 30s timeout, **50 MB** response cap (`ARR_FETCH_MAX_BYTES`), injects `X-Api-Key`, throws `ArrResponseError` on non-2xx, routes through `safeFetchAdminConfigured`.
- Body cap was raised from 10 MB because libraries with >3k movies were being silently truncated. Do not lower it.

**safe-fetch helpers** — [src/lib/safe-fetch.ts](src/lib/safe-fetch.ts)
- `safeFetch(url)` — full SSRF policy (resolve+pin, blocks RFC1918/loopback/link-local/CGNAT/multicast). For user-supplied URLs.
- `safeFetchTrusted(url, { allowedHosts })` — required hostname allowlist; still runs the DNS-based SSRF check (resolve + per-address public-IP check, `allowPrivate=false`, so a DNS rebind to a private address is blocked). For fixed third-party APIs (TMDB, plex.tv, discord.com, ipinfo.io, api.trakt.tv, api.github.com, raw.githubusercontent.com, www.omdbapi.com, api.mdblist.com, api.resend.com).
- `safeFetchAdminConfigured(url)` — runs SSRF policy with `allowPrivate=true` (RFC1918/ULA/loopback OK; link-local + 0.0.0.0 still blocked). For URLs persisted in `Setting` (Radarr/Sonarr/Jellyfin/Plex server).

**Webhook auth** — [src/app/api/webhooks/](src/app/api/webhooks/) (**sonarr, radarr only**)
- There is **no Plex or Jellyfin webhook handler** — those routes were removed. Plex real-time activity comes from the SSE stream ([src/lib/plex-events.ts](src/lib/plex-events.ts)); Jellyfin activity from the 5s play-history poller. Only `radarr/route.ts` and `sonarr/route.ts` exist.
- SHA-256 + `timingSafeEqual` against the stored webhook secret (`radarrWebhookSecret` / `sonarrWebhookSecret` + 4K variants, with a legacy shared `webhookSecret` fallback).
- Accepts either `Authorization: Bearer …` **or** a `?token=…` query param. The query-string fallback is load-bearing — see guardrails.
- No HMAC signature validation; none of these services send one.

**Play history** — [src/lib/play-history.ts](src/lib/play-history.ts)
- `recordCompletedSession()` ingests when an `ActiveSession` completes and writes a `PlayHistory` row with full playback metrics (duration, pause, codec, resolution, bitrate, device, IP, etc).
- `getActivityCalendarUncached()` (~line 1892) backs the GitHub-style 365-day heatmap in [src/components/admin/activity-calendar.tsx](src/components/admin/activity-calendar.tsx). A `$1` placeholder offset bug in its filtered-query path was fixed — the dynamic SQL builder starts parameters at `$1`, not `$2`.

**"For You" recommendations** — [src/lib/recommendations.ts](src/lib/recommendations.ts) + [src/lib/recommendation-graph.ts](src/lib/recommendation-graph.ts) + [src/lib/recommendation-quality.ts](src/lib/recommendation-quality.ts)
- Split by what varies: the SERVER-WIDE half (a title's suggestion edges and its quality verdict) is precomputed once per instance into `TitleSuggestion` + `RecommendationTitle`; the PER-USER half (seed selection, weighting, exclusions, ranking) is arithmetic over the caller's own rows — server play history, the imported Trakt history (guardrail 34c, merged into the history pool under the same cap), watchlist and requests.
- The `warm-library` cron (daily) pre-builds the same suggestion edges alongside its metadata walk (`prewarmSuggestionEdges`), so the graph is normally already warm — an accelerant only; the required build below still runs unconditionally.
- `warmRecommendationsCache` (the `warm-recommendations` cron, 12h) runs in three phases: **select** every active user's seeds, **build** the graph for exactly that union (uncapped), then **compute** each user from the same plan. There is no live fallback anywhere — the ordering is what guarantees coverage, and `conclusive` (seed-coverage based) is what stops an incomplete build from replacing a good shelf. Guardrail 40 has the rules.
- `getUserRecommendations` is the only live-request read: it re-filters the stored shelf against the user's CURRENT watchlist/watched/hidden/requested state, which is genuinely per-user and stays that way. `recommendedBecause.seeds` is attached only with `{ includeSeeds: true }` (the /for-you page and `/api/recommendations`); the home rails take the default and carry `seedCount` alone.

**Request watch grades** — [src/lib/watch-grade.ts](src/lib/watch-grade.ts) (pure rules) + [src/lib/watch-grade-data.ts](src/lib/watch-grade-data.ts) (prisma)
- Grades each user A–F (by default A 80%+, B 60%+, C 40%+, D 20%+, once 3 requests are scored) on the share of their APPROVED requests that became AVAILABLE they went on to watch, from `PlayHistory` (approval counts per title on an instance, for everyone who requested it; pending and declined requests, and requests whose title nobody approved, never count — `MediaRequest.approvedAt`). A request they skipped still counts as watched once enough OTHER people watched it (`watchGradeOtherViewers`, default 2). **Display-only** by product decision: a chip on Admin → Users and beside each requester in the request queue, opening the per-request breakdown from `GET /api/admin/users/[id]/watch-grade` (MANAGE_USERS or MANAGE_REQUESTS). Nothing reads it to gate requests, quotas or auto-approve.
- Computed on demand in one batch (no table, no cron). Tuned by `watchGradeGraceDays` / `watchGradeWindowDays` / `watchGradeTvPercent` / `watchGradeOtherViewers` / `watchGradeBandA`–`D` / `watchGradeMinRequests` (Settings → Media → Watch Grades, which previews the letter spread before saving via ADMIN-only `POST /api/admin/watch-grade/preview`) and switched off by `feature.behavior.watchGrades`; hidden entirely while play history tracking is off. Guardrail 34a has the rules.

**Library cleanup** — [src/lib/library-cleanup.ts](src/lib/library-cleanup.ts) (pure rules) + [library-cleanup-data.ts](src/lib/library-cleanup-data.ts) (prisma) + [library-cleanup-arr.ts](src/lib/library-cleanup-arr.ts) (Radarr/Sonarr listing + delete), page `/admin/cleanup` behind `feature.admin.cleanup` (default OFF), ADMIN-only.
- Maintainerr-style: a title is a candidate when ANY enabled rule matches (unwatched N days, never watched + N days in the library, ≥N deletion votes) and NO exclusion applies (recently added, pending/approved request, recently fulfilled request, on a watchlist, playing now, still airing, protected via `CleanupProtection`). Rules are `cleanup*` Setting rows edited on the page (`/api/admin/cleanup/settings`). Computed on demand, no cron, NOTHING deleted automatically. The uncached report GET is rate-limited 30/min per admin.
- The still-airing exclusion reads Sonarr's own status for every series it manages — a tvdb-only one (Sonarr v3) through TMDB's TVDB cross-reference, the lookup the delete uses (`fillAiring`) — before TMDB's cached status; unknown means neither answered.
- **The tmdb→tvdb cross-reference is cache-only on read paths** (`CrossRefMode` in [library-cleanup-arr.ts](src/lib/library-cleanup-arr.ts); `resolveArrTargets` takes it as a REQUIRED argument, so every caller chooses). The cleanup GET, the never-watched report and the `/admin/stats` figure pass `"cached"`: they read only the `tmdb-to-tvdb:` cache rows, a miss reads as "no cross-reference", and the misses go to ONE bounded per-process background drain, so the next load has them. Only the delete route passes `"fetch"` — it must find every copy it removes (14b). On Sonarr v3 every series is tvdb-only, so a cold cache used to cost one TMDB call per show inside a page render, past a proxy's patience (the 37a problem). The report stays a subset of the dry run: a missed cross-reference leaves a tvdb-only show with no copies, so it is never eligible.
- "Requester never watched it" is deliberately not a rule: answering it honestly needs the watch grade's per-account identity resolution (34a), which is not cheap.
- Deletion is a dry run then an execute echoing the count; guardrail 14b has the rules, including the `cleanedUpAt` stamp that stops the sync re-pushing a deleted title. A delete takes at most `CLEANUP_MAX_ITEMS` (500) titles: the route's parser (`parseCleanupItems`) and both pages' selections read that one constant ([library-cleanup.ts](src/lib/library-cleanup.ts)), so "Delete selected" never offers a request that can only 400.
- An execute answered by a proxy's 502/503/504, by a body that isn't the route's JSON, or by nothing at all is OUTCOME UNKNOWN (`cleanupExecuteFailure`, [cleanup-execute-outcome.ts](src/lib/cleanup-execute-outcome.ts)): the page drops the plan, reloads, and says titles may already be gone — never "the delete failed" while "Delete N now" is still offered. The Radarr/Sonarr listing retries a 502/503/504 once, and only when the first attempt failed fast (≤10 s), so a slow gateway can't double the 30 s listing the synchronous dry run and execute wait on (the 37a proxy-hold problem).

**Request "Pick release"** — `GET/POST /api/requests/[id]/releases` (MANAGE_REQUESTS): interactive search on an APPROVED/AVAILABLE request's own instance, the same projected `ArrRelease` list the Issue "Replace" panel uses. Each release's `guid` is replaced by an OPAQUE handle bound to the request, instance and season ([release-handles.ts](src/lib/release-handles.ts), 30-minute TTL, in memory): some indexers — and Prowlarr's proxied feeds — build the guid from the apikey'd download link, and this list reaches delegates, not only admins. The grab POSTs the handle, never a guid (410 when expired or from another search). The grab CLAIMS the handle synchronously before calling the arr (`claimReleaseHandle`): a second grab racing the first is 409 with nothing sent (a double submit or replay would otherwise reach the download client twice). A definite refusal (`grabDefinitelyRefused`: a 4xx answer other than 408, or the title missing from the arr) hands it back, and so does a failure BEFORE the grab is sent (no config, the title lookup, the tvdb resolution — `GrabProgress.sent` in [arr.ts](src/lib/arr.ts), set on the line before `postReleaseGrab`), because nothing reached the arr. An accepted grab, a 408/5xx (a gateway that gave up, an arr mid-restart — the grab may have gone through), a timeout or a network failure spends it. The same rule holds on all three grab routes. It is offered only for movies, EPISODE issues and SEASON issues with a season (`seriesReleaseScopeSearchable`, [release-scope.ts](src/lib/release-scope.ts)): a whole-series TV issue has no release search — 422 for both the search and the grab, and `getReleasesForSeries` throws `ReleaseSeasonRequiredError` rather than build the series-only (RSS) query — so it uses Refetch or Replace file instead.

A job is readable by its OWNER only, and the same owner re-searching the same scope while one runs JOINS it (no second indexer hit, no rate token). A finished answer (a whole release list) is readable for 10 minutes and every expired one is swept on each start and poll, never left to fill the map; a search that throws answers 500. So does the issue Replace panel (`GET /api/issues/[id]/releases?async=1`, polled at `?job=`); its synchronous bare-array default stays for the iOS app. Both pages poll through ONE client loop, `runReleaseSearchJob` ([release-search-job.ts](src/lib/client/release-search-job.ts)). Every `/api/v3/release` read carries `RELEASE_SEARCH_TIMEOUT_MS` (120 s) — the arr's own search is the slow part, and the job is what keeps that wait off the proxy — and every grab POST carries `RELEASE_GRAB_TIMEOUT_MS` (120 s) through `postReleaseGrab`, the only grab call: the arr fetches the .torrent/.nzb from the indexer before it answers. The synchronous default stays for API callers.

## Deployment

Multi-stage Docker (`node:26.3.0-alpine3.23`, five stages: deps → prisma-gen → builder → migrate-deps → runner) → standalone Next build, non-root `nextjs` user (UID 1001). Postgres 17-alpine sidecar with `postgres-data` volume. Internal port 3000 → host 3001. The image creates `/data` (app) and `/app/.next/cache` dirs, but neither compose file mounts them as volumes — only `postgres-data` is persisted. There are **no** external `sync-cron` / `upcoming-cron` compose services: the app container runs its **own internal cron loop** (`docker-entrypoint.sh` `_cron_loop` + `_play_history_loop`), POSTing to `http://localhost:3000/api/...` with `Bearer ${CRON_SECRET}` so the secret never leaves the container. **Image-size discipline**: the migrate-deps stage prunes the Prisma CLI's dependency tree via [scripts/prune-migrate-deps.mjs](scripts/prune-migrate-deps.mjs) (~250 MB → ~66 MB — studio/dev tooling, mysql2/postgres drivers, typescript, react, etc. are never loaded by `db push`), then a build-time smoke test runs a real `db push` against an unreachable DB and requires the P1001 error — proving the pruned module graph still loads — before the tree ships. **That smoke test runs unconditionally, and it must stay that way — do NOT re-add a cross-build skip.** It was briefly gated on `TARGETPLATFORM == BUILDPLATFORM` because under QEMU the pruned CLI's wasm get-config returns corrupted bytes and reports every line of a valid schema as unparseable, which blocked the v0.25.0 release twice. That was an emulator fault, not an arch or schema one — proven by `--platform linux/arm64 --target migrate-deps` passing on a native arm64 host while the emulated CI build failed identically. **The skip is unnecessary because nothing cross-builds any more**: [docker-publish.yml](.github/workflows/docker-publish.yml) builds each platform on its own native runner (`ubuntu-latest` for amd64, `ubuntu-24.04-arm` for arm64, stitched by `docker buildx imagetools create`), and the security gate + ci.yml's docker build are amd64 on amd64 hosts. Native arm64 went from a **cancelled 3h0m22s** emulated build — GitHub's hard job ceiling, so no `timeout-minutes` could have saved it — to **~3 min**. If you ever reintroduce an emulated leg you will hit the wasm bug again; add a native runner, not a skip. The native `schema-engine-*` binary in `@prisma/engines` MUST stay: `db push` executes it and silently re-downloads it at boot when missing (a boot-time internet dependency; the bundled wasm schema engine is NOT used). The builder stage also strips the glibc sharp/libvips variants (`@img/sharp-*linux-*`) from the standalone output — the Alpine runtime is musl-only, and `outputFileTracingExcludes` does not actually drop them (tested; hence the explicit `rm`).

## Releasing — PR-then-tag flow

The project version is duplicated across four files. Drift is the default unless every bump touches all of them in the same commit.

**The git tag is `v<X.Y.Z>`; the published image tag is bare `<X.Y.Z>`. NEVER write a `v` into a `SUMMONARR_VERSION` example.**

- `docker/metadata-action`'s `type=semver,pattern={{version}}` **strips the `v`** ([docker-publish.yml](.github/workflows/docker-publish.yml)), so pushing git tag `v0.20.2` publishes `:0.20.2`, `:0.20`, `:0`, `:latest`, `:sha-<short>` — and no `:v0.20.2`.
- [docker-container/docker-compose.yml](docker-container/docker-compose.yml) interpolates the value straight in: `ghcr.io/summonarr/summonarr:${SUMMONARR_VERSION:-latest}`. A `v`-prefixed value therefore resolves to a tag that does not exist and the pull fails with `manifest unknown`.
- This shipped broken for two releases — `:v0.20.1` and `:v0.20.2` both 404 in GHCR while `:0.20.1` / `:0.20.2` are fine — because this file told you to write the `v`. Verify a pin before documenting it:

```bash
TOK=$(curl -s "https://ghcr.io/token?scope=repository:summonarr/summonarr:pull&service=ghcr.io" | python3 -c "import sys,json;print(json.load(sys.stdin)['token'])")
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $TOK" https://ghcr.io/v2/summonarr/summonarr/manifests/<X.Y.Z>
```

The release flow is **PR-then-tag**: bump versions on `build`, PR to `main`, merge, *then* tag the merge commit on `main`. Tagging before the merge orphans the tag on a feature-branch commit unreachable from `main` — `git describe` breaks, `:v<X.Y.Z>` and `:main` reference different SHAs, and the [docker-publish workflow](.github/workflows/docker-publish.yml) builds the same release twice from two different commits. (`v0.9.1` and `v0.9.2` were tagged this way; both are orphan tags. Don't repeat it.)

### Step 1 — Bump versions on `build`

`<X.Y.Z>` is bare semver; the docker tag form is `v<X.Y.Z>`. Edit all five locations in one commit:

1. [package.json](package.json) — `"version": "<X.Y.Z>"` (root field).
2. [package-lock.json](package-lock.json) — `"version": "<X.Y.Z>"` in **two** places only: the top-level field and `packages.""` (lockfile v3 keeps both; `npm install` will rewrite either if they disagree). **Do not** global-find-replace the old version across this file — common SemVers like `0.1.0` appear inside transitive-dep entries (e.g. `node_modules/yocto-queue`, `node_modules/powershell-utils`) where the `version` field must match the `resolved` URL and `integrity` hash. Edit the two project entries individually.
3. [README.md](README.md) — the `Status: v<X.Y.Z>` line at the top. The project is stable, not beta (since v0.33.0) — don't reintroduce a beta label.
4. [docker-container/README.md](docker-container/README.md) — both `SUMMONARR_VERSION=<X.Y.Z>` examples (env table row and the "Pin to a specific version" code block). **Bare semver, no `v`** — see above.
5. [README.md](README.md) `## Changelog` — **prepend** a new `### v<X.Y.Z>` block above the previous release. Group bullets under `**Added**` / `**Changed**` / `**Fixed**`. Source entries from `git log v<previous>..HEAD --oneline`, surfacing user-visible changes only (skip `chore`, `refactor`, `deps`). Conventional-commit scopes translate cleanly.

```bash
git commit -am "chore(release): v<X.Y.Z>"
git push origin build
```

### Step 2 — PR `build` → `main`

```bash
gh pr create --base main --head build --title "Build" --body "<changelog summary + test plan>"
```

Wait for review and CI. Merge.

### Step 3 — Tag the merge commit on `main`

```bash
git checkout main && git pull
git tag -a v<X.Y.Z> -m "v<X.Y.Z>"
git push origin v<X.Y.Z>
```

### Why this order

- The PR merge fires [docker-publish.yml](.github/workflows/docker-publish.yml) on the `main` push, but the job **deliberately skips** when the push contains a `chore(release):` commit (the `if:` at [docker-publish.yml:55](.github/workflows/docker-publish.yml#L55)) — the tag push publishes the same SHA, so building here would duplicate ~11 min of work. A *non-release* push to `main` still publishes `:main` and `:sha-<short>`.
- The tag push then runs the only build for the release → publishes `:<X.Y.Z>`, `:<X.Y>`, `:<X>`, `:latest`, and `:sha-<merge>` (bare semver — the `v` is stripped, see above). Expect ~11-15 min: this is a cold multi-arch `linux/amd64,linux/arm64` build, NOT a cache hit off an earlier main-push build, because that one skipped.
- Tag is reachable from `main` — `git describe` works, and `:latest` / `:<X.Y.Z>` / `:sha-<merge>` all reference the same commit SHA.

**NEVER** force-move a published tag (`git push --force origin v<X.Y.Z>`) to fix a misplaced one. Anyone with `SUMMONARR_VERSION=<X.Y.Z>` pinned silently gets new bits on the next pull, and `:latest` re-resolves on `docker compose pull`. Cut a new patch release instead.

There is no version constant in `src/`. Don't add one — `package.json` + the git tag is the source of truth, and a third copy is a third place to forget.

## Guardrails

1. **Next.js 16 is not the Next.js in your training data.** Before editing routing, caching, metadata, `fetch`, server/client boundaries, or anything framework-shaped, read the relevant file under [node_modules/next/dist/docs/](node_modules/next/dist/docs/) (`01-app/`, `03-architecture/`). Do not pattern-match from Next 13/14/15 memory.

2. **Never remove the `?token=` webhook query param.** Sonarr and Radarr webhook UIs have no header field, and both handlers share the same code path. (There are no Plex/Jellyfin webhook handlers — only `radarr` and `sonarr`.) Keep the timing-safe compare. Do not "upgrade" to HMAC — the upstream services do not sign requests.

2a. **The webhook token NEVER leaves the server during one-click setup — not in a response, not in an audit row, not in an error the arr echoes back.** `setupArrWebhook` ([arr-health-data.ts](src/lib/arr-health-data.ts)) builds the `?token=` URL itself and writes it straight into Radarr/Sonarr.

    Why:
    - The arr test-POSTs the URL before saving, and its HTTP error text quotes the request URL — token included. Relayed verbatim, the refusal shown to the admin (and logged) would carry the secret.
    - The health report is polled by the browser; a URL in it would put the secret in the RSC/devtools surface the copy-on-click design (`/api/settings/webhook-urls`) exists to avoid.

    Rules:
    - Refusal text goes through `arrValidationMessage`, which masks `token=`. The health GET returns only the verdict (`ok`/`missing`/`tokenMismatch`/`eventsMissing`). The `SETTINGS_CHANGE` audit records the BASE address, never the URL.
    - An instance with no secret gets one generated, create-if-absent (`setting.createMany` + `skipDuplicates`, encrypted by the Prisma extension — guardrail 7a), so two setups racing end on ONE secret instead of the second stranding the first hook's token. The generation is audited the moment it commits, even if the arr then refuses the hook. The default instance reuses the legacy shared `webhookSecret` when it has no own secret, exactly as the handlers resolve it.
    - An existing Connect entry pointing at `/api/webhooks/<service>` is updated IN PLACE (PUT), keeping the admin's name, tags and extra events; only the URL and Summonarr's handled events (`WEBHOOK_EVENTS`) are set — never a second entry.

3. **Schema-first Prisma.** No migrations directory exists. Schema changes are applied with `prisma db push`, then `prisma generate`. Do not scaffold `prisma migrate` workflows.

4. **Bulk writes must use `batchCreateMany` + `BATCH_TX_TIMEOUT`.** Raw `createMany` on library-sized datasets blows transaction timeouts. Always chunk via `batchCreateMany` and pass `{ timeout: BATCH_TX_TIMEOUT }` to `$transaction`.

5. **Do not lower `ARR_FETCH_MAX_BYTES` (50 MB)** and do not bypass `arrFetch` with bare `fetch` for Radarr/Sonarr calls. The cap exists because large libraries silently truncated at 10 MB.

5a. **Pick the right `safe-fetch` helper.** Never call `fetch` directly for outbound HTTP. Hardcoded third-party URL → `safeFetchTrusted(url, { allowedHosts: [...] })`. URL persisted in `Setting` (Radarr/Sonarr/Jellyfin/Plex server) → `safeFetchAdminConfigured(url)`. URL from end-user input → `safeFetch(url)`. The `allowedHosts` arg on `safeFetchTrusted` is required and exists so a future code change can't accidentally fan that path out to user-controlled hosts.

5b. **Sole allowed direct `fetch` (internal loopback)**: The *only* exception to 5a is the controlled loopback in `src/lib/internal-trigger.ts` (`triggerFullSync`). It is used exclusively by the Plex SSE timeline handler (`plex-events.ts`) to drive a full orchestrator run (`/api/sync`) so that the advisory lock (2000), `withCronRunRecording`, `isCronAuthorized`, and `LIBRARY_SYNC` audit path are identical to an external cron. Target is always `http://127.0.0.1:${PORT}/api/sync` authenticated with `CRON_SECRET`. Update this note (and the helper) if you ever need another internal trigger. All other server HTTP must go through the safe-fetch helpers.

5c. **A queue removal is ONE bulk `DELETE /api/v3/queue/bulk` carrying ONE record id per download (`removalIds`), with every flag sent explicitly.** `removeFromQueue` + `queueRemoveQuery` ([arr-queue-data.ts](src/lib/arr-queue-data.ts), [arr-queue.ts](src/lib/arr-queue.ts)).

    Why:
    - Sonarr reports a season pack as one queue record PER EPISODE, and ANY one of them resolves the whole tracked download on v3 and v4 (MarkAsFailed, RemoveItem and StopTracking act per download). Removing them one id at a time removes the download on the first call and the rest 404; sending them ALL in one bulk call is no better on v3 — its bulk Remove loops over the ids with no dedupe and stops tracking only after the loop, so N ids blocklist the release N times and call the client's RemoveItem N times (Deluge errors on the repeat). v4 dedupes by downloadId anyway; repeated searches are deduped by the arr's command queue.
    - Radarr and Sonarr default `removeFromClient` to TRUE. An omitted flag is not "off": dropping it deletes the files from the download client when the admin asked only to stop tracking.

    Rules:
    - Send `removeFromClient`, `blocklist`, `skipRedownload` and `changeCategory` on every call. "Blocklist and search" is `blocklist=true&skipRedownload=false` — the arr's own redownload logic, which honours its "Redownload Failed" setting; don't add a second search of ours on top (it doubles the indexer hits).
    - The removal METHOD maps onto the flags and nothing else: `removeFromClient` → `removeFromClient=true`; `changeCategory` → `changeCategory=true` (and `removeFromClient=false`); `ignore` → both false, which the arr reads as "stop tracking, leave it in the client". The older `removeFromClient: boolean` body maps true/absent → `removeFromClient`, false → `ignore`; an explicit `method` wins. Offer `changeCategory` only when the row's `canChangeCategory` (the arr's `downloadClientHasPostImportCategory`) says the client has one.
    - Sonarr v3 reads only `removeFromClient` and `blocklist` on a queue removal — `skipRedownload` and `changeCategory` are ignored — so on v3 a blocklist always triggers the arr's redownload-failed search when that setting is on. The dialog says so for a v3 instance (`honoursSkipRedownload`, version from the health report); never promise "no search" there.
    - `tests/arr-ops.test.mts` and `tests/arr-ops-routes.test.mts` pin all of it, mutation-verified; the one-id-per-download and v3 rules are pinned in `tests/audit-fix-release-queue.test.mts`.

5e. **On every admin arr route, a value from the browser is only ever a NAME for something the instance itself reports for that title — and no provider `fields`, history `data`, release guid or upstream credential reaches the browser, a log line or an audit row.** The 5d rule, generalized to the title manager, history, blocklist, calendar and system routes.

5f. **An issue's Replace file deletes ONLY files the instance reports inside the issue's scope, re-read at POST time, and it blocklists with ONE Mark failed per DOWNLOAD.**

    Why:
    - A search can't replace a file on disk unless it finds an upgrade — a corrupt file at cutoff left the issue IN_PROGRESS with nothing that could ever fix it.
    - Marking the wrong grab blocklists a release that isn't the one on disk; marking a pack once per episode is the 5c per-episode trap (blocklists and searches N times).

    Rules:
    - Every id must be one of the in-scope files read now (`chooseFiles`; FULL = all, SEASON = that season's, EPISODE = the file holding the S/E). A miss is 409 with no CAS and nothing deleted (5e).

Only a throw with nothing gone answers the arr failure. File deletes carry a 120 s timeout (a recycle bin on another filesystem makes each delete a copy).
    - A file's grab is the newest grab of the download its newest import came from, recorded before that import. It is UNKNOWN — searched for, never guessed — when a non-"Upgrade" deletion followed that import, when a movie has two files and no import's `importedPath` matches, when a multi-episode file's episodes came from different downloads, or when the import it would fall back to names a DIFFERENT path with no later rename record of the unit naming the file (an unrecorded manual in-folder import, or a folder move — both lose attribution and are searched for).

A mark covers its files only when the arr's own redownload will follow it (`redownloadCovers`): `/api/v3/config/downloadclient` says `autoRedownloadFailed: true` AND, for a grab whose history `releaseSource` is `InteractiveSearch` (every Summonarr Pick release / Replace release grab), `autoRedownloadFailedFromInteractiveSearch` is not false — absent on an older arr ⇒ the main switch decides — and, for Radarr, the movie does not read `isAvailable: false`: its redownload is an automatic MoviesSearch, which applies Minimum Availability (our manual one does not), so a not-yet-available movie is not covered and we search. Config unreadable ⇒ nothing is covered and we search ourselves; history unreadable ⇒ every grab counts as interactive. The cost of guessing wrong is one extra search, never none.
    - **"Unmonitor deleted episodes/movies" is undone, exactly.** With that arr setting on, the manual delete unmonitors what it deleted, and a monitored-only SeasonSearch or the arr's redownload then finds nothing. The route reads `monitored` before the delete, re-reads after, and sets back ONLY what flipped monitored→unmonitored (`unmonitoredByDelete`; Sonarr `PUT /api/v3/episode/monitor`, Radarr the movie editor) before any mark or search, audited `ARR_TITLE_EDIT` after the arr accepts it. Something the admin had unmonitored beforehand stays unmonitored. A failed re-monitor or re-read answers `remonitorFailed: true`, no mark counts as covering, and the search names the files' episodes (EpisodeSearch) or the movie (manual MoviesSearch).
    - The dialog shows Sonarr's own episode TITLES beside S/E and the file name (the issue's numbering is the media server's, Sonarr's is TVDB's), and an anime series carries a numbering note.
    - Search shape (`followUpSearch`, never SeriesSearch): movie MoviesSearch; EPISODE EpisodeSearch; SEASON SeasonSearch only when nothing of it is left and 2+ episodes went, else EpisodeSearch; FULL the Missing plan's season-pack rule applied to the DELETED episodes only (`{ kind: "plan" }` — a SeasonSearch per regular season emptied with 2+ of them gone, one EpisodeSearch for the rest, deleted specials and undated episodes included, which the Missing plan's aired-regular-season rule could never reach) — never the series' whole missing backlog. The Missing plan itself only when the deleted files named no episodes; an EpisodeSearch naming them when the arr unmonitored them.

5h. **An admin arr page paints its last answer at once and then reads live — and a snapshot is DISPLAY ONLY: nothing that writes ever reads one.** Server: [arr-snapshot.ts](src/lib/arr-snapshot.ts) (`withAdmin(snapshotted(…))` on each admin Radarr/Sonarr READ route); client: [use-arr-snapshot.ts](src/components/admin/use-arr-snapshot.ts) + [arr-snapshot-note.tsx](src/components/admin/arr-snapshot-note.tsx).

    - Every arr page used to open on a spinner until Radarr/Sonarr answered — seconds on a big library, the full 30 s timeout on a dark instance. The admin asked for "instant, then live": the last-known view at once, marked with when it was read, then the live read swapped in.
    - The danger is an action decided on old data. Every admin arr write already re-checks against a FRESH read of the instance (5d/5e), so a row painted from a snapshot is only a NAME the server re-judges — that, and only that, is what makes painting stale data safe.

    Rules:

Only a live 200 JSON is kept: a single-instance read that fails (5xx) leaves its last good answer on screen, marked stale, while a multi-instance report that answers 200 with one instance in `errors[]` is kept exactly as answered. `job=` polls are never kept.

    export const GET = withAuth(async (req, ctx, session) => { ... });        // any authenticated user
    export const POST = withAdmin(async (req, ctx, session) => { ... });      // ADMIN only
    export const PATCH = withIssueAdmin(async (                               // ADMIN or ISSUE_ADMIN
      req,

6b. **Session auth is dual-transport: HttpOnly cookie (web) OR `Authorization: Bearer <session-jwt>` (native/mobile clients).** Added for the iOS app (Phase 0). The bearer token is the *same* session JWT the cookie carries — there is no separate token type.

    Why the rules below exist:
    - A native app has no cookie jar, no web `Origin`, and an arbitrary `User-Agent`. The browser-shaped gating (CSRF Origin check, UA-fingerprint binding, 302→HTML login) rejects it unless these paths know about bearer auth.
    - Bearer and the `X-Summonarr-Client` tag are *custom* headers a cross-origin page cannot attach to a credentialed request (CORS preflight blocks them), so they are sound CSRF-skip / fingerprint-skip signals — a cookie-riding forgery can carry neither.

    Rules:
    - **Every session reader resolves bearer-FIRST, then cookie.** The helper is `parseBearerToken` ([src/lib/mobile-auth.ts](src/lib/mobile-auth.ts)). Current readers: [src/proxy.ts](src/proxy.ts), `authenticateRequest` + `requireAuth` ([src/lib/api-auth.ts](src/lib/api-auth.ts)), [/api/auth/me](src/app/api/auth/me/route.ts), [/api/auth/sign-out](src/app/api/auth/sign-out/route.ts). If you add a new path that reads the session cookie directly (`parseSessionCookie` / `cookies().get(getSessionCookieName())`), add the bearer fallback too or native clients silently 401 on that route only. Bearer-first (not cookie-first) is load-bearing: it stops a forged cookie from riding a request a bearer made CSRF-exempt.
    - **CSRF Origin check and UA-fingerprint check skip when the request is bearer/native.** Don't "tighten" the proxy CSRF block or the `matchesStoredFingerprint` callsites back to unconditional — you'll lock out the app. Bearer sessions deliberately drop UA-binding (the JWT lives in the Keychain, not an ambiently-replayed cookie); the remaining defenses (JWT signature, DB revocation, `sessionsRevokedAt`/`passwordChangedAt` cutoffs, sessionId rotation, expiry) still apply.
    - **The session JWT reaches a native client ONLY via the sign-in response body, ONLY when the client sends `X-Summonarr-Client`.** Go through `buildSignInResponse` ([src/lib/sign-in-response.ts](src/lib/sign-in-response.ts)) — never return `result.token` in a body unconditionally (that would expose the JWT to web JS and defeat HttpOnly).
    - **OIDC has a SECOND, native-only path, and the two must not be crossed.** The web flow is unchanged: `/api/auth/oidc/start` 302s and sets the HttpOnly state cookie, and `/api/auth/oidc/callback` exchanges the code and mints the session cookie itself. Native clients cannot use it — `/start` is called by the app's own HTTP client while the IdP redirect lands in a separate web-auth view with its own cookie jar, so the callback sees no flow cookie. For a caller sending `X-Summonarr-Client`, `/start` instead returns `{ authorizeUrl, flowState, callbackScheme }` as JSON (mirroring `/api/auth/plex/start`), the callback bounces `(code, state)` to `summonarr://oidc-callback`, and the app finishes at `POST /api/auth/sign-in/oidc`. Load-bearing details: the native flow is detected by a `nat.` PREFIX on the OIDC `state` (`isNativeOidcState`), because `state` is the only value that round-trips without the cookie — it is ROUTING information, never an authorization; the code bounced through the custom scheme is safe precisely because the PKCE `codeVerifier` and expected nonce live only inside the signed `flowState` the app holds, so an intercepted code cannot be redeemed; the callback's native branch must NEVER exchange or set a session cookie; `/api/auth/sign-in/oidc` REFUSES a flow state lacking the native marker, so a stolen web flow cookie can't be replayed through the native path to trade a code for a bearer token; and the custom-scheme target is a hardcoded constant (`NATIVE_OIDC_CALLBACK_URL`) — accepting a client-supplied one would turn the callback into an open redirect that leaks the code.
    - **No refresh for bearer clients** — they can't read `Set-Cookie`, so they keep presenting the token they were handed at sign-in. That token never expires by time: a native sign-in's deadline is the never-reached sentinel (guardrail 6c), so there is nothing to refresh and no Phase-3 refresh-token grant is needed for longevity. Don't append `Set-Cookie` on a bearer request (guarded by `!bearerToken` / `!result.fromBearer`). The `X-Summonarr-Client` header ALONE selects the never-expiring session; `rememberMe` and a mobile `User-Agent` only affect the device label (send them anyway so the device list reads right).
    - **That forbids handing the CLIENT a new token; it does NOT forbid the server-internal forwarded-header rewrite, which is REQUIRED for both transports.** Every request is session-verified twice (proxy, then `authenticateRequest`/`authActive`), and both read the credential off the request `proxy.ts` forwards. So when `verifyAndRefreshSession` re-signs, `proxy.ts` must rewrite the forwarded credential with the new token — `cookie` via `replaceSessionCookie` for browsers, `authorization` as `Bearer <token>` for bearer — BEFORE constructing `NextResponse.next({ request: { headers } })` (Next snapshots those into `x-middleware-request-*` at construction; mutating after is a no-op). `dbCheckedAt` is stamped ONLY by that re-sign and is never present at mint (`initializeTokenOnSignIn`), so a transport left out of the rewrite can never carry the claim, can never take the fast path, and pays the full DB-checked verify on BOTH passes — 6 session queries per request instead of 3. It also means a sessionId rotation (privilege change) kills the second pass, since the credential the client sent is already dead. Gating the rewrite on `!bearerToken` was exactly that bug. The client still receives nothing: no `Set-Cookie`, no token in a body, and it keeps presenting its original token.

6c. **A session lives until its sign-in deadline — nothing shortens it, nothing caps it, and a native session has no deadline at all.** `verifyAndRefreshSession` rejects a token past the `expiresAt` claim and otherwise re-signs with `exp` AT that claim; `initializeTokenOnSignIn` sets the claim to the admin-configured desktop/mobile/remember-me duration for browsers and to `NEVER_EXPIRES_AT_SEC` ([session-lifetime.ts](src/lib/session-lifetime.ts)) for a caller presenting `X-Summonarr-Client`.

    Why:
    - Both of the things this rule forbids used to exist, and together they made the settings form a lie. A 1-hour non-ADMIN *inactivity slide* re-signed every cookie with `Max-Age ≤ 3600`, so "Remember me: 30 days" ended after any hour-long gap — every user signed in again most days and blamed whatever had happened last (a deploy). A 7-day *ADMIN ceiling* (iat-based on the fast path, `AuthSession.createdAt`-based on the slow path) signed the operator out weekly, which lined up exactly with the weekly Dependabot cadence and read as "bumping deps logs everyone out".
    - A bearer client has no refresh channel (guardrail 6b), so any finite TTL is a forced re-login at that TTL. The old fixed 1-year native TTL was the same bug on a longer fuse; now a native session ends only through revocation — sign-out, per-device revoke, revoke-all, a password change, account deactivation — all of which the DB-checked verify already honours on the next request, independent of any deadline. The deadline was never the security boundary; revocation is.

    Rules:
    - **Never reintroduce an inactivity window or a role-based ceiling** in `verifyAndRefreshSession`. If a shorter admin session is wanted, it belongs in the *configured durations* (Admin → Settings → Session), which already cap at 90 days. `tests/session-refresh.test.mts` pins both: an 8-day-old ADMIN session (old iat AND old `createdAt`) survives both paths, and an idle remember-me session survives a 29-day gap and dies one second past its deadline. They were mutation-tested — each reintroduction fails a named test.
    - **"Never expires" is a sentinel deadline, NOT an absent claim.** `exp`, the `expiresAt` claim, the non-null `AuthSession.expiresAt` column and the `/api/sessions` wire contract all expect a number/date — and the iOS app decodes each device's `expiresAt` as a **non-optional string**, so a `null` there breaks the Sessions screen of every shipped build. Test for it with `isIndefiniteDeadline`, never `expiresAt == null`.
    - **The only housekeeping allowed to delete an `AuthSession` row is the `expiresAt < now` sweep** in [purge-auth-sessions](src/app/api/cron/purge-auth-sessions/route.ts). A "sessions older than N days" / "idle for N days" sweep on `createdAt`/`lastSeenAt` would sign every iOS user out on its first run; `tests/cron-routes.test.mts` pins the predicate's shape.
    - The native selection keys on the `X-Summonarr-Client` header alone (a custom header a cross-origin page cannot attach — guardrail 6b), never on `rememberMe` or a UA-derived device class: a spoofed mobile UA must not mint a never-expiring *cookie*.

6d. **For a LOCAL-CREDENTIALS account with two-factor, a correct password NEVER mints a session — only a challenge. The session is minted ONLY by `POST /api/auth/sign-in/mfa`, through the same `signInAndMintSession` + `buildSignInResponse` as the password path.** Libraries in [src/lib/mfa/](src/lib/mfa/); the password-step branch is `mfaChallengeFor` ([signin-challenge.ts](src/lib/mfa/signin-challenge.ts)).

    Why:
    - A second factor that any path can skip is not a second factor. The credentials route is the only place a password becomes a session, so the branch lives there, BEFORE `signInAndMintSession`; and the second step reuses the mint chokepoint (guardrail 33) and the response builder (6b) instead of a parallel copy that could drift on deactivation, the native-token gate or the session lifetime (6c).
    - Plex/Jellyfin/OIDC are out of scope by design — their IdP owns MFA. Two-factor is offered only to accounts with a `passwordHash` whose session provider is `credentials` (`mfaReauthStepUp` / `mfaEligibleUser` in [step-up.ts](src/lib/mfa/step-up.ts)).

    Rules:
    - **The factor ROWS are the only source of truth for "has 2FA"** (`getMfaState`: an ENABLED `UserTotp` or any `WebAuthnCredential`). Never add a denormalized `User` flag — one that drifts to false silently skips the second factor. A pending (unconfirmed) TOTP setup is not a factor. A failed factor lookup must propagate (500), never fall through to the no-2FA branch.
    - **An account WITHOUT 2FA gets a byte-identical password response.** The iOS app depends on it; `tests/mfa-routes.test.mts` pins it with `deepEqual`. The challenge is **HTTP 401** `{ error, mfaRequired: true, methods, mfaToken, expiresInSeconds, webauthn? }` with `Cache-Control: no-store` — 401, not 200, so a client that predates 2FA shows `error` instead of reading a success with no token.
    - **The challenge token can never be a session.** `mfa-token.ts` signs it with an HKDF subkey of `NEXTAUTH_SECRET` (per purpose), its own `typ` and audience, and no `id`/`role` claims — `verifySessionJwt` rejects it on the signature alone, and it rejects a session JWT the same way. Never sign one with the raw session secret. It is single-use (consumed on success), burns after `MAX_TOKEN_FAILURES`, lives 5 minutes, carries `rememberMe` and the `native` flag from the password step (the MFA step must present the SAME native-ness — the header selects the never-expiring session and the body token), and a password fingerprint (`pwv`, an HMAC under its OWN HKDF subkey `summonarr:pwv:v1` — never the raw secret) so a password change between the steps kills it. The jti ledger is in-process (guardrail 17), and every token is REGISTERED at mint: an unknown jti is dead (a restart kills in-flight tokens), at most `MAX_LIVE_PER_SUBJECT` (5) are live per user — a sixth evicts that user's oldest — and a full ledger evicts expired then oldest entries, never refusing the newcomer (the old fail-closed-at-50k let one account with its own password block every MFA sign-in). An evicted entry is never recreated fresh, so eviction can't un-burn a token.
    - **Claim the challenge BEFORE touching the factor.** `POST /api/auth/sign-in/mfa` does `reserveToken` (a synchronous check-and-set — at most one request per token is ever verifying) → verify → `commitToken` on success / `releaseToken({ failed })` on a miss; a parallel request on a reserved token gets 409 without verifying anything. The factor verifiers BURN single-use DB state, so the old verify-then-consume let two parallel requests on one token spend two recovery codes. The per-token failure count is incremented synchronously at release. `tests/mfa-routes.test.mts` pins it with a gate that parks the first request inside the verifier.
    - **Second-factor guessing is bounded PERSISTENTLY** ([lockout.ts](src/lib/mfa/lockout.ts), `User.mfaFailedAttempts`/`mfaLockoutCount`/`mfaLockedUntil`) — the in-memory per-account bucket resets on restart and a correct password refunds the password-step limiter, so without a DB counter challenges (and guesses) were unlimited. Every code check — sign-in AND enrollment step-up — goes through `verifySecondFactorGuarded`, never bare `verifySecondFactor`. CONSECUTIVE wrong codes (TOTP + recovery) count; at `MFA_LOCKOUT_THRESHOLD` (10) a CAS imposes `mfaLockedUntil` (15 min, doubling per lockout, cap 24 h) — exactly one request imposes it, audited `AUTH_LOGIN_FAILED` `reason: "mfa_lockout"` post-commit and mailed to the owner. While locked every CODE is refused with one generic 429 BEFORE it is checked, so a correct code is neither accepted nor burned. A correct code resets the consecutive count; the escalation level resets only once the last lockout is more than 24 h old (an owner signing in between bursts must not hand an attacker a fresh 15-minute rung). **Passkeys are exempt both ways**: a failed assertion never counts, a passkey still works during a lockout (that is how the owner gets in while someone with their password hammers codes), and a passkey success does NOT clear the count or the lockout. Admin reset and turning 2FA off clear it (`clearMfaLockoutInTx`).
    - **Every "use once" is a conditional UPDATE whose row count decides, never a read-then-write**: TOTP `lastUsedStep < step` (a step is accepted once; ±1 step window), recovery `usedAt IS NULL`, WebAuthn `signCount = <verified value>` and `userId` in both the lookup and the CAS. A WebAuthn credential lookup is ALWAYS scoped to the user.
    - **WebAuthn is hand-rolled on purpose** ([webauthn.ts](src/lib/mfa/webauthn.ts) + the strict [cbor.ts](src/lib/mfa/cbor.ts)) — no `@simplewebauthn` dependency. It verifies type, challenge, exact origin, `crossOrigin`, RP-ID hash, UP (UV when demanded), BE/BS consistency, the signature (ES256/EdDSA/RS256 ≥2048) and a strictly increasing counter (0→0 allowed). Attestation is `none`; any other fmt's statement is ignored, never trusted. RP ID = `AUTH_URL` host; origins = `AUTH_URL` origin + `AUTH_TRUSTED_ORIGIN` entries under that host; no `AUTH_URL` ⇒ passkeys unavailable (503), never a guessed host. Every check is pinned by a real-key vector in `tests/mfa-webauthn.test.mts`.
    - **Every enrollment CHANGE takes the current password** (`mfaReauthStepUp`; TOTP `enable` is the one exception — it needs the pending secret only `setup`, which IS step-up'd, ever disclosed) and is audited `MFA_CHANGE` after the commit (`logAudit`, guardrail 26). Enabling the FIRST factor, turning 2FA off, AND removing the last remaining factor one at a time (`DELETE /totp`, `DELETE /passkeys/[id]` — `dropRecoveryCodesIfNoFactorInTx` returns whether none is left) sign out the account's OTHER sessions (`revokeOtherUserSessions` — no `sessionsRevokedAt` stamp, which would kill the current one too; ledger after the delete, guardrail 27). Removing the last factor removes the recovery codes.
    - **Once a factor is ACTIVE, every enrollment change ALSO needs a fresh second factor** (`mfaSecondFactorStepUp` in [step-up.ts](src/lib/mfa/step-up.ts), body field `secondFactor`: `{method:"totp"|"recovery", code}` or `{method:"webauthn", credential, challengeToken}` with the challenge from `POST /api/profile/mfa/challenge` — single-use, user- AND session-bound, its own token purpose). Covered: `DELETE /api/profile/mfa`, `POST /totp/setup` (adding an app beside a passkey), `DELETE /totp`, `POST /recovery-codes`, `POST /passkeys/options`, `PATCH`/`DELETE /passkeys/[id]`. Why: a session obtained by relaying the password plus ONE code through a phishing proxy could otherwise regenerate recovery codes, add its own passkey or switch 2FA off — durable access from a one-time relay. The FIRST factor stays password-only (nothing to prove). It reuses the sign-in verifiers through `verifySecondFactorGuarded` (same CAS writes, same persistent lockout budget) — never a fork; a recovery code used as proof is consumed. Two loopholes are closed with it: the passkey registration token records `factorVerified` and is refused if the account gained a factor since it was minted on the password alone, and a passkey that becomes the FIRST factor deletes any pending TOTP secret issued on the password alone (`totp/enable` takes no password, so that secret would otherwise be confirmable onto a now-2FA account). Missing proof is `400 { secondFactorRequired: true, methods }`; a lockout is 429. Every change also emails the owner via `notifyMfaSecurityEvent` ([notify.ts](src/lib/mfa/notify.ts)) — `void`, best-effort, the ordinary notification-email path; it never fails the change.
    - **Admin reset** (`DELETE /api/admin/users/[id]/mfa`) is `MANAGE_USERS`, an ADMIN target needs the ADMIN bit — re-read INSIDE the transaction under advisory lock 42 (the role-change/deactivate lock), so a promotion landing between the pre-check and the write can't let a delegated manager strip an admin's factor — the caller's own account is refused (it would skip the step-up), it clears any code lockout, revokes ALL the target's sessions and audits `MFA_RESET`. Disable-all, admin reset and **account purge** share ONE write set, `deleteAllMfaInTx`; deactivation (reversible, guardrail 33) never touches 2FA.
    - **Recovery-code writes serialize per user** — `ensureRecoveryCodesInTx`/`replaceRecoveryCodesInTx` take `pg_advisory_xact_lock(4610, <31-bit hash of the user id>)` (`lockUserMfaInTx`) BEFORE the count; under READ COMMITTED two concurrent first-factor enrollments otherwise both counted zero and one showed the user codes the other had deleted.
    - **"Prompt administrators to set up two-factor"** (Setting key `requireMfaForAdmins` — the UI label was "Require two-factor for administrators", which overstated it; [policy.ts](src/lib/mfa/policy.ts)) only redirects a local-credentials ADMIN without a factor from the `(app)/admin` layout to enrollment. It never blocks signing in, it is a policy nudge rather than an authz boundary (the API is unaffected), and `SUMMONARR_DISABLE_MFA_ENFORCEMENT=true` switches it off. The break-glass for a lone locked-out admin is `scripts/reset-password.mjs … --reset-mfa`.
    - **Native/iOS**: additive — `API_VERSION` is NOT bumped (guardrail 25): the challenge is reactive, so a client learns 2FA exists from the 401 itself. Native passkeys would need the app to be associated with each self-hosted RP domain, so the iOS follow-up is TOTP + recovery codes first.

7. **No success logs.** `console.error` and `console.warn` only, namespaced with a `[scope]` prefix. Silent success is the convention. Do not add `console.log` for happy-path events.

7a. **NEVER call `encryptToken` at the call site for `Setting.value`, `Account.{access_token,refresh_token,id_token}` or `UserTotp.secret`.** The Prisma extension in [src/lib/prisma.ts](src/lib/prisma.ts) handles encryption on every write to those fields and decryption on every read. Pre-encrypting at the route, sign-in/OIDC, or library layer produces double-encrypted rows of the form `enc:v1:<enc:v1:…>` — on read the extension decrypts once and hands callers the inner ciphertext, which then gets sent as an API key/token to upstream services and fails auth. This bug shipped in `bc81802` (a route-level pre-encryption in `/api/settings` and an `encryptingAdapter` wrapper in `auth.ts`); both were removed afterward. The remaining legitimate `encryptToken` callers are: `PushSubscription` writes ([src/app/api/push/subscribe/route.ts](src/app/api/push/subscribe/route.ts), the extension does not cover that table) and the one-shot migration scripts under [scripts/](scripts/). Do not add a third. `UserTotp.secret` (guardrail 6d) is covered by the extension — and unlike `Setting.value` every write of that column is sensitive, so its `updateMany`/`createMany` are ENCRYPTED rather than refused; never read it through a nested `include: { totp: … }` from a user query (that bypasses the `userTotp` hooks — `tests/mfa-prisma-extension.test.mts` scans for it).

7b. **A warning that restates an UNCHANGED condition on every pass goes through `warnOnChange` ([log-dedup.ts](src/lib/log-dedup.ts)). Rate questions are answered by the cron run history — NEVER by counting log lines.**

    Why:
    - `[jellyfin] 90 TMDB id(s) matched more than one Movie` and `[sync] N conflated ratingKey(s)` describe the LIBRARY, not an event. The orchestrator re-derived and re-emitted them verbatim on every run, so their volume tracked the caller's polling rate rather than the condition. At the intended hourly cadence that is ~24 lines a day; when an SSE trigger loop drove the orchestrator to roughly once a minute it became ~1,400 a day. The repetition did not report the anomaly — it *was* the flood that hid it.
    - The ledger could not answer it either. `recordCronRun` kept only the newest run per target, so `cron:lastRun:sync:full` read identically whether the job ran once or four hundred times — on the very panel `[internal-trigger]` tells operators to go check.

    Rules:
    - Repeat-suppress with `warnOnChange(key, signature, message)`. Derive the signature from **everything the message states** (the dropped ratingKey LIST, not just its length) or a changed message is silently swallowed. Suppression is per-process, so a restart always re-logs the current state.
    - **NEVER emit "(repeated N times)"** — that reintroduces the per-pass line the suppression exists to remove.
    - **NEVER repeat-suppress an EVENT.** This is only for a condition recomputed on a schedule. A webhook delivered twice, a request failing twice, a session finalizing twice are distinct occurrences and each must log.
    - `recordCronRun` keeps a bounded `recent[]` (`CRON_RUN_HISTORY_LIMIT`) **inside** the existing `cron:lastRun:<target>` row. The three top-level fields are unchanged, so `parseCronLastRun` and every existing reader still work and a pre-history row still parses. Admin → Settings → System renders it as runs/h; that is where a cadence anomaly is read.
    - The history read is best-effort and MUST stay swallowed — several suites stub `prisma.setting` with `upsert` alone, and an observability read must never turn a cron route into a 500. `tests/cron-auth.test.mts` pins that, the write cap (against the RAW row — `parseCronRunHistory` truncates on read too, which masks an uncapped write), and the pre-history fallback.

7c. **The Radarr/Sonarr monitor announces a disk on a CHANGE of state only, and each failed or newly stuck download exactly ONCE — state written BEFORE the events.**

    Why:
    - A low disk is a condition recomputed every 15 minutes; re-announcing it every run is the flood 7b forbids. A failed download is an event and must never be held back because a similar one was sent.
    - Sonarr writes one DownloadFailed record per episode of a pack — per-record alerts would send one message per episode.

    Rules:
    - Disk state is per (instance, disk), with hysteresis (low: < threshold % or < 10 GB; ok again: threshold + 2 points and 12 GB). Only disks holding a root folder are judged. A root folder is judged against the `/diskspace` entry it sits on ONLY when their free space agrees (within max(1 GB, 1%) — `rootDisk`, shared with Arr System's Storage tab); otherwise (a mergerfs/shfs/rclone mount `/diskspace` doesn't list, which "/" would otherwise swallow) it is its own reading, keyed by its own path, total unknown, judged by the 10 GB floor. A root folder or disk reporting no free space is never matched to the catch-all "/" (unless the folder is "/") — with nothing to compare, that match can't be believed — and a root with no free space of its own is then skipped. A disk missing from one read is remembered for 24 h (`goneDisks`), so a flapping mount is not re-announced.
    - Failures come from a cursor over the arr's own history (date, then id), read via `/history/since` from 14 h before the cursor (v3 `DateTime.Parse`s the date as local time); a record dated after Summonarr's clock is held back, not consumed, until the clock reaches it (any tolerance is a window of failures lost once a transient jump corrects), and a stored cursor more than `MAX_FUTURE_SKEW_MS` (1 h) ahead restarts at now (not a day back) — a forward clock jump on the arr host must never blind the cursor. They fold by `downloadId` within 1 h of the announcement's first record (`FAILURE_FOLD_WINDOW_MS`), in one run exactly as across runs; at most 25 per instance per run — the rest are deferred by the cursor, never dropped.
    - A DownloadFailed record the arr wrote for a MANUAL mark ("Manually marked as failed": Summonarr's Mark failed, Blocklist, Replace file, or the arr's own UI) is consumed silently: it is an admin's action, not a failed download, and is neither announced nor counted in `failed24h`.
    - Attention is a diff against what was ANNOUNCED in the last 24 h (`attentionSeen`, `WATCH_GRACE_MS`, counted from when each was last seen needing attention — time with no successful queue read (the arr unreachable, Summonarr down; any gap past `attentionReadGapMs(ARR_WATCH_INTERVAL)` — twice the cadence, never under `ATTENTION_READ_GAP_MS` (1 h), so a slow cadence's regular gaps are observed time) does not count toward it (`attentionReadAt`, stamped only by a successful read), and a key kept through such a gap is stored moved forward by it, so a download stuck through an outage is not re-announced on recovery or on the run after), not against the previous run alone: an arr restart, an unreachable download client or a paging shift drops a stuck download from one read, and it must not come back as "newly stuck". Accepted: the same download getting stuck again within 24 h is not re-announced (the badge and queue page still show it). At most `MAX_ATTENTION_PER_RUN` (25) per instance per run; the rest are not remembered, so the next run announces them (`deferredAttention`). A first run per instance seeds silently; a pre-grace stored state seeds the memory, so an upgrade replays nothing.
    - State is written (one transaction) BEFORE the events are emitted; a failed read keeps that part's previous state; an aborted run (guardrail 41) writes and sends nothing.
    - Alert text goes through `scrubArrText`: no paths, URLs reduced to their host, credentials masked. A path is removed to the end of its clause (a quote, a bracket, `;`/`,`/`.` + space, or the end), never cut at its first space, because media folders contain spaces.
    - `tests/arr-watch.test.mts` pins all of it, mutation-verified (44 mutants).

14a. **A TV request is "now available" ONLY when Sonarr reports the series COMPLETE — every aired, monitored, regular-season episode on disk, specials excluded. Library presence alone NEVER flips a request Sonarr still lists as wanted.**

    Why:
    - Sonarr fires one Download webhook per EPISODE, and Plex/Jellyfin index a show from its first imported file. Under the old rule (a continuing series was "available" with any single episode file; only an *ended* one had to be complete) a requester was told "ready to watch" off episode 1 of a 24-episode season pack, by three independent paths: the webhook's first confirmed event, the Sonarr-available cache, and the library marking pass seeing the show in Plex. The claim burned, so nothing ever announced the real completion.
    - The webhook used to flip OPTIMISTICALLY when Sonarr was unreachable. Sonarr 503s under import load — exactly when the per-episode events arrive — so a single transient 503 promoted an incomplete series.
    - Sonarr's series-level `statistics` block SUMS EVERY SEASON, season 0 included (`SeriesStatisticsService.MapSeriesStatistics`; only the resource's `seasonCount` filters `SeasonNumber > 0`). A monitored special with no release would hold a complete series in APPROVED forever, so specials must be excluded in OUR code, from the per-season blocks.

    Rules:
    - **One definition: `sonarrSeriesCompletion` ([sonarr-completion.ts](src/lib/sonarr-completion.ts), pure, zero-import).** Both the sync writer (`getSonarrWantedTmdbIds`) and the webhook gate (`isSeriesDownloadedInSonarr`) call it; `tests/arr.test.mts` pins that neither carries a private threshold. A divergent rule flips a request on one path and reverts it on the other, every tick. It sums `seasons[].statistics` over `seasonNumber > 0` and falls back to the series-level block only when no regular season carries stats. `episodeCount` is Sonarr's own "(monitored AND aired) OR has-file" denominator, so unmonitoring an unobtainable episode in Sonarr is the operator's escape hatch — the series reads complete on the next sync. Never use `totalEpisodeCount`, and never reintroduce a `status !== "ended"` any-file shortcut.
    - **Every library-marking pass filters TV candidates through `sonarrIncompleteKeys` ([arr-availability.ts](src/lib/arr-availability.ts)) BEFORE the CAS** — the orchestrator's `markLibraryRequests`, `/api/sync/plex`, `/api/sync/jellyfin`. A `SonarrWantedItem` row for the request's own `arrInstance` means incomplete; the row stays PENDING/APPROVED with `notifiedAvailable=false` and is re-evaluated next run. Pre-CAS is load-bearing (guardrail 14 — the claim is never burned for a gated row; guardrail 15 — the `stillPending` snapshot is still read once, the gate is a filter over it). A title with NO wanted row keeps the old behaviour: library presence marks it, which is the only signal on a Sonarr-less deployment or for a show that arrived by another route.
    - **The webhook never transitions on an unverifiable verdict.** `isSeriesDownloadedInSonarr` returns a `SeriesDownloadVerdict`: `"incomplete"` skips the flip but STILL schedules the library scan (new episodes must show up while the request waits); `"absent"`/`"ids-disagree"` are the forgery shapes and are refused; `null` defers — the `after()` task re-verifies once `scheduleLibraryScan` has settled (that wait already spans Sonarr's queue draining) and flips then, otherwise the periodic sync reconciles. Don't restore the optimistic flip.
    - The incomplete path is deliberately SILENT (guardrail 7): it is the state of every event but the last of an import. The counts are in the webhook response and in `GET /api/admin/debug/arr-state` (`liveCompletion` per instance) — that is where "it's in Plex, why is it still APPROVED" is answered.
    - Consequence, accepted: a series with one aired episode that can never be found stays APPROVED until the operator unmonitors the episode in Sonarr or marks the request AVAILABLE by hand. That is the requested behaviour, not a bug.
    - `pickSeriesByTmdbId` trusts a LONE lookup row only when it carries no positive `tmdbId`; one naming a different title is a degraded id/text search (`term=tmdb:84503` was answered with tvdbId 84503 live) and must resolve to null, or the ids-disagree guard refuses a genuine event. `findTitle` ([arr-title-data.ts](src/lib/arr-title-data.ts)) does NOT reuse that lone-row trust: it resolves the TARGET of deletes and edits (Replace file, the title manager, add/remove, Why?), so it accepts only a lookup row whose tmdbId equals the requested one. Sonarr v3 rows never carry a tmdbId, so on v3 a degraded `tmdb:` match can't be detected and `findTitle` resolves only through TMDB's TVDB cross-reference.
    - **A tmdb lookup with no verified match falls back to TMDB's own TVDB cross-reference** (`resolveTmdbToTvdb` → `term=tvdb:<id>` → `pickSeriesByTvdbCrossRef`), in `addSeriesToSonarr` and every read path through `lookupSeriesByTmdbId`. Sonarr's metadata service answers `tmdb:`/`imdb:` lookups from an index that lags a new show by days: TMDB 304842 answered `[]` eight days after its premiere while TVDB 478738 already carried that tmdbId, so every approve failed with "no series found". The tvdb row must carry TMDB's TVDB id and must not name a different TMDB title. **The webhook's download verify is the one opt-out (`{ tvdbCrossRef: false }`)**: it decides whether a payload is forged, and TMDB's cross-reference is user-edited third-party data, so one wrong edit would refuse genuine events as ids-disagree. It loses nothing by opting out — an unresolved tmdb id leaves `resolved` null and the verify proceeds on the payload's tvdbId. `tests/arr-tvdb-crossref.test.mts` pins both, mutation-verified.

14b. **A title an admin deleted through Library cleanup must NEVER be demoted and re-pushed. The demote's CAS carries `cleanedUpAt: null`, and nothing takes a TITLE off Radarr/Sonarr except the confirmed cleanup route and the title manager's confirmed Remove — both stamp before deleting.** (File deletes — the title manager's Files tab, an issue's Replace file — leave the title on the instance, so the arr's own search, not a re-push, is what follows them.)

    Why:
    - The orchestrator demotes an AVAILABLE request to APPROVED when its title leaves every *arr cache and library, and the next run re-pushes APPROVED titles the *arr doesn't know (34a's "Accepted" note). That is right for a lost file and exactly wrong for a deliberate delete: the cleanup would re-download everything it removed, one sync later.

    Rules:
    - The stamp is withdrawn ONLY by an admin putting the title back through the title manager's Add (that instance's stamps, after the arr accepted the add) — the deliberate delete was undone by the same person, so a later loss is a lost file again. Nothing else clears it.
    - `POST /api/admin/cleanup/delete` ([route](src/app/api/admin/cleanup/delete/route.ts)) stamps `MediaRequest.cleanedUpAt` on every AVAILABLE request for the title BEFORE the first upstream delete. A title's requests are matched by tmdb id OR — for a show — the tvdb id of every Sonarr target (`cleanupRequestIdentity` in [library-cleanup-data.ts](src/lib/library-cleanup-data.ts), the title manager's `requestIdentity` rule), for both the active-request exclusion and the stamp; the route resolves its targets BEFORE judging, so a tvdb-only link (a Sonarr v3 series reached through TMDB's cross-reference) holds the delete back too. It never writes `status` or `approvedAt` (34a). Keep the check in the demote's WHERE, not a JS filter over the run-start snapshot — a stamp landing mid-run must still win. `tests/sync-orchestrator-route.test.mts` pins both directions (stamped stays AVAILABLE and is never re-added; unstamped is demoted then re-pushed), mutation-verified.
    - **Only a DEFINITE refusal removes a stamp.** The cleanup removes the stamps it wrote from the requests of any instance that definitely refused its delete — that instance still holds the title (all of them when every instance refused). An UNKNOWN outcome (a timeout, a network failure, a 502/504 from a proxy — `arrWriteOutcomeUnknown` in [arr.ts](src/lib/arr.ts)) KEEPS them: the arr may have taken the delete, and an unstamp on a deleted title re-downloads it; the result carries an additive `uncertain: true`. The title manager's Remove stamps in ONE conditional write (`updateManyAndReturn` on `cleanedUpAt: null`) whose returned rows are the only stamps that call owns, counts and may remove, and removes them only when the arr definitely refused AND a re-read shows the title still on the instance — an unknown outcome keeps them even then, and so does an unreadable instance. `tests/audit-fix-release-delete-outcome.test.mts` / `tests/audit-fix-release-remove-outcome.test.mts` pin both.
    - A delete that went through re-asserts the stamp, with its own time and by id, on every AVAILABLE request of the title (except on an instance that refused); the title manager's Remove does the same for its instance. So does a cleanup execute whose outcome is UNKNOWN even when nothing was definitely deleted — "maybe deleted" holds the stamp exactly as "deleted" does, and this call may own no stamp at all (a concurrent execute stamped first); a failed re-assert there rides the `failed` result as an additive `bookkeepingError`. A concurrent execute or Remove whose delete failed therefore can't unstamp a title that is gone (`tests/audit-fix-cleanup-lib.test.mts`).
    - A stamped AVAILABLE row is a REMOVAL, not a greenlight: the "already greenlit" mirror lookups (`request-create.ts`, the Discord `/request` path, `requests/bulk`) carry `cleanedUpAt: null`, so a new request for a deliberately removed title goes to the admin as PENDING (or the requester's own auto-approve) instead of being copied as APPROVED and re-pushed by the sync.
    - Deletion is ADMIN-only, dry-run first, and executes only with the dry run's `targetCount` echoed and still live (the backfill-playtime confirmation idea); a title that stopped being a candidate drops out of the count, so the execute 409s. The confirm UI's execute sends exactly the titles the dry run listed (the plan's own items, `cleanupExecuteBody` in [cleanup-delete-plan.ts](src/lib/cleanup-delete-plan.ts)), never the live selection, and a dry-run (or 409) answer for a selection that has since changed is discarded (`planGen` in cleanup-delete.tsx), because the route compares only the COUNT — `tests/audit-fix-cleanup-ui.test.mts` pins it. Every instance holding the title is a target (guardrail 32), through `arrFetchNoContent` (guardrail 5); a 404 counts as deleted; an instance whose listing failed refuses its titles rather than half-deleting them. Audit is `void logAudit` after the upstream delete (26). `tests/library-cleanup-routes.test.mts` pins all of it.
    - The rule engine ([library-cleanup.ts](src/lib/library-cleanup.ts), pure) only judges watch rules over the window play history OBSERVED (later of addedAt and the first recorded play); with tracking off they never match. Nothing runs on a schedule — the page computes on demand, and `feature.admin.cleanup` defaults OFF.

14c. **NEVER list notification channels at a "now available" call site — every claimed winner goes through `fanOutAvailableWinners` ([request-notifications.ts](src/lib/request-notifications.ts)) — the sync/webhook claimers AND the admin's manual "mark available" in `dispatchRequestStatusChange` — and it is the ONLY `request.available` emit (the hub itself emits only `request.approved`/`request.declined`). Outbound channels (webhook / ntfy / Gotify, `NotificationAgent` rows) are reached ONLY through `emitNotificationEvent(s)` ([notify-agents.ts](src/lib/notify-agents.ts)), which never throws and never blocks the caller.**

    Why:
    - The four-channel "available" fan-out (Discord, push, in-app, email) was copy-pasted into SIX sync sites plus the webhook poll. Adding a fifth channel meant editing seven places, and the copies had already drifted (two swallowed errors silently, the rest warned).
    - The outbound channels are instance-wide and admin-configured, so the same event must reach them however it was produced — single approve, batch approve, Discord button, sync, webhook.

    Rules:
    - A new channel for "now available" is added INSIDE `fanOutAvailableWinners`, never at a call site. Callers pass only the claimed, deliverable winners, so the once-only claim (guardrail 14) and the disabled-requester drop (guardrail 33) cover every channel at once. `tests/notify-agents.test.mts` pins that the three sync route files contain no per-channel call.
    - The outbound channels follow the requester-facing hubs for request events (`dispatchRequestStatusChange`, the batch route): a self-action or a disabled requester sends nothing to them either (`filterActiveOwners` in `requests/batch/route.ts` — one active-owner read, every channel fed the same filtered set). `AvailableWinner.arrInstance` and `PendingAvailableRequest.arrInstance` are REQUIRED on purpose: a select that omits the column fails to compile instead of reporting the default instance (guardrail 32) in the outbound event. Admin events (new request/issue, issue reply/resolve, vote threshold, *arr manual import / replacement grab) emit beside the existing admin fan-out.
    - Channel URLs are admin-entered, so delivery goes through `safeFetchAdminConfigured` (guardrail 5a — LAN allowed, metadata blocked). The one credential per channel lives in `NotificationAgent.secret`, encrypted by the Prisma extension (guardrail 7a — never `encryptToken`); the admin wire shape carries only `hasSecret`. Gotify's token goes in `X-Gotify-Key`, never the query string. A secret with any control character (NUL, CR/LF, …) is refused on input; a header value the transport still rejects is a `fail` with a constant message, never the thrown message (which embeds the secret). The create/update `SETTINGS_CHANGE` audit records the DESTINATION (url; webhook `headerName` + `hasTemplate`; ntfy `topic`) and only whether the secret changed — never the secret.
    - Delivery: 2xx ok; 408/429/5xx/network retried at 30 s / 2 min / 10 min through `scheduleDelayed`; any other 4xx and every SSRF refusal fail at once. Retries are in memory — a restart drops pending ones (accepted; an outbox table is the upgrade if delivery must survive restarts). **A retry re-resolves the agent by id at fire time** (`retryDelivery`): a channel disabled, deleted, unsubscribed or re-pointed while a retry is pending is delivered with its CURRENT config or not at all — never from the attempt-0 snapshot, and never recording an outcome onto a withdrawn channel. **A retry the shared `delayed-jobs` pool refuses — at schedule time (`scheduleDelayed` returned `false`) or at fire time (its `onDrop` hook) — is terminal and is recorded on the row as `failed: retry queue full: <reason>`**; nothing is silently lost. The last outcome is recorded on the row for the admin list; the Test button awaits that write before responding, the dispatch path does not.
    - Messages are written in the instance default language and media titles are localized at send time (guardrail 40a). The webhook payload is versioned (`WEBHOOK_PAYLOAD_VERSION`); a custom template is `{{field}}` substitution from `TEMPLATE_FIELDS` only, each value JSON-string escaped, and must render to valid JSON for BOTH samples — the full one and a sparse one with every nullable field null (`media` absent, no text/votes) — or it is refused on save; an unquoted `{{media.tmdbId}}` is therefore refused. ntfy/Gotify URLs are a BASE the path is appended to, so a query or fragment on them is refused; generic webhooks keep theirs.
    - Text keys are a LITERAL map (`AGENT_TEXT_KEYS`), never built from the event name — the i18n dead-string check can't see a built key.

14d. **"Never watched" has ONE definition — the verdict in [never-watched.ts](src/lib/never-watched.ts), fed by the evidence loader in [never-watched-data.ts](src/lib/never-watched-data.ts). The report, the cleanup `neverWatched`/`unwatched` rules, the delete route's re-judgement and the detail-page chip all go through it; a private `playCount === 0` anywhere is a second definition, and the two drift.**

    Why:
    - The list feeds a DELETE, so the failure that matters is a false "never watched". The cleanup engine's first version judged every title against ONE global `min(PlayHistory.startedAt)` and ignored the per-source tracking switches, so a server tracked later (or not at all) read as observed for years; it dropped every play stored with `tmdbId = null` (a show watched before the next library sync, every episode of a Plex show's second-section copy); and the delete route's narrowed re-check filtered plays by `tmdbId IN (…)`, so it re-judged more leniently than the page that offered the title.

    Rules:
    - **Evidence is a union and is NEVER filtered** by user (deactivated, departed, admin), the `watched`/`completed` flags, source or server. Hard evidence: a play attributed by tmdb id, by the movie's own item key (`sourceItemId` → `plexRatingKey(s)`/`jellyfinItemId(s)`, which also catches a 37b conflation loser and a rematch done in Plex/Jellyfin), by the show's key (`PlayHistory.sourceShowId`), a session playing now, or the media server's own record. Soft evidence — an unattributed play whose title merely matches a library title of the same type on ANY server — is "possibly watched" and never eligible. Not only a holder: a server that never identified the item, or whose library isn't synced, still serves the same file. The match depends on the (play, title) pair alone, never on which other titles the play's server holds — that is what keeps the narrowed read at parity, and "own server first, else any" breaks it. An item key can sit on more than one title (a 37b conflation whose loser key rides another row's `plexRatingKeys`); a key credits EVERY title that answers to it, never only the last row read. `tests/never-watched-data.test.mts` pins the no-filter rule structurally.
    - **A title is judged only when EVERY server holding it is recorded and has history** — an intersection, never a union. The window opens at the later of the title's arrival (the EARLIEST of every holder's `addedAt` and a fulfilled request's `availableAt` — a media server's own "added" resets on a re-add or an upgrade, so it errs late and never makes a claim longer. NEVER Radarr/Sonarr `added`: it is when the title entered the arr, often months before a file existed, so it would lengthen the claim; it is read only as a bound. A fulfilment older than the same instance's current entry (a re-add since — after a deliberate removal that is a new arrival, not a continuation, 14b) belongs to the deleted copy and is dropped, and a request stamped `cleanedUpAt` never supplies an arrival) and the LAST holder's coverage start (`max(first surviving recorded play, the tracking switch's last off→on stamp)` — `trackingStampsFor` in the `/api/settings` write). Anything else is `unobservable` with a reason, never silently dropped. Retention purges move the first recorded play forward with them, so "since <date>" stays true without a watermark.
    - **The narrowed read (`only`) must reach the full read's verdict.** It filters by tmdb ids OR item keys OR show keys OR titles (every holder's own title — servers may name a title differently; `contains`, not `equals` — the exact match is made in memory, the same way for both reads). Past `NARROW_TITLE_FILTER_MAX` (50) titles the unattributed read is unfiltered — the full read's own query — since the exact match is made in memory either way. It must also know which keys belong to OTHER library titles: an unattributed play keyed to an unchosen title is placed there, never soft evidence for a same-named chosen one. The parity test re-judges every fixture title one at a time; it caught the `equals` version.
    - The narrowed read's key reads must stay index-served: a show's plays by `sourceShowId IN (…)` (PlayHistory `@@index([sourceShowId])`), a movie's by `sourceItemId IN (…)` scoped to the movie keys' own sources, so the `[source, sourceItemId, …]` index serves it (Postgres has no skip scan). That source scope is the ONE source predicate allowed, and only on the narrowed read — lossless, because a key group counts only when its (source, instance, key) belongs to a holder; the full read never carries it (`tests/audit-fix-activity-ingest-nw-index.test.mts`). The evidence read runs its five whole-table PlayHistory aggregates at most two at a time (`EVIDENCE_AGGREGATE_CONCURRENCY`, never in a `$transaction`).
    - **Upstream evidence is READ-ONLY** — `UpstreamWatchEvidence`, keyed by the upstream id (never a tmdb id) and joined at read time. It is never written into PlayHistory (guardrail 19), a failed refresh keeps the previous snapshot, and a snapshot whose health is anything but `ok` (missing, failed, stale, unreliable, incomplete) is never read as "zero plays": it is the `upstreamUnchecked` exclusion (`cleanupRequireUpstreamCheck`, default on), which holds watch-rule candidates back — the votes rule is the users' own call and needs no check. The refresh's agreement check (`upstreamHealth`) turns a parser that understands nothing into `failed`, not into an empty history — and so is a snapshot whose episode records mostly (> 50%, once there are ≥ 20) carry no show id (`upstreamEpisodesUnplaced`): the show key is TV evidence's ONLY join, and neither `matched` (movies keep it above 0 on a mixed server) nor the agreement check (it compares the items' own keys) can see it. A named server removed while its refresh is in flight writes nothing afterwards: the evidence replace and the status write each lock the registry row (`FOR UPDATE`) and re-check the slug (`stillRegisteredInTx`, [upstream-watch-data.ts](src/lib/upstream-watch-data.ts)), and the media-instances removal writes that row FIRST in its transaction — otherwise a server registered later under the same slug inherits the removed one's evidence and `ok` status. Jellyfin's per-user played/resumable read is `GET /Items?userId=` (`getJellyfinUserPlayedItems`): the same `ItemsController.GetItems` handler the `[Obsolete]` `/Users/{userId}/Items` forwards to on every release from 10.6 to master (source-verified 2026-10-13) — don't switch it back.
    - An EMPTY answer from a server Summonarr recorded completed plays on is `unreliable` however few the samples (the 20-sample floor applies only to the agreement ratio), and the refresh refuses to store it, keeping the previous snapshot (`failed`, "the server returned no watch records"). A TRUNCATED read (a Plex history past `PLEX_WATCH_HISTORY_MAX_ITEMS` watch records, or past `PLEX_WATCH_HISTORY_MAX_RAW` raw records — the cap counts watch records only, so music plays don't consume it) is stored `truncated` and reads health `incomplete`, never `ok`, because the records it dropped are the OLDEST — the pre-install views the snapshot exists for; its rows are still written (each is real evidence).
    - Plex's history lists only views it counted as watched (its played threshold), so an abandoned partial Plex view from before Summonarr is not evidence; Jellyfin's IsResumable is. Accepted, not a bug.
    - **Seasons are reported only for shows that HAVE been watched** (a never-watched show is reported whole, so nothing is counted twice), from `TVEpisodeCache` (the media server's own numbering, specials excluded) — when the Plex and Jellyfin copies of a show disagree on a season they BOTH hold (different episode counts — anime in TVDB vs TMDB order), a play under one numbering can't be placed in the other's, so the show's other seasons' plays are SOFT evidence for each season (possibly watched, never "never watched"); a partial copy is not a disagreement. A season's window opens at its first episode's `addedAt` and its age counts from its newest; one undated episode makes it `unobservable`. A season's size is attached only when Sonarr's `episodeFileCount` agrees with the library's episode count (`seasonSizeIfAgreed`) — otherwise it is another season's size. Seasons are report-only; nothing deletes a season.
    - **"Eligible" on the report is exactly the delete dry run's selection** — the report runs `evaluateCleanupTitle` over the same loader; `tests/library-cleanup-routes.test.mts` pins the equality against the real dry run, mutation-verified. Its targets come from `resolveArrTargets` (tvdb-only Sonarr series included), resolved inside `loadCleanupTitles` (`resolveTargets`) before the requests are read, so a request linked only by tvdb id holds the title back on the report as it does in the dry run. A service with ANY failed instance listing makes none of its titles eligible (`failedArrInstances`, the helper the route uses). The cleanup page's rows carry the same targets (`computeCleanupReport({ resolveTargets: true })`): a matched show whose targets add a tvdb id is re-judged narrowed with it.
    - The report is cached ~2 minutes (`getNeverWatchedReport`) and dropped early by a new recorded play (the activity-cache generation) and by `invalidateNeverWatchedReport()`, called by the Summonarr actions that change an input: protect, cleanup settings, cleanup delete, the upstream refresh route and its cron, the title manager's Add and Remove, a media-server instance's removal, and a `/api/settings` write of a tracking switch, `playHistoryRetentionDays` or the cleanup/never-watched feature flag. Every other input change (library syncs, a fix-match, votes, requests, watchlists, edits made inside Radarr/Sonarr) is bounded by the TTL; the cleanup dry run never reads the cached report, so that staleness never reaches a delete. A computation that spans an invalidation is never stored (the 19b shape), and the shared Radarr/Sonarr index (`getCachedArrLibraryIndex`) follows the same rule: `invalidateArrLibraryIndexCache` bumps a generation that is part of the coalesce key, so a listing begun before an invalidation is never stored. The `/admin/stats` storage section computes this report and the Library cleanup report from ONE whole-library facts load (`shareLibraryWatchFacts` in never-watched-data.ts — one index, one `now`); each still computes exactly what it computes alone, and a shared load that doesn't fit the read it replaces throws. The never-watched report runs first, and one built from a shared load is stored only when the load had not started before it read its generation and the index it carries is still the shared index cache's current object; otherwise it serves that caller alone (`tests/audit-fix4-stats-load.test.mts`).

15. **The `stillPending` snapshot is taken once per sync run.** If you add a third source to the orchestrator, remember that changes made by the Plex pass won't be visible to the Jellyfin pass within the same run — that's intentional. Within a source the marking likewise runs once, over the already-unioned map, so no instance can shadow another's rows.

16. **NEVER call `Date.now()` or `new Date()` inside the render path of a `"use client"` component.** Module-level constants and direct calls in JSX are both render-time evaluations.

    Why:
    - Server-side: the value is captured during SSR (frozen at module load if at module level, or at the moment of `renderToString` if inside the component).
    - Client-side: the value is captured again at hydration, milliseconds-to-hours later.
    - The two values disagree → React #418 hydration error (`args[]=text` for relative-time strings, `args[]=HTML` for `<option>` lists derived from `getFullYear()`).
    - Bundlers can also bake module-level values at build time, widening the drift to days.
    - Six distinct hydration bugs in this codebase have come from this single antipattern: `top-filter-bar.tsx`, `activity-history-table.tsx`, `activity-recent-plays.tsx`, `trash-guides/spec-section.tsx`, `activity-calendar.tsx` (the year-dropdown logic that bit `filter-bar.tsx` now lives in `top-filter-bar.tsx`; the trash-guides client was split under `src/components/admin/trash-guides/`).

    Fix shape — pick one:

    a. **Pass the reference time as a prop from a server component** (preferred when the consumer is itself a server component or sits one level below):
    ```ts
    // server page.tsx
    <ActivityCalendar data={data} today={new Date().toISOString()} />
    <FilterBar maxYear={new Date().getUTCFullYear() + 1} />
    ```

    b. **Gate on `useHasMounted` from `@/hooks/use-has-mounted`** (when the value is purely cosmetic — relative-time labels in tables, "X ago" timestamps):
    ```tsx
    const mounted = useHasMounted();
    return <td>{mounted ? formatRelativeTime(row.startedAt) : ""}</td>;
    ```

    Examples already in the codebase: `cron-job-table.tsx`, `audit-log-table.tsx`, `activity-now-playing.tsx`. Match the pattern when adding a new component.

    ❌ Wrong:
    ```ts
    const currentYear = new Date().getFullYear(); // module-level: bake-or-drift
    function Row({ ts }) { return <span>{formatAgo(Date.now() - ts)}</span>; }
    ```

    ✅ Right:
    ```ts
    function Row({ ts, mounted }: { ts: number; mounted: boolean }) {
      return <span>{mounted ? formatAgo(Date.now() - ts) : ""}</span>;
    }
    ```

16a. **The `nonce` mismatch on the root layout's theme script is NOT a guardrail-16 bug — do not go hunting for render-time nondeterminism, and do not remove its `suppressHydrationWarning`.**

    Why:
    - Under a **header-delivered** CSP (which [src/proxy.ts](src/proxy.ts) sets on every request) the browser moves the nonce into an internal slot and blanks the content attribute — HTML spec, "nonce attributes", so a CSS attribute selector can't exfiltrate it. Verified live: `getAttribute("nonce")` → `""` while `.nonce` → the real value, and the served HTML carries the real value.
    - React's **DEV-only** hydration attribute check reads props back with `getAttribute` (`diffHydratedProperties` → `hydrateAttribute` in react-dom), so it compares that `""` against the real nonce from the RSC payload and logs *"A tree hydrated but some attributes of the server rendered HTML didn't match the client properties"* on every page.
    - **Read the diff direction correctly**: React's `describePropertiesDiff` prints `+` for the CLIENT props and `-` for the value it read back from the DOM (which it labels "server"). `+ nonce="<real>"` / `- nonce=""` therefore means the server HTML was **right** and the DOM readback was blanked — not "the client lost the nonce". Misreading this sends you looking for a nonexistent threading bug in `headers()`.
    - It is a `console.error` only: React never patches up or re-renders attribute mismatches, so there is **no #418, no recoverable error, no client re-render**. `diffHydratedProperties`/`hydrateAttribute`/`serverDifferences` are absent from the production react-dom build entirely, so it never fired outside `next dev`.

    Rules:
    - The nonce cannot be dropped from that tag — `strict-dynamic` blocks un-nonced inline scripts, and the anti-FOUC script would be CSP-killed. `suppressHydrationWarning` on the `<script>` is the fix; the one on `<html>` does **not** cascade to it.
    - The CI crawl ([scripts/e2e-crawl.mts](scripts/e2e-crawl.mts)) never saw this: it builds and runs `npm run start`, i.e. **production**, where the diff path does not exist. There is no ignore-filter to narrow. Its `/#418/` match is on `pageerror` — real hydration *errors*, a different class.
    - Corollary gap, accepted: because CI runs production, dev-only attribute-mismatch **warnings** are invisible to it. A genuine one (a `Date.now()`-derived attribute) would only surface in a local `next dev` console — which is exactly why that console must stay free of known-benign noise.

17. **Do not "fix" the intentional fire-and-forget `tmdbId` backfill in [src/app/(app)/admin/activity/page.tsx](src/app/(app)/admin/activity/page.tsx).**

    Why:
    - The `void Promise.all(... activeSession.update ...)` block is a cache warm, not part of the response. Awaiting it would add DB round-trips to every Activity page render for no user benefit.
    - It is safe **only because** Summonarr runs as a single long-lived Node server (see Deployment) — the unawaited promise survives past render. On serverless/edge it would be dropped; this app is never deployed that way.
    - Errors are swallowed by design: the next sync re-resolves the `tmdbId`, so a failed backfill is self-healing.

    A reviewer pattern-matching "unawaited promise in a server component" will want to await it or move it into the sync path. Both are wrong here. Leave it; the inline comment explains the same.

    - The Docker image is built from Next.js standalone output, which traces only runtime JS and strips `node_modules` LICENSE/NOTICE files. [Dockerfile](Dockerfile) explicitly `COPY`s [LICENSE](LICENSE) + `THIRD_PARTY_LICENSES.txt` into the runner so the shipped artifact carries them.
    - `THIRD_PARTY_LICENSES.txt` is generated from `package-lock.json` (not `npm ls` — its deduped tree hid the libvips subtree under `sharp`) by [scripts/generate-licenses.mts](scripts/generate-licenses.mts). It bundles canonical Apache-2.0 + LGPL-3.0 + GPL-3.0 text from [licenses/](licenses/) for deps that ship none.
    - **The output must be byte-identical on every OS.** Platform-gated optional binaries (lockfile entries with `os`/`cpu`/`libc`, e.g. `@img/sharp-*`) are installed by `npm ci` only for the host platform, so reading their on-disk LICENSE makes a macOS-generated file fail the Linux-CI `--check` (and vice versa — this is exactly how the check shipped broken in `dc965a1`). The generator therefore **never reads disk for gated packages** — it emits canonical text keyed off the lockfile `license` (SPDX `AND`/`OR` compounds decomposed via `canonicalFor`). Do not "optimize" this back to `readLicenseText` for gated packages, and do not key canonical lookup off the raw `CANONICAL[license]` map (it misses compounds).

    ```bash
    npm run licenses:generate          # after any prod dep add/remove/bump
    node scripts/generate-licenses.mts --check   # what CI enforces (blocking)
    ```

    CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs the `--check` and fails the PR if the committed file is stale. Do not delete `node_modules` LICENSE files in any Dockerfile slimming step, and do not lower this to a non-blocking CI step — a stale notices file is a license violation in the shipped image, not a lint nit.

    **When checking `--check` by hand, do NOT pipe it.** `node scripts/generate-licenses.mts --check | tail -5` reports `tail`'s exit code, not the script's — a stale file reads as a pass. Run it bare, or `… >/dev/null && echo PASS || echo FAIL`.

18a. **High/critical vulnerabilities BLOCK the release, and the only way past is a dated, owned exception.**

    Why:
    - Every scanner in this repo was observability-only: Trivy ran `exit-code: '0'` in all three places, `audit:deps` was `continue-on-error: true`, `npm audit` wasn't in CI at all, and `dependency-review` only inspects a PR's dependency *diff* — so it is blind to a vulnerable dependency already in the lockfile. Nothing could fail a release. A HIGH in a production dependency (`fast-uri`, GHSA-7p8r-x3mc-p8w7) sat in the tree as a direct result.
    - `ci.yml` also runs on `pull_request` only, while `docker-publish.yml` runs on tag pushes. A tag placed on any commit published `:latest` with no security check on that tree.

    Rules:
    - **The gate is the `security-gate` job in [docker-publish.yml](.github/workflows/docker-publish.yml)**, and `build-and-push` `needs:` it. It runs on every trigger this workflow has, which is what closes the tag hole. Do not remove the `needs:` edge — that silently un-gates publishing while leaving a green-looking job in the graph.
    - **PR-time advisory checks stay non-blocking on purpose.** An advisory filed overnight against a transitive package must not fail an unrelated PR. Blocking belongs at the release, where the risk becomes someone else's. Don't "fix" the `continue-on-error: true` on `audit:deps`.
    - **Exceptions live in [.github/security-exceptions.json](.github/security-exceptions.json)** and require `id` (GHSA), `package`, `owner`, `expires` (ISO date), `reason`. An **expired entry is a hard failure**, not a silent pass — expiry that degrades to "allow" makes every entry permanent by neglect. A package-name match alone never suppresses: the advisory **id** must match too, or accepting one advisory would blanket-accept the next one filed against that package.
    - `npm run security:exceptions` validates the file alone — no network, no advisory feed — so it is blocking in CI and can only fail on this repo's own file.

    ```bash
    npm run security:gate         # what blocks the release (high+, allowlist-aware)
    npm run security:exceptions   # validate the exception file (blocking in CI)
    ```

    - Trivy's scheduled runs are blocking; its push/PR runs are not. A weekly job that can never go red is not an alert.
    - **The image is scanned BEFORE it is published.** `security-gate` builds the runner image single-arch (`platforms: linux/amd64`, `load: true`) and Trivy-scans the loaded image with `exit-code: 1`. Single-arch is not a shortcut — `load: true` exports to the local docker daemon so Trivy can read it, and **a multi-arch manifest cannot be loaded**, which is why this was previously only possible post-publish. `provenance: false` is REQUIRED alongside `load: true` (BuildKit cannot export attestations to the docker exporter and the build fails). The build shares the GHA cache with the publish job and with ci.yml's `docker-build`, so it is normally a cache hit and it primes the amd64 half of the multi-arch release build.
    - The post-publish scan stays `exit-code: 1` for the two things the pre-push gate structurally cannot cover: the **exact published digest** and the **arm64** half of the manifest (not loadable). Divergence between the two is the signal. **The arm64 half is covered ONLY by the explicit `TRIVY_PLATFORM: linux/arm64` scan step, never implicitly by scanning the index digest** — Trivy resolves an index to **`linux/amd64` by default — NOT the scanning host's platform** — unless `--platform`/`TRIVY_PLATFORM` is set, so a lone digest scan re-reads the amd64 layers the gate already checked and the arm64 image goes unscanned. **A single-platform build is an index too** whenever `provenance`/`sbom` are on (the attestation manifests ride beside the image manifest), so the pin is required there as well — an unpinned per-platform scan on an arm64 runner fails outright with `no child with platform linux/amd64 in index`, while the amd64 leg passes because the default happens to match. The host-platform belief is what made the pin look droppable on native runners; it is wrong in both directions. Both post-publish scans pin their platform via `TRIVY_PLATFORM` (trivy-action forwards `TRIVY_*` env vars) and upload under distinct SARIF categories (`trivy-publish` / `trivy-publish-arm64`). Don't collapse them back into one step.
    - **Dry-run the gate before you need it.** `workflow_dispatch` takes a `gate_only` boolean that runs `security-gate` and skips publishing entirely, so a surprise high/critical surfaces when someone chooses to look rather than when it blocks a release mid-flight:

    ```bash
    gh workflow run docker-publish.yml -f gate_only=true
    ```

    Why:

With it gone, all Jellyfin rows share the live namespace, so the `@@unique([source, sourceSessionId])` constraint + `createMany({skipDuplicates})` in `recordCompletedSession` is the whole dedup story — no cross-namespace `liveCovers` guard is needed anymore.

    Rules:
    - **NEVER** make the live poller skip Jellyfin finalize — it's the only writer now; skipping it loses the watch entirely.

19a. **NEVER reconcile a `bitrate` column by MAGNITUDE. Normalize on `source` via [bitrate.ts](src/lib/bitrate.ts).**

    Why:
    - `PlayHistory.bitrate` / `ActiveSession.bitrate` store what the upstream sent, verbatim — there is no write-time normalization. The unit is a property of the row's `source`: **Plex is kbps** (`Media.bitrate`; a 20 Mbps file reads `20000`), **Jellyfin is bps** (`TranscodingInfo.Bitrate` / `MediaStream.BitRate`; the same file reads `20000000`).
    - The two ranges genuinely OVERLAP, so a `bitrate > N` threshold is wrong at one end no matter which N you pick — and **both** wrong answers have already shipped:
      - `> 100_000` erased Plex UHD: a 128 Mbps remux (`128000` kbps) is above the cutoff, so it was divided by 1000 and read as 0.128 Mbps — the heaviest sessions vanished from the panel meant to surface them.
      - `> 1_000_000` inflated Jellyfin 1000×: anything under 1 Mbps (music, and Jellyfin's stock sub-1-Mbps mobile transcode rungs) stayed unscaled and was read as kbps. A 2-hour 720 kbps phone stream reported **648 GB** against a true 0.65 GB.
    - "It's rare, and it contributes little bandwidth" is NOT a valid reason to accept a gap — that reasoning shipped the second bug. The error *multiplies* the row's contribution by 1000, so the **lightest** sessions become the heaviest line items. One phone stream can outweigh a real month.

    Rules:
    - One definition: `BITRATE_KBPS_SQL` (raw-SQL sites) and `bitrateToKbps(raw, source)` (TS/client). Never a private copy — the copies drift. The fix that raised the SQL threshold updated all nine SQL sites and missed **four** UI helpers, which sat on the old cutoff for releases while the SQL and the UI on the same page disagreed about the same session.
    - `source` is a **required** parameter on every formatter, never optional — an optional one silently defaults Jellyfin rows to the Plex reading and renders them 1000× high.
    - An unrecognized `source` is read as kbps. Guessing wrong that way under-reports; guessing wrong the other way multiplies by 1000.
    - `tests/bitrate.test.mts` pins both failure directions plus a repo-wide structural scan for the magnitude antipattern (it caught two undiscovered copies the moment it was written). Adding a media server means editing `BPS_SOURCES`, not a call site.

    **Bandwidth stats use `DELIVERED_KBPS_SQL`, not the raw column** — they answer "how many bytes left the server", and three of the four (server × play-method) cases already measure that: Plex DirectPlay and Jellyfin DirectPlay push the source as-is, and a Jellyfin transcode reports its true output via `TranscodingInfo.Bitrate`. The fourth, a **Plex transcode**, cannot be read at all — `TranscodeSession` carries width/height/codec/container/size/speed and **no bitrate field**. So `Session.bandwidth` (the Streaming Brain's *reserved* estimate, explicitly "not the used bandwidth" per Tautulli) is used for that case alone, wrapped in `LEAST(bandwidth, bitrate)`. The clamp is the load-bearing part: delivered can never exceed the source when transcoding, so a garbage reading (10500 Mbps has been seen in the wild) degrades to *exactly* the un-clamped number — the expression can never be worse than measuring at source, only closer. Never drop the clamp, never extend the estimate to DirectPlay (there source *is* delivered, exactly), and keep both `> 0` guards — Postgres `LEAST` ignores NULLs, so `LEAST(bandwidth, NULL)` returns `bandwidth` and would count a row the raw column calls unknown.

    **Jellyfin DirectPlay bitrate is the SOURCE TOTAL, via `sourceBitrateBps`** ([jellyfin.ts](src/lib/jellyfin.ts)) — `MediaSources[].Bitrate` (the container total, selected by `PlayState.MediaSourceId`), falling back to video + audio stream sum. The old fallback was `videoStream.BitRate`, the video track alone, which dropped the audio from every direct-played session — 128 kbps for stereo AAC, up to ~4.5 Mbps for TrueHD/DTS-HD MA. Do not "simplify" back to a single stream; the sum is already a floor for multi-audio-track files and can only under-report.

20. **The Plex stall anchor (`progressUpdatedAt`) must track playhead MOVEMENT, not strict forward advance — in BOTH writers (SSE and the 5s poller).**

    Why:
    - The poller's stall detector ([sync/play-history/route.ts](src/app/api/sync/play-history/route.ts)) finalizes a *still-playing* Plex session when `now - progressUpdatedAt >= PLEX_STALL_THRESHOLD_MS` (60s). It's the "playhead last moved" anchor.
    - Two paths write `progressMs`: the 5s poller (a lagging `/status/sessions` snapshot) and the SSE `playing` handler `applyLiveStateUpdate` ([plex-events.ts](src/lib/plex-events.ts), real-time). SSE pushes `progressMs` *ahead* of the poller's snapshot.
    - A **strict greater-than** liveness check (`s.viewOffset > existing.progressMs`) reads false on a healthy stream whenever SSE wrote `progressMs` last — the poller's older snapshot is `<=` the SSE value. That false reading both (a) suppresses the `progressUpdatedAt` refresh and (b) satisfies the `!moved` term in the stall condition, so the anchor ages past 60s and the poller **stall-finalizes a live stream** — then the 1h `recentlyFinalizedPlexSessions` ledger blocks the now-playing card from returning. This shipped as a regression with the SSE feature; patching only the SSE writer (commit `af1442b`) was insufficient because it held only while SSE emitted frequent advancing events.
    - A **genuine ghost** (client quit, Plex keeps reporting it) has a *frozen* `viewOffset`, so an inequality check (`!==`) is false there and the stall still fires at 60s. Ghosts emit no SSE events, so refreshing the anchor on movement in the SSE writer can never keep one alive.

    Rule: refresh `progressUpdatedAt` whenever the playhead **moved** (`s.viewOffset !== existing.progressMs` / `BigInt(viewOffset) !== prior.progressMs`), forward *or* backward — not only on a strict forward advance. The poller does this via `playheadMoved`; SSE does this on `transitionedToPlaying || playheadMoved`. Don't regress either to `>` or to transition-only.

21. **`ActiveSession.lastSeenAt` must be re-anchored to "now" once at boot, before any absence-finalize runs.**

    Why:
    - `lastSeenAt` is the "we last saw this session live" anchor for all three finalize paths: the SSE bootstrap reconcile ([plex-events.ts](src/lib/plex-events.ts) `bootstrapReconcile`), the 5s poller's stale sweep ([sync/play-history/route.ts](src/app/api/sync/play-history/route.ts)), and `cleanupStaleSessions`.
    - A restart (Docker upgrade, host reboot) takes the poller and SSE down for the whole outage, so every row's `lastSeenAt` is stale by the downtime and the `>= SESSION_ABSENCE_GRACE_MS` (60s) grace becomes trivially true the instant the process comes back.
    - On the first boot snapshot a session can be briefly absent from `/status/sessions` — Plex still spinning up, an incomplete session list, or a Plex-side `sessionKey` reset. With the grace defeated, that single transient absence **finalizes AND ledger-locks a session that's still playing**, and the now-playing card never returns (matches the reported "restart marked my stream stopped and never picked it back up").

    Rule: call `reanchorActiveSessionsOnBoot()` ([play-history.ts](src/lib/play-history.ts)) — an in-memory once-guarded `updateMany` that sets `lastSeenAt = now` for every row — at the top of BOTH `bootstrapReconcile` and the poller's `syncPlayHistory`, before either reads rows for its stale sweep. Whichever runs first wins; it covers Plex and Jellyfin in one write. A genuinely-ended session is still finalized ~60s after boot once confirmed absent across real post-boot observations. Don't move the finalize ahead of the re-anchor, and don't measure the grace off a pre-restart timestamp.

23. **NEVER swallow a write error with `try/catch` *inside* a single-level interactive `$transaction`.**

    Why:
    - Prisma 7 + `@prisma/adapter-pg` emits SQL `SAVEPOINT`s only for *nested* transactions. A top-level `prisma.$transaction(async (tx) => …)` runs its statements straight on the connection with no per-statement savepoint.
    - In PostgreSQL the first statement that errors puts the whole transaction into the *aborted* state. A `try { await tx.x.create(...) } catch {}` hides the JS error but issues no `ROLLBACK TO SAVEPOINT` (there is none), so when the callback returns the adapter's `COMMIT` is silently converted to a **ROLLBACK** — every earlier write in the tx is discarded while the handler still returns success.
    - This shipped in `/api/votes`: a one-shot "notify admins at threshold" gate did a caught `tx.setting.create` of a unique key *after* the vote insert. Once the key existed, every later vote hit the unique violation, aborted the tx, and the vote was rolled back behind a `201`. Fixed in this commit by moving the gate out of the tx.

    Rules — a unique-violation you intend to tolerate must either:
    - be the transaction's **last** op and **propagate** so the outer `catch` maps `P2002` (the `/api/requests` pattern — nothing runs after the throw in-tx), OR
    - live **outside** the transaction as an idempotent `createMany({ data: [...], skipDuplicates: true })` one-shot gate (`count === 1` ⇒ this caller won), OR
    - use `upsert`. Never a bare `create` whose error is caught-and-ignored mid-transaction.

23a. **NEVER interpolate an SQL fragment into a TAGGED `$queryRaw`/`$executeRaw`. Build the query with `Prisma.sql` and pass it as ONE value: `prisma.$queryRaw(Prisma.sql\`…${fragment}…\`)`.**

    Why:

Postgres answered `syntax error at or near "$1"` and `/admin/stats` 500'd on every query that carried an optional `AND createdAt >= …` clause.

The `Prisma.sql(...)` builder composes fragments itself, so the form above is immune; every other raw query in `src/` already used it.

24. **The native-client version gate (426) fails SOFT and is NEVER an authz input.**

    Why:
    - The 426 force-upgrade gate in [proxy.ts](src/proxy.ts) exists to stop an *honest, stale* native build from running known-bad client code. It is NOT a security control — a hostile client spoofs any `build=`. Auth, DB revocation, `passwordChangedAt`/`sessionsRevokedAt` cutoffs, and TLS are the real boundaries; none look at the version.

    Rules:
    - **Version never gates authorization, the CSRF Origin check, or the UA-fingerprint check.** Those skips key off bearer / `X-Summonarr-Client` *presence* (CORS-sound — guardrail 6b), never off the parsed version. Do not add an "if old client, relax X" path.

A missing/unparseable build (e.g. a legacy bare `ios` header) ⇒ false ⇒ never blocked. Keep `parseNativeClient` tolerant.
    - **Only MUTATING `/api/*` requests get 426.** Reads are never blocked. Do not widen the gate to GETs.

To force-upgrade builds below `N`, raise `MIN_CLIENT.ios = N` and redeploy the server — no app release is needed to fire the gate (the gate UI already ships in the client). 25. **API contract version is a protocol constant; `/api/config/compat` stays public + coarse; the upgrade URL is client-hardcoded.**

    Why:
    - `API_VERSION` ([src/lib/api-version.ts](src/lib/api-version.ts)) is a *capability-negotiation* integer, NOT the marketing version. It is the deliberate exception to the Releasing section's "no version constant in `src/`" rule (which forbids a third copy of the *marketing* version). Bump it only on a breaking wire-contract change; never auto-derive it from `package.json`.
    - The compat descriptor is a pre-auth surface any internet scanner can hit; a precise version string there is a CVE-targeting aid (defense-in-depth — the login page already leaks hints, so it's not treated as a secret).
    - A server-supplied "update here" link would let a malicious/compromised server redirect the upgrade flow to a phishing or sideload URL.

    Rules:
    - **`GET /api/config/compat` returns integers only** (`apiVersion` / `minApiVersion` / `minClient`) — no marketing version, no secrets, no server URL, no DB read. It is intentionally public: listed in `isPublicPath` ([proxy.ts](src/proxy.ts)) AND as a documented `ROUTE_EXCEPTIONS` entry in [scripts/audit-routes.mts](scripts/audit-routes.mts). Native clients probe it BEFORE sign-in; fail-soft — a 404 (legacy server) or any reachable response ⇒ proceed.
    - **`X-Summonarr-Api` is stamped on responses** in `proxy.ts` so clients can learn the contract passively. Keep it a coarse integer.
    - **The force-upgrade CTA URL is hardcoded in the client** (iOS `AppInfo.appStoreURL`), NEVER taken from a server response. The server may send a message string, never a link the client opens.
    - **Floors are for breaking changes; feature-gate for graceful degradation.** `MIN_API_VERSION`, the client's `requiredServerApiVersion`, and `MIN_CLIENT` are HARD floors — the accepted version *range* is `[floor, ∞)`, not an exact pin. Raise a floor ONLY when a peer genuinely cannot function. To keep supporting an older peer that merely *lacks* a newer feature, leave the floor and gate that feature on the reported `apiVersion` (the iOS client reads `X-Summonarr-Api` → `SessionStore.serverSupports(N)`). Bumping a floor per feature collapses the range into a hard cutoff — the opposite of "support a prior version for a while."

26. **NEVER `logAuditOrFail` after a mutation that has already committed.** Use `logAudit` (the swallowing variant) post-commit.

    Why:
    - `logAuditOrFail` ([src/lib/audit.ts](src/lib/audit.ts)) re-throws on a failed audit write — it exists for use *inside* a `$transaction`, where a failed audit should roll the whole thing back.
    - Called *after* a `prisma.x.delete`/`update`/raw mutation has already committed (no enclosing tx), a transient audit-write failure returns **500 on a successful destructive operation**. The retry then 404s (row already gone) with no audit trail, or re-applies and double-audits (role-change).
    - This was the failure mode in six routes (user delete + role-change, play-history delete, DB restore, Plex + Jellyfin terminate, cache clear) — all switched to `void logAudit(...)`.

    Rule: `logAuditOrFail` is legitimate **only** as the last op inside a `$transaction` (so its throw rolls back the mutation it audits). Anywhere the mutation is already durable, use `logAudit` — its contract is "a failed audit write must never break the triggering request."

27. **In-memory ledgers / "force-revalidate" marks go AFTER the DB write they guard, not before.**

    Why:
    - Several finalize/revocation paths keep an in-process set (`recentlyFinalizedPlexSessions`, `markSessionForceRevoked`) alongside a DB write (`recordCompletedSession`, AuthSession delete). The in-memory mark is the single-replica fast path; the DB row is the source of truth.
    - Marking *before* the write means a failed/rolled-back write leaves the ledger asserting a state the DB doesn't reflect: a session ledger-locked with no `PlayHistory` row (the now-playing card never returns for ~1h), or a "revoked" mark on a row that's still live (resurrects on restart).
    - `revokeAllUserSessions` already does it right (mark after the tx); `revokeSessionById` was fixed to match.

    Rule: write the DB row first; only on success update the in-memory ledger. If the write throws, let it propagate so the caller learns the operation failed instead of trusting a phantom mark.

28. **NEVER hard-delete a `MediaServerUser`. Soft-delete (`active = false`) instead.**

    Why:
    - `PlayHistory` and `ActiveSession` FK `MediaServerUser`. The FK used to be `onDelete: Cascade`, so deleting a server-user *permanently and unrecoverably* destroyed their entire watch history — and the live poller is the only Jellyfin-history writer (guardrail 19), so it cannot be rebuilt. Play history is server/usage data that must outlive a user's removal; it is not part of the user's account.
    - A degraded Jellyfin `/Users` fetch (a `200` with a truncated list) once made the hourly download-policy prune delete every absent user and cascade-erase their history.

    Rules:
    - The FK is now `onDelete: Restrict` on both `PlayHistory` and `ActiveSession` — any hard-delete of a `MediaServerUser` that still has history/sessions THROWS, surfacing the landmine instead of silently erasing data. Do not revert it to `Cascade`.
    - The Jellyfin prune in [download-policy.ts](src/lib/download-policy.ts) sets `active = false` (soft-delete) for departed users; the next sync re-activates a returning one. Do not reintroduce `deleteMany` on `MediaServerUser`.
    - Active-management surfaces (the diagnose count, the REST server-users list) filter `active: true`; history/stats surfaces (the play-history user filter, the activity/stats aggregates) intentionally do NOT — a departed user's history stays visible and attributed. The admin server-users **page** is the deliberate middle case: it lists active rows PLUS departed ones that still hold play history, because those are exactly the rows whose attribution may need fixing by hand. `PATCH /api/admin/server-users/[id]` mirrors that split — the `{ userId }` link branch accepts a departed row, the `{ downloadsEnabled }` branch still 404s it (there is no server-side account left to push a policy to).
    - **De-registering a media-server instance is NOT a licence to hard-delete its rows.** The removal cleanup in `/api/admin/media-instances` (guardrail 35) deletes that slug's library items and `ActiveSession` rows, but `MediaServerUser` is soft-deleted (`active = false`) and `PlayHistory` is left completely untouched — the same rule, at a new temptation site.

29. **Page/layout authorization is DB-checked (`authActive()` / `readActiveSummonarrSession()`), NEVER the proxy alone and NEVER JWT-only `auth()`.**

    Why:
    - `proxy.ts`'s matcher carries a `missing: [next-router-prefetch, purpose=prefetch]` clause, so the proxy (login redirect, DB session check, admin/role gating) does **not** run on prefetch requests. A forged `GET /page` with header `next-router-prefetch: 1` skips all of it. Next's own docs say the same — *"Always verify authentication and authorization inside each Server Function rather than relying on Proxy alone"* ([proxy.md](node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md)) — and prescribe a check close to the data ([data-security.md](node_modules/next/dist/docs/01-app/02-guides/data-security.md)).
    - `auth()` ([src/lib/auth.ts](src/lib/auth.ts)) verifies only the JWT signature + expiry. It does NOT see a revoked `AuthSession`, a `sessionsRevokedAt`/`passwordChangedAt` cutoff, or a role demotion. On the prefetch path (proxy skipped) it would be the *only* check, so a demoted-but-unexpired admin token could read admin pages.

    Rules:
    - Every `(app)` page is login-gated by the DB-checked root [(app)/layout.tsx](src/app/(app)/layout.tsx) (`authActive()` → `redirect("/login")`). Keep that gate — it's the prefetch-safe backstop for the whole subtree. The redirect MUST stay before/outside the layout's `try/catch` or the `NEXT_REDIRECT` throw gets swallowed.
    - A page/layout that makes a **role-based** redirect (`role !== "ADMIN"`, etc.) MUST read the session with `authActive()` (drop-in for `auth()`, identical `SummonarrSession` shape) or `readActiveSummonarrSession()` (the [admin layout](src/app/(app)/admin/layout.tsx) pattern) — never JWT-only `auth()`.
    - `auth()` is fine for **personalization** reads (badge visibility, "my vote", "show admin shortcut") — a few seconds of staleness there is cosmetic, not an authz decision. Don't pay the DB round-trip on every discovery-page render for those.
    - API routes are already DB-checked via `withAuth`/`withAdmin` (guardrail 6a). This rule is about server-component pages/layouts only.
    - `authActive()` and the public `/api/auth/me` ALSO re-check the UA fingerprint (`matchesStoredFingerprint`, [ua-fingerprint.ts](src/lib/ua-fingerprint.ts)) for cookie sessions — the prefetch-skip means the page-render path and that public route are otherwise the only authenticated surfaces with no fingerprint enforcement. Bearer/native sessions skip it (app-secure storage, not an ambient cookie).

30. **Cap every JSON request body — `readJsonCapped(req, maxBytes)` (or `readJsonCappedOr` for tolerant routes), never a bare `await req.json()`.**

    Why:
    - [next.config.ts](next.config.ts) sets `proxyClientMaxBodySize: "50mb"` — a backstop, NOT a per-route limit. A bare `await req.json()` will parse up to 50 MB, so an oversized body (anonymous on first-run `register`, or any authenticated user on request/issue/vote routes) forces a large JSON parse = memory/CPU DoS.
    - The helpers in [body-size.ts](src/lib/body-size.ts) combine `checkBodySize` (Content-Length fast-reject) + `assertBodyBytesUnderCap` (post-read byte check; catches `Transfer-Encoding: chunked`) + `JSON.parse`. `readJsonCapped` 400s on malformed JSON; `readJsonCappedOr(req, max, fallback)` tolerates an empty/malformed body for routes where no body is a valid request.

    Rules:
    - New JSON route → `const parsed = await readJsonCapped<T>(req, CAP); if (parsed instanceof NextResponse) return parsed; const body = parsed;`. Caps: ~16 KB single object, 32–64 KB text-bearing, ~1 MB bulk/batch arrays.
    - Don't reintroduce a bare `await req.json()`. Upload/binary bodies (thumbnails, backup restore) are the only legitimate bypass.
    - Every JSON-reading route — including admin/settings/sync — now goes through the helpers; there are zero bare `await req.json()` calls left in `src/app/api`. Keep it that way.

31. **Bound large async fan-outs with `mapLimit` / `settleLimit` from [src/lib/concurrency.ts](src/lib/concurrency.ts) — never a bare `Promise.all(items.map(...))` over a user/library-sized list.**

    Why:
    - A bare `Promise.all` issues every task at once. Over a request-batch- or library-sized list this saturates the small Prisma connection pool and bursts hundreds of requests at upstream APIs (TMDB ~50 req/s; OMDB free tier 1k/day). Two live cases motivated the helper: the blocking ratings batch fanned out up to 200 OMDB chains ([omdb-availability.ts](src/lib/omdb-availability.ts)), and the cold Discover page fired ~105 concurrent TMDB list fetches ([tmdb.ts](src/lib/tmdb.ts)).
    - `mapLimit` is a bounded `Promise.all` (rejects if a task rejects — use when tasks self-catch). `settleLimit` is a bounded `Promise.allSettled` (never rejects) — a drop-in for the paged TMDB `Promise.allSettled(Array.from(...))` pattern.

    Rules:
    - Fixed-size fan-outs (2–3 elements, e.g. movie+tv split, similar+recommendations) stay as plain `Promise.all` — the cap is only for lists whose length scales with input/library size.
    - Pair the cap with `coalesce(key, fn)` (now exported from [concurrency.ts](src/lib/concurrency.ts); tmdb.ts, trakt.ts and mdblist's top-rated helper all import it) on shared cache-key computations so simultaneous callers share one fan-out instead of multiplying it. The list helpers wrap their whole body in `coalesce` (keyed on their cache key) and bound the page fetch with `settleLimit`; match that shape for any new list helper.
    - Don't add a third copy of the OMDB API key read — `getApiKey()` in [omdb.ts](src/lib/omdb.ts) is memoized + in-flight-coalesced (30s TTL) precisely so a 200-item batch doesn't issue ~400 identical `setting.findUnique` reads. Pass `{ fresh: true }` only for the admin connection test.

31a. **A limit only bounds work the task AWAITS, and `after()` has no limit at all. NEVER pass a stale-while-revalidate getter to `mapLimit`, and a cron calling `attachRatingsUnified` ALWAYS passes `deferToAfter: false`.**

    Why:
    - `getOmdbRatingsForTmdb` returns a stale row immediately and DETACHES its refresh. `mapLimit(staleRows, 6, getter)` therefore capped six cache reads at a time while every upstream refresh started together.
    - Next runs a request's `after()` callbacks through a p-queue with no concurrency limit, all at once when the response closes. The recommendation verdict pass calls `attachRatingsUnified` once per 200 titles, so up to 50 calls' worth of deferred refreshes ran together after the cron responded. Observed live: hundreds of `[omdb] TMDB external_ids fetch failed (429)` lines right after `[warm-recommendations ok]`.

    Rules:
    - A task handed to `mapLimit`/`settleLimit` must await all of its upstream work. For a list refresh use `revalidateOmdbForTmdb` ([omdb.ts](src/lib/omdb.ts)), the getter with its refresh awaited, or write the awaited twin of whatever getter you need.
    - `deferToAfter: false` runs the deferred refresh before `attachRatingsUnified` returns. It is for callers with no response to protect and many calls to make; pages keep the default so the viewer isn't held waiting.
    - The OMDB fallback never fetches a title that already has an OMDB row (`lacksOmdbRow`). The getter would only hand that row back, plus a detached refresh; the stale-OMDB pass refreshes it instead.
    - `tests/ratings-refresh.test.mts` pins every route with in-flight counts and `tests/recommendations.test.mts` pins the verdict pass's option; all twelve mutations fail a named test.

32. **A Radarr/Sonarr instance is identified by an `arrInstance` slug string, NEVER the old `is4k` boolean.** The two-instance (HD/4K) model was generalized to N named instances (e.g. an "anime" instance).

    Why:
    - The instance identity moved from `is4k Boolean` to `arrInstance String @default("")` across all six models (`MediaRequest`, `Radarr/Sonarr{Wanted,Available}Item`, `TrashApplication`) — `arrInstance` sits in the `@@id`/`@@unique` keys. Slugs: `""` = the default instance, `"4k"` = the legacy 4K instance, `"anime"`/… = named.
    - **The migration is NON-DESTRUCTIVE.** `is4k` is RETAINED in the schema (deprecated, out of every key) so `prisma db push` never drops a column — a column drop is a "genuinely destructive" change the entrypoint refuses to auto-apply (`docker-entrypoint.sh` exits 1). A pre-`db push` hook in the entrypoint backfills `arrInstance` from `is4k` (false→"", true→"4k") on boot, so db push only swaps the PK/unique keys onto an already-populated column — landing as the entrypoint's **auto-safe** "unique constraint" / "primary key will be changed" warnings. No manual step, no data loss; a real key collision fails db push loudly (23505) rather than merging 4K into the default. Non-Docker deploys run [scripts/migrate-is4k-to-arrinstance.mjs](scripts/migrate-is4k-to-arrinstance.mjs) before their manual push. Don't drop `is4k` until a later release when every deployment has migrated (mirrors the deprecated `User.autoApprove`/`quotaExempt`).

    Rules:
    - **Instance→Setting-key derivation is centralized in [arr-instances.ts](src/lib/arr-instances.ts)** (`arrSettingKey(service, slug, field)`; named slugs capitalize their first char → `radarrAnimeApiKey`; `"4k"` is unchanged so all legacy `radarr4k*` keys survive). The server-side registry (which instances exist + their routing/access metadata, a JSON `arrRadarrInstances`/`arrSonarrInstances` Setting) is [arr-instance-registry.ts](src/lib/arr-instance-registry.ts) — `getArrInstances` / `getSyncableArrInstances`.
    - **`arr.ts` client fns take `variant: ArrVariant = ""` — an instance slug.** Pass a request's `arrInstance` through. The legacy `"hd"` spelling still maps to `""` in `getCfg` (don't remove that back-compat). Sync fans out over `getSyncableArrInstances` with per-instance SCOPED `deleteMany` (guardrail 13); webhooks resolve the firing instance by secret-as-discriminator over every instance's `arrSettingKey(service, slug, "WebhookSecret")` (guardrail 2 — no early return, no HMAC).
    - **Per-instance secret Setting keys (`radarr<Slug>ApiKey`/`WebhookSecret`) must stay encrypted.** `isSensitiveSettingKey` in [settings-sensitive-keys.ts](src/lib/settings-sensitive-keys.ts) matches them by regex (guardrail 7a) — the static list can't enumerate admin-defined slugs.
    - **Access to a NAMED instance is a per-user grant** (`User.instanceGrants` JSON; `canRequestInstance`/`canAutoApproveInstance` in [permissions.ts](src/lib/permissions.ts)). The default is open to any requester; `"4k"` still uses the `REQUEST_4K*`/`AUTO_APPROVE_4K*` bits (zero user-data migration). Request routing (anime = TMDB genre 16 + `ja`/JP) is `routeMediaToSlug`.
    - **Instance-aware surfaces (landed post-v0.15.0):** the trash-guides admin UI/API (`?variant=<slug>`), the approve quality-profile picker (`/api/requests/quality-profiles?instance=<slug>`, legacy `?is4k=` kept), admin request-list instance chips, bulk "Request all" + Discord `/request` auto-routing (per-item `routeMediaToSlug`, access-gated fallback to default), the per-user grants editor (Users → Permissions & Quota → Instance access), detail-page "Request on <instance>" buttons ([request-instance-button.tsx](src/components/media/request-instance-button.tsx)) — whose target list has ONE resolver, `resolveNamedInstanceTargets` ([named-instance-targets.ts](src/lib/named-instance-targets.ts)), shared by the movie page, the TV page and `GET /api/requests/instances`; **never re-derive it at a call site.** All three had open-coded it and two had already drifted: the route enumerated `getArrInstances` (every REGISTERED instance) while the pages used `getSyncableArrInstances` (configured only), so a native client got a button for an instance with no url/apiKey that `/api/requests` can only answer 400 to. Enumerating the *configured* set is the correct behavior, and the resolver also collapses the per-instance `findFirst`+`findUnique` pair into two `arrInstance: { in: … }` reads for the whole set — library-diff arr verdict, per-instance disk stats (`ArrDiskSpace.extra` — additive, don't change the `radarr`/`sonarr` fields native clients decode), and `IssueGrab.arrInstance` + the issue Replace instance picker (webhook completion match is instance-scoped). The per-source `/api/sync/plex` + `/api/sync/jellyfin` Resync routes are ALSO instance-aware since a body `instance` slug was added — every read, delete AND insert follows it. That last one is not optional: scoping the deletes while leaving `serverInstance` off the inserted rows deletes a named server's library and re-creates it under the default slug, which un-restricts a `restricted` server and puts its server-local ratingKeys in the default's namespace. Their marking pass carries the same per-user visibility gate as the orchestrator, for the same reason. `/api/sync/tv-episodes` likewise rebuilds `TVEpisodeCache` from the UNION of every configured server, gated all-or-nothing — that table has no `serverInstance` column, so a partial union would wipe a down server's rows.
    - **Still default/HD+4K-scoped by design (not gaps):** the legacy HD/4K connection forms in settings-ui.tsx (named instances use `ArrInstancesManager`), `Request4kButton`'s `is4k:true` body (legacy shorthand the API keeps), the TRaSH starter pack + overview KPIs, and `RequestButton`'s request-time profile picker (default instance; the server drops the override on auto-route — see requests/route.ts).

33. **Account removal DISABLES; it never scrubs. The irreversible scrub is a separate, admin-only, two-step action.** [account-lifecycle.ts](src/lib/account-lifecycle.ts) is the only module that implements either half.

    Why:
    - Both removal paths (`DELETE /api/profile` self-delete and `DELETE /api/admin/users/[id]`) used to anonymize in place. That set `MediaServerUser.userId = null`, and **both `getMyWatchHistory` and the admin per-user views resolve play history through `MediaServerUser.userId`** — so from the moment an account was removed, every watch the person kept racking up on Plex/Jellyfin stopped being attributed to anyone. It never healed: the only relink path is by email, and the scrubbed row's `deleted-<id>@deleted.invalid` (or a Jellyfin user's synthetic `@jellyfin.local` login email) can never match what the media server reports.
    - Anonymizing also destroyed the identity an operator needs to undo a mistaken removal. A self-hosted instance wants "turn this account off", not "erase this person", as the default.

    Rules:
    - **`deactivateUserInTx` writes EXACTLY two things**: `authSession.deleteMany` (kill every device) and `{ deactivatedAt, sessionsRevokedAt }` on the User row. Do NOT add a field to that payload, and do NOT touch `MediaServerUser` — that link staying bound is the whole point. The deepEqual pins in `tests/account-lifecycle.test.mts` and `tests/profile-routes.test.mts` fail if you do.
    - **`purgeUserDataInTx` (POST `/api/admin/users/[id]/purge`) is the only place that scrubs**, and it throws `NotDeactivatedError` unless the row is already disabled — an active user's data can never be destroyed in one click. It is what services a real "delete my data" request (App Store Guideline 5.1.1(v) / GDPR erasure); the in-app "close account" button no longer does, so **an operator must run a purge when a user asks for erasure**. It sets `purgedAt`, which permanently blocks reactivation.
    - **Identity survives, so SIGN-IN must be refused explicitly.** Every provider's lookup (email, `plexUserId`, `jellyfinUserId`, OAuth `Account`) still matches a disabled row. `signInAndMintSession` ([auth.ts](src/lib/auth.ts)) is the single chokepoint: it re-reads `deactivatedAt` and throws `AccountDeactivatedError` **before** `initializeTokenOnSignIn` mints a JWT or writes an AuthSession row. If you add a provider, route it through that function — do not rely on `verifyAndRefreshSession`'s `deactivatedAt` check, which only fires on the *next* request, after the client already holds a token.
    - **Notifications are suppressed at two chokepoints, not per channel.** A disabled row keeps a live notification email, Discord link and push subscriptions. `claimAvailableNotificationWinners` ([notify-available.ts](src/lib/notify-available.ts)) drops disabled requesters from the batch "now available" winners (covering all six sync sites × four channels at once), and `notifyRequestStatusChange` gates the single-request approve/decline/available fan-out on one lookup. Don't re-scatter this into the individual push/Discord/email queries.
    - **NEVER test for a purged row with a bare `purgedAt != null`** — use `isPurgedRow` ([account-lifecycle.ts](src/lib/account-lifecycle.ts)). `purgedAt` postdates the deactivate/purge split, so every account removed by the older anonymize-on-delete code carries the scrubbed SHAPE (`deleted-<id>@deleted.invalid`) with a NULL marker. Reading those as merely "disabled" let one be re-enabled into a **zombie**: an ACTIVE row with no password, no provider subject, no OAuth rows and an unroutable email, so nobody can ever sign into it, while it counts toward the active-admin total and re-enters the Plex backfill's candidate set (warning on every boot). `markLegacyPurgedAccounts()` stamps the marker at boot and re-disables any existing zombie; it runs BEFORE `runPlexUserBackfillIfNeeded` in [instrumentation.ts](src/instrumentation.ts) for exactly that reason. The tombstone address has one producer, `purgedEmailFor` — keep it that way or detection silently breaks.
    - The last-admin CAS (advisory lock 42) lives on the deactivate path only; purge doesn't need it because a disabled row is already out of the active-admin count. Callers MUST short-circuit an already-disabled row before calling `deactivateUserInTx` — re-running it on a disabled ADMIN sees its own row excluded from the count and throws `LastAdminError` spuriously.

34. **`MediaServerUser → User` attribution resolves on the provider SUBJECT id first, email second — and NEVER overwrites a manual pin.** This binding is what makes play history belong to somebody: both `getMyWatchHistory` and every admin per-user view resolve through `MediaServerUser.userId`.

    Why:
    - `MediaServerUser.sourceUserId` **is** the Plex accountID / Jellyfin userId, i.e. exactly what sign-in pins to `User.plexUserId` / `User.jellyfinUserId`. A match there is the same identity by construction, with no collision risk — those columns are unique and written only by the matching provider's sign-in.
    - Email is a weak key and used to be the ONLY one. A Jellyfin account needs no email at all (both sides null ⇒ nothing ever linked), a Jellyfin-provisioned row carries the synthetic `jellyfin-<id>@jellyfin.local` login address no media server will ever report, and either side is user-changeable. Those users' watches were silently attributed to nobody, forever.

    Rules:
    - Both resolvers — `resolveMediaServerUser` ([play-history.ts](src/lib/play-history.ts), every 5s poll) and the hourly Jellyfin sync in [download-policy.ts](src/lib/download-policy.ts) — try the subject id, then fall back to email. Only the **email** branch carries the `mediaServer` cross-provider guard; a subject match needs none.
    - **Neither resolver may filter on `deactivatedAt`** — a disabled account still owns its history (guardrail 33). A PURGED account is excluded by construction on both branches instead (the purge nulls the subject columns *and* rewrites the email), so don't add a redundant status filter that would also catch disabled users.
    - **`manualUserLink = true` means an admin set the binding by hand — automatic resolution must skip the row entirely.** Set by `PATCH /api/admin/server-users/[id]` for both a manual link and a manual unlink (an unpinned unlink would be re-bound on the next poll). Without this pin the admin action is useless: the poller re-derives `userId` every 5 seconds. `{ autoLink: true }` releases the pin.
    - The link half of that route is deliberately NOT gated on `isServerAdmin` or `source === "plex"` — those guards belong to the `downloadsEnabled` half. Every identity owns watch history that has to land on the right account.

34a. **The request watch grade scores only APPROVED, MATURED, COVERED requests, reads attribution through `linkedIdentityBranches`, and never gives an F to a user whose watches can't be seen.** Rules in [watch-grade.ts](src/lib/watch-grade.ts), data in [watch-grade-data.ts](src/lib/watch-grade-data.ts).

    Why:
    - AVAILABLE doesn't mean approved. A library sync marks a PENDING request AVAILABLE when its title shows up on Plex or Jellyfin, so a grade that reads status alone weighs requests nobody approved. By product decision only approved requests are weighed; pending and declined ones never are.
    - Approval is a decision about a TITLE. The web queue approves every pending duplicate together, but Discord offers only the earliest one and the iOS app approves one request at a time, so the same approval would otherwise count for some requesters of a title and not others. By product decision, approving a title counts for everyone who requested it.
    - Scoring a request that is still inside its grace period — or was fulfilled before play history covered the user's servers — only when it happens to be watched is survivorship bias: the watches you saw lift the score while their unwatched siblings wait. So those requests are never scored, watched or not.
    - A Plex `MediaServerUser` row is created at an account's FIRST recorded play, so the requester who never watches anything has no row at all. Reading "no row" as unlinked exempts exactly the user the grade exists for; a provider subject (`User.plexUserId`/`jellyfinUserId`) that an admin hasn't pinned to another account makes the account observable.
    - An account linked to nothing, or only to untracked servers, gets NO letter. An F built from data that was never collected is worse than no grade.

    Rules:
    - **Only APPROVED requests are graded, and approval counts per TITLE on an instance.** An AVAILABLE request counts when it, or ANY request for the same `(tmdbId, mediaType, arrInstance)`, carries `approvedAt` (`keepApprovedRequests` in watch-grade-data.ts, shared by the grade and the preview's requester list). A Discord or iOS duplicate, a copy of a greenlit request, and another user's pending request left alone by an auto-approval all count through the approved request. Another instance's approval does not, and a declined request covers nothing.
    - **`MediaRequest.approvedAt` records DECISIONS, and only the `/api/requests` routes (POST's create path lives in [request-create.ts](src/lib/request-create.ts), which the watchlist auto-request shares — guardrail 34b) and Discord interactions write it.** Approval sets it: admin approve (single, batch or Discord) and auto-approve at creation, unconditionally, from any prior status. Decline clears it. A failed Radarr/Sonarr push that rolls an approval back to PENDING KEEPS it, because the approval was made. A copy of a greenlit request records none of its own. NEVER write it from a sync, a webhook, a revert, the availability CAS or raw SQL: that grades unapproved requests again. `tests/request-approval.test.mts` scans every MediaRequest write in `src/`, including one built in a variable, and every mention of the column.
    - **Rows older than the column carry their `createdAt`, stamped ONCE EVER** by `backfillRequestApprovals` ([request-approval.ts](src/lib/request-approval.ts)) behind the `requestApprovedAtBackfillRanAt` marker, because nothing recorded whether they were approved. Never let it run per boot: after the first run a null `approvedAt` on an AVAILABLE row means nobody approved it, and a re-run would stamp exactly those rows. For the same reason `register()` awaits it before any fire-and-forget DB work and retries a failed run in the same boot. A run that only succeeds at a LATER boot stamps whatever a sync marked AVAILABLE in between.
    - Accepted: when a title leaves the library, the sync reverts an AVAILABLE request to APPROVED (and pushes it again) without recording an approval, so it counts only through another request's approval of the title. A downgrade that drops the column with `SUMMONARR_ACCEPT_DATA_LOSS` keeps the marker, so upgrading again stamps nothing.
    - Attribution goes through `resolveAccountMediaIdentities` ([my-watch-history.ts](src/lib/my-watch-history.ts)), which evaluates the same `linkedIdentityBranches` the self-service history page queries with. Never restate the linkage rule in SQL: the play aggregate receives explicit (user, identity) pairs. `tests/watch-grade-data.test.mts` runs a parity check between the two resolvers.
    - Only plays at or after the request's `createdAt` count, and summed plays count toward "watched" so chunked viewing isn't marked unwatched. Half credit needs a real start — `startedFloorSeconds`: a quarter of the runtime, never under 15 minutes, half of a short. With the old five-minute floor a requester who sampled every request could never score below a C.
    - **TV is scored PER SEASON and the best season counts** — `tvEpisodePercent` of ONE season's REGULAR-season library episodes (specials excluded, integer ceil). A whole-show denominator made a 200-episode show need 100 watched episodes, and grew every week for an airing show, so a request fully watched at 8 of 8 DECAYED to partial once later seasons landed. `loadLibraryEpisodes` is per (tmdbId, season) for this reason.
    - **One title, one unit.** `@@unique([tmdbId, mediaType, requestedBy, arrInstance])` lets a user hold an HD and a 4K request for one title; `foldByTitle` keeps the earliest (its plays-since-request set is the superset), dates fulfilment from the first, and reports `duplicates`. Without it one watch or one miss counted twice and the pair reached `MIN_GRADED_REQUESTS` alone.
    - Coverage starts at the LATEST history start among the user's *tracked* servers. Plays through an identity on an untracked server still count as watches.
    - **Other viewers are PEOPLE, counted through the same linkage rule.** A request the requester didn't watch counts as watched once `watchGradeOtherViewers` other people watched it since the request, as play history recorded them: a movie play flagged watched/completed, or a season's watched episodes reaching the same `tvEpisodePercent` share. The audience aggregate returns media-server identities, each keyed by the account that owns it via `resolveMediaServerUserOwners` ([my-watch-history.ts](src/lib/my-watch-history.ts)) — or, with no account, by its provider id, so one Plex account seen on two servers (two `MediaServerUser` rows) is still one person. One account's Plex and Jellyfin logins count once (merged per season by MAX — never summed), and a login an admin pinned away from the requester counts as someone else. When an FK link and an unpinned subject match claim one login, the FK account owns it. The requester's own logins are NOT filtered out, by construction: a login whose plays were flagged watched already gave the request full credit, and full-credit requests never have their audience read — a filter there was an equivalent mutant, so it went.
    - **The audience is read ONLY where it can change a verdict** — scored requests short of full credit, chosen by a first `gradeUser` pass — and as ONE ROW PER IDENTITY AND SEASON from the stored `watched`/`completed` flags, never per episode. The Users page grades up to a thousand accounts over a year of requests on every render; per-episode rows for every viewer of every popular show is what that costs otherwise. `otherViewers` is null on every verdict the audience wasn't read for (rule off, unobservable, grace, untracked, watched) — a `0` there would be an artefact.
    - Other viewers only ever RAISE a request's credit. They never score a grace or untracked request, and `0` turns the rule off — every viewer count is ≥ 0, so the `> 0` guard in `gradeUser` is load-bearing. `watchGradePairError` refuses a window no longer than the grace period on write (merged with the stored values); that pair scores nothing, silently.
    - **The letter cutoffs and the requests a letter needs are settings, and cutoffs must stay STRICTLY descending.** Out of order, `letterForScore` hands out the first letter a score clears, so an A below a B turns every B into an A. The write path — the settings PATCH and the preview alike — validates the RAW merged values: `mergedWatchGradeSettings` (stored values for keys the body leaves out, defaults for blank ones) into `watchGradeCrossFieldError`. NEVER route that check through `parseWatchGradeSettings`: its read-side repair (all four cutoffs back to the defaults, together) would make a bad set look valid and then silently ignore it.
    - **The preview judges exactly what a save would**, with the same merge and rules — an answer for values the save would refuse previews something that can't happen. It grades every requester twice (stored, then proposed), sequentially so it never doubles the load on the five-connection pool, which is why it is ADMIN-only and runs from a button rather than on every keystroke.
    - List surfaces (`getWatchGradeSummaries`) swallow failures to `null`: a broken aggregate must not take down the Users page or the request queue. The detail route surfaces the error.
    - The test files were mutation-verified: counting grace watches, dropping the coverage or since-request bound, treating unlinked users as observable, ignoring subjects, a float `ceil`, and averaging rounded credits each fail a named test. So do counting logins instead of people, counting the requester's own logins, `0` not meaning off, picking a login's owner by anything but the FK first, a whole-show TV denominator, the five-minute start floor, summing a person's logins, counting duplicate requests twice, and reading the audience for a watched or grace request. So do letters ignoring the configured cutoffs or count, allowing tied cutoffs, repairing on the write path, a preview that grades the proposal with the stored settings, and a preview open to non-admins. So do grading or previewing without approval, dropping per-title coverage or its instance scope, a chunked approval lookup that drops a title, any sync, webhook, revert, CAS or raw-SQL write of `approvedAt` (inline or through a variable), an approve or decline that stamps or clears only from PENDING, a push rollback clearing it, a copy or a mirrored bulk row recording one, and a backfill that runs every boot, doesn't retry, or runs after the fire-and-forget startup work.
    - Making the grade ENFORCE anything (quota, auto-approve, blocking) is a product decision, not a refactor. It would also need these unobservable-user semantics revisited, so that nobody is penalized or exempted by accident.

34b. **A watchlist auto-request files ONLY through `createMediaRequest` ([request-create.ts](src/lib/request-create.ts)), and the `AutoRequestLedger` is what stops it re-requesting in a loop.** Rules in [auto-request.ts](src/lib/auto-request.ts), the Plex half in [plex-watchlist.ts](src/lib/plex-watchlist.ts).

    Why:
    - `createMediaRequest` is POST `/api/requests` minus its HTTP shell: instance routing and access (guardrail 32), quota, blacklist, content cap, duplicates, the Serializable create (guardrail 23), auto-approve + `approvedAt` (34a), the push rollback and the admin fan-out. A second create path is a second copy of all of that, and the copies drift.
    - The Plex watchlist is re-read every poll. Without a per-(user, title) memory, a title an admin DECLINED or DELETED is filed again on the next run, forever.

    Rules:
    - **Never write a `MediaRequest` from the auto-request code.** Call `autoRequestTitle`; it applies the route's pre-body gates (maintenance, Discord link, and — for a user-driven add — the `requests:` rate limit) and then `createMediaRequest`.
    - **`requested` is TERMINAL.** A filed request that is later declined or deleted is never re-filed by the cron; so are `already-available`, `already-requested`, `blacklisted`, `permanently-declined`, `rating-cap`. Only the outcomes in `RETRYABLE_OUTCOMES` (quota, access, transient) are retried, and only after `AUTO_REQUEST_RETRY_AFTER_MS`. An unknown outcome string is terminal. `Ledger.requestId` has NO FK on purpose — cascading a request delete into the ledger would re-arm the loop.
    - **A Summonarr watchlist add is always attempted** (an explicit user action), never blocked by the ledger, and it never fails the add: the response gains an additive `autoRequest` field, absent whenever auto-request does not apply (the iOS app decodes this response).
    - **Gates, in order:** an `AUTO_REQUEST*` bit for the media type (checked first — no query for users without one), then `feature.behavior.watchlistAutoRequest` (default OFF), then for Plex the user's `plexWatchlistAutoRequest` toggle. The bits grant only the automation; the request itself still needs the base `REQUEST*` bits.
    - **The Plex token is the user's own**, stored as an `Account { provider: "plex" }` row at Plex sign-in ONLY while the feature is on, encrypted by the Prisma extension (guardrail 7a — never `encryptToken`). A plex.tv 401 deletes it. Both plex.tv hosts go through `safeFetchTrusted` with `PLEX_WATCHLIST_HOSTS`.
    - **The SERVER-TOKEN path is the optional second way in** (Setting `plexWatchlistServerSource = "true"`, [plex-friends-watchlist.ts](src/lib/plex-friends-watchlist.ts)): for a user with NO token of their own, the cron reads their watchlist through each configured Plex instance's owner token (`getMediaInstances` + `getPlexConfig(slug)` + skip-if-unconfigured, guardrail 35) via community.plex.tv GraphQL (`allFriendsV2`, `userV2.watchlist`), hosts in `PLEX_COMMUNITY_HOSTS`. Friends are unioned across instances and deduped by numeric account id; the owner themself is matched through `plex.tv/api/v2/user` and read from the discover list. A user's OWN token always wins when present. Same ledger, same `"plex-watchlist"` source, same per-run cap — switching paths never re-files a title. **Friend nodes carry no guid, so each needs a `metadata.provider.plex.tv` lookup; results (positive and negative) are cached in-process by ratingKey (`METADATA_CACHE_*` in [plex-watchlist.ts](src/lib/plex-watchlist.ts)) so an unchanged watchlist costs zero GETs on the next run. A FAILED lookup is never cached; a user none of whose titles resolved because lookups failed reads `"error"`, not `"ok"`, counts in `errors` (the run degrades) and is surfaced in `server.lookupFailures`. A metadata 401 still goes to `rejectToken`, never near the Account delete.**
    - **An ADMIN-token 401/403 NEVER reaches the branch that deletes a user's `Account` rows.** It raises `AdminTokenRejectedError` (or a metadata-lookup `PlexTokenRevokedError` caught inside the server path), stops that instance for the run, counts in `server.adminTokensRejected`, degrades the run (`plexWatchlistRunProblems` → `X-Cron-Degraded`), and warns through `warnOnChange` (7b). The only `account.deleteMany` in the cron is the user-token path's catch. A null friend watchlist is the friend's privacy setting — per-user status `"private"`, not an error.
    - **Consent: the server path reads only users with `User.plexWatchlistOptInAt` set** — stamped when the user switches the profile toggle ON (PATCH `/api/profile/auto-request`), cleared when they switch it off — because `plexWatchlistAutoRequest` defaults true and is therefore not consent to file requests for someone who may never have opened Summonarr. The admin may override with `plexWatchlistServerAutoEnroll = "true"`. The own-token path is unchanged (signing in with Plex while the toggle is on already is the action).
    - **Friend → user is subject-first and never by email** (`resolvePlexAccountUsers`): an admin's manual `MediaServerUser` pin (incl. a pin to nobody) > `User.plexUserId` > an automatic plex `MediaServerUser` link; deactivated/purged accounts are dropped, not fallen through. The GraphQL friend id is believed to be the account UUID, bridged to the numeric id by `plex.tv/api/v2/friends` (`friendAccountId`; an all-digit id passes through) — **this mapping is UNVERIFIED against a live plex.tv** and every shape assumption lives in the pure parsers there. The run writes `plexWatchlistServerStatus` (per-user `ok`/`private`/`error` + unmatched-friend count, best-effort, swallowed) for the profile copy and the Settings → Media → Plex Watchlist card.
    - The cron (`/api/cron/sync-plex-watchlists`, lock `PLEX_WATCHLIST_LOCK_ID`) walks users one at a time, isolates each user's failure, caps new filings per user per run (`MAX_AUTO_REQUESTS_PER_USER_PER_RUN`), and observes its AbortSignal at user and title boundaries (guardrail 41).
    - **Every POLLED source files through `fileAutoRequestTitles` ([auto-request.ts](src/lib/auto-request.ts))** — the dedupe, the per-type permission filter, the ledger read, the per-run cap and the sequential `autoRequestTitle` loop. The Plex cron and the Trakt cron (34c) both call it; a new polled source must too, never a private copy. Because the ledger is keyed per (user, title) and not per source, a title on two of a user's lists is filed once, by whichever cron sees it first.
    - **Discord's `/watchlist add` is a Summonarr watchlist add** (`addToWatchlist` in [watchlist-add.ts](src/lib/watchlist-add.ts), the same body as POST `/api/watchlist`), so it auto-requests exactly like the web add — and needs a LINKED, active account (`linkedSiteAccount` in the interactions route).

34c. **A user's Trakt account is connected ONLY by the device-code flow, its tokens live ONLY in an `Account { provider: "trakt" }` row, and only a REFUSED grant ends the connection.** Rules in [trakt-user.ts](src/lib/trakt-user.ts), cron `/api/cron/sync-trakt` (lock `TRAKT_SYNC_LOCK_ID`, `TRAKT_SYNC_INTERVAL`).

    Why:
    - Trakt is the watchlist a Jellyfin user does not otherwise have: Jellyfin favorites only hold titles the library already has, which `createMediaRequest` answers "already available", so a Jellyfin-side watchlist could never file anything. It is also For You history for accounts with no media-server identity at all.
    - A self-hosted instance has no fixed public URL to register as an OAuth redirect, and the device flow never sends the user's Trakt password through Summonarr.
    - Since March 2025 Trakt access tokens live 24 hours and every refresh ROTATES the refresh token. A refresh written half-way (new access token, old refresh token) is a connection that dies a day later.

    Rules:
    - **The device code never leaves the server.** `POST /api/profile/trakt/device` answers the user code only; the device code is held in-process per user (`pendingDeviceAuth`), a restart drops it (the user starts again). Polls are paced SERVER-side (`nextPollAt`, widened on Trakt's 429) and a poll RESERVES the code before calling Trakt (`polling`), so two tabs never redeem it twice. The verification URL shown is always a trakt.tv https URL (`safeVerificationUrl`).
    - **Both app credentials are admin Settings, both encrypted** (`traktClientId`, `traktClientSecret` in `SETTINGS_SENSITIVE_KEYS` and the two script copies — guardrail 7a). The id alone powers the public popular lists ([trakt.ts](src/lib/trakt.ts)); the secret is what turns per-user connections on. The cron and the profile card are no-ops without it.
    - **Tokens are raw on write** — the Prisma extension encrypts `Account.access_token`/`refresh_token` (7a, never `encryptToken`). `providerAccountId` is the Trakt user **uuid** (`/users/settings`), not the renamable slug, and the `Account` unique key means one Trakt account backs at most one Summonarr account: a second user connecting it gets `conflict`, checked INSIDE the storing transaction so the upsert can never overwrite the other user's credential. A grant Trakt issued but we did not store (a conflict, or a failure after the code was redeemed) is revoked at Trakt, best-effort.
    - **Refresh before use, write both tokens together.** `TraktUserClient` refreshes a token within `REFRESH_MARGIN_MS` of expiry and once more on a 401. ONLY an `invalid_grant` refusal (`classifyTraktRefreshFailure`; Trakt answers it with 400 or 401) ends a connection (`TraktTokenRevokedError`): the credential AND the imported history are deleted and the connection reads `"reauth"` — the user may have revoked Summonarr on trakt.tv precisely to stop it. Any OTHER 400/401 (`invalid_client`, or a body we cannot read) is the ADMIN's credentials being refused (`TraktClientRejectedError`): nothing is deleted, the run stops and degrades, and one `warnOnChange` line says so (7b) — otherwise a mistyped client secret ends every user's connection within a day (24h tokens), the same hazard 34b forbids for the Plex admin token. A 5xx or network failure deletes nothing and retries next run. A revoked grant alone never degrades the run (`traktRunProblems`).
    - **Watchlist auto-request is 34b, unchanged:** `fileAutoRequestTitles` with the `"trakt-watchlist"` source, per-user toggle `TraktConnection.watchlistAutoRequest`, gated on the AUTO_REQUEST bit and `feature.behavior.watchlistAutoRequest`. Connecting is the consent — no opt-in stamp like the Plex server path needs.
    - **The history is imported, never read live** (guardrail 40 — the engine makes no upstream call). `TraktWatchedItem` is a full per-user replace, newest `MAX_TRAKT_HISTORY_ITEMS`, only when `/sync/last_activities`' watch stamp moved, and at most every `TRAKT_HISTORY_MIN_INTERVAL_MS` (only the 12-hourly For You run reads it). Turning `historySeeds` off, disconnecting, a refused grant and an account purge (`purgeUserDataInTx` deletes `TraktWatchedItem` + `TraktConnection` — the User row is anonymized in place, so the schema cascade never fires) all delete the rows. The replace LOCKS the connection row (`SELECT … FOR UPDATE`) and re-checks the toggle and the grant before writing, so a switch-off or disconnect that lands while the history is being read is never undone by the write.
    - **In For You the Trakt history IS watch history, under the SAME cap.** `mergeHistorySeedRows` folds it into the server history and keeps at most `MAX_WATCH_HISTORY_SEEDS` — the per-user seed ceiling, and with it the graph's required-set budget (40), did not move. A title in both is ONE seed with the later watch and the LARGER play count — never the sum (a scrobbler records the same plays the server did). Both the seed read and the exclusion read carry the `historySeeds` toggle IN the query (`readTraktHistory`). With no Trakt rows the server rows come back untouched.
    - `tests/trakt-user.test.mts`, the Trakt tests in `tests/recommendations.test.mts` and the Trakt cron test in `tests/auto-request.test.mts` pin all of it, each mutation-verified (no poll reservation, no ownership check, an unrotated refresh token, a transient refresh treated as revoked, every 400/401 treated as revoked, a client rejection that does not stop the run, no import spacing, no stamp skip, no toggle re-check under the lock, a leaked device code, client-side pacing, a revoke that keeps the history, no revoke after a failed connect, a purge that keeps the history, summed play counts, a toggle-blind read, a missing exclusion, an uncapped merge, the wrong ledger source).

35. **A Plex/Jellyfin server is identified by a `serverInstance` slug string, and availability is a UNION across every configured server — NOTHING routes to a specific one.** Mirrors guardrail 32's arr model with that one deliberate divergence: an arr *request* must land on exactly one instance, whereas the only question multi-server answers here is "is this watchable somewhere, and what's playing right now."

    Why:
    - Identity moved into `serverInstance String @default("")` on five models — `PlexLibraryItem`, `JellyfinLibraryItem`, `MediaServerUser`, `PlayHistory`, `ActiveSession` — sitting inside the widened `@@id`/`@@unique` keys. Slugs: `""` = the default (and, for every single-server deployment, only) server; `"remote"`/… = named. Unlike `is4k`→`arrInstance` there is **nothing to backfill** — a plain `ADD COLUMN` with a `""` default is already correct for every existing row, which is why this migration needed no interpretation step.
    - The default instance is **byte-identical to the pre-multi-server behavior, everywhere**: `plexSettingKey("", …)`/`jellyfinSettingKey("", …)` reproduce the exact legacy Setting keys, `activeSessionId("plex", "", key)` emits the exact legacy 2-segment `plex:<key>` id (named instances get a 3rd segment), and `mediaInstanceLabel` returns a bare `"plex"`/`"jellyfin"`. A single-server deployment must never be able to tell this generalization happened — treat any diff it *can* observe as a bug.

    Rules:
    - **Key derivation is centralized in [media-instances.ts](src/lib/media-instances.ts)** (`plexSettingKey`/`jellyfinSettingKey`/`activeSessionId`/`parseActiveSessionId`/`mediaInstanceLabel`/`isValidMediaInstanceSlug`) — a **pure, zero-import** module, so `"use client"` components import it directly for badges. The server-side registry (which instances exist; a JSON `plexInstances`/`jellyfinInstances` Setting) is [media-instance-registry.ts](src/lib/media-instance-registry.ts) — `getMediaInstances`/`getSyncableMediaInstances`/`saveMediaInstances`. Entries are deliberately thin (`{slug, name}`): there is no `restricted`/`serverAll`/`autoRoute` metadata because nothing routes. The default `""` is **synthesized, never registry-backed** (a `""` registry entry would shadow it), and `saveMediaInstances` is a full replace — which is why the POST's "instances must be an array" guard is load-bearing: coercing a missing array to `[]` reads as "remove every named instance" and destroys unrecoverable encrypted tokens.
    - **Every library write is `serverInstance`-scoped and every fan-out is all-or-nothing** (guardrail 13). The orchestrator's Plex and Jellyfin arms each fetch per instance with per-instance error isolation, union the results into the one map the ~300 lines of downstream availability logic already expect, and write inside ONE shared transaction looping a scoped `deleteMany` + `batchCreateMany` per instance. `plexSyncSucceeded`/`jellyfinSyncSucceeded` require the write AND *every* configured instance's fetch to have succeeded, because they gate the revert/stale-fallback checks, which need to know this run's union is a COMPLETE picture. A failed instance contributes nothing and keeps its existing rows.
    - **`TVEpisodeCache` has no `serverInstance` column** (episodes are TMDB-anchored shared data), so its rewrite accumulates across instances and runs ONCE at the end, gated on `allEpisodesFetched && writable.length === fetched.length && writable.length > 0`. **That middle term is load-bearing**: an instance whose *library* fetch failed never enters `writable` and so never gets an episode fetch at all — without it the whole-table rewrite proceeds on an incomplete union and wipes the down server's episode rows for the length of its outage. Looping delete+insert per instance is also wrong (each pass would wipe the previous one's rows).
    - **Session ids carry the instance, and the finalize ledger must respect it.** Build every `ActiveSession.id` with `activeSessionId(...)` — a single stray `` `plex:${sessionKey}` `` template literal reintroduces the collision where two servers reusing the same low-cardinality `sessionKey` fight over one row. `clearFinalizedNotInCurrentSnapshot(instance, keys)` releases only entries whose *parsed* id belongs to that instance: instance A's snapshot can never release B's ledger state (B's keys are never in A's snapshot). Absence sweeps and bootstrap reconciles are likewise scoped, or one instance finalizes another's live sessions.
    - **Auth: the membership union fails open, and an INDETERMINATE instance poisons it.** `getCachedPlexAllowlist` ([plex-membership.ts](src/lib/plex-membership.ts)) caches per slug and returns the union; a configured instance that is cold with a failing/empty fetch returns `null` for the WHOLE call (no opinion, nobody locked out) — a partial union would mass-revoke every user whose only membership is on the down server. A STALE set is not indeterminate (it serves stale, so one outage never blanks the others); an UNCONFIGURED instance contributes nothing and never poisons; and an "unconfigured" verdict must never arm the retry backoff, or honoring that cached skip after an admin finishes configuring the instance yields an *enforcing* partial union. Sign-in ([auth.ts](src/lib/auth.ts)) loops instances first-match-wins with per-instance error isolation but still fails CLOSED overall; QuickConnect's instance is pinned into the signed flow cookie at initiate time and read back from the VERIFIED cookie, never a client-supplied field; and **rate-limit keys stay unscoped by instance** so an attacker's budget can't multiply with server count.
    - **On the PLEX membership, poller, backfill and SSE paths, read config with `setting.findUnique` ONLY** — `getMediaInstances` + `getPlexConfig(slug)` + a skip-if-unconfigured `continue`, never `getSyncableMediaInstances`/`isMediaInstanceConfigured` (they issue `findMany`). This is a test-harness contract, not a style preference: those suites discriminate reads BY SHAPE — `session-refresh`'s stub defines only `findUnique`, and the poller's harness starves plex-events' reconcile by matching *any* `findMany` over **Plex** connection keys, so a shape change there opens a real SSE stream against a fetch stub or silently converts a config-guard test into an accidental exception test. The poller's **Jellyfin** arm is the deliberate exception and still calls `getSyncableMediaInstances("jellyfin")` — the starvation trap is Plex-only, and that harness's `isSyncRead` branch depends on the `findMany` reaching it. The in-code comment above the Plex arm in [sync/play-history/route.ts](src/app/api/sync/play-history/route.ts) is the authority on which arm is which; don't "unify" them.
    - **Per-instance secret Setting keys must stay encrypted.** `MEDIA_INSTANCE_SECRET_RE` in [settings-sensitive-keys.ts](src/lib/settings-sensitive-keys.ts) matches `plex<Slug>AdminToken`/`jellyfin<Slug>ApiKey` by regex (guardrail 7a) — the static list can't enumerate admin-defined slugs. It deliberately does NOT match `ServerUrl`/`AdminEmail`/`Libraries`/`*PathStripPrefix`/`RestrictSignIn`, which stay plaintext.
    - **De-registering an instance must clean up its derived rows** — `/api/admin/media-instances`'s removal path deletes that slug's `PlexLibraryItem`/`JellyfinLibraryItem`, `ActiveSession` and `UpstreamWatchEvidence` rows, its full Setting-key set and its `upstreamWatch:status:<source>:<slug>` row, inside the same transaction as the registry write, and drops the cached never-watched report. A status left behind is inherited by a server re-registered under the slug and reads `ok` before that server's first refresh, lifting the cleanup's `upstreamUnchecked` hold on evidence it never produced (guardrail 14d). Without it those library rows are unreachable by every writer (no sync path targets a de-registered slug) while still counting toward the admin dashboard, the settings library count and `/api/admin/stats`, which read them unscoped. (Since grants landed, the user-facing read path no longer shows them — the visible-instance list comes from `getMediaInstances`, which returns only REGISTERED entries, so a de-registered slug is filtered out. Don't weaken the cleanup on the strength of that: the admin surfaces above still count the orphans, and nothing else would ever remove them.) `MediaServerUser` is soft-deleted and `PlayHistory` untouched (guardrails 28/19); that kept history still gives the slug a coverage row on the never-watched page, flagged `holds: false`, which is never named as unchecked. The cleanup is not retroactive: a deployment that removed an instance before this shipped still has orphans.
    - **A RESTRICTED instance's library counts only for users granted it, and that answer must be produced in the DATA layer.** `MediaInstanceConfig.restricted` + `User.mediaServerGrants` + `canViewMediaInstance` ([permissions.ts](src/lib/permissions.ts), still a zero-import leaf) + the resolvers in [media-visibility.ts](src/lib/media-visibility.ts). Load-bearing details: grants are **service-namespaced** (`{plex:{…}, jellyfin:{…}}`) because Plex `"remote"` and Jellyfin `"remote"` are different servers with different content — do NOT copy arr's flat `instanceGrants` map, which has that collision latent; the default `""` instance can never be restricted (the byte-identical-default rule); ADMIN short-circuits; and `UNSAFE_GRANT_SLUGS` guards BOTH nesting levels on parse and serialize. **Never enforce this at the presentation layer** — `getBadgeVisibility` is a cosmetic mask and the raw payload ships the unmasked field, so a mask there leaks a restricted server's availability to anyone with devtools or the native client. `attachAllAvailability` resolves visibility internally from the `userId` it already receives (like its existing `getUserHiddenSet` read), so all 28 call sites stayed untouched; the eight surfaces that bypass that chokepoint (request POST's already-available rejection, bulk — which must use the TARGET user's grants, not the caller's — issues, votes, both Discord paths, person pages, the two detail pages) each scope their own query. **`TVEpisodeCache` is the one table that cannot be scoped** — it has no `serverInstance` column and every server's episodes accumulate into one `source` namespace, so its three read sites instead gate on whether the viewer can see some server of that type actually holding the title (`visibleEpisodeSourcesFor`/`From` in [media-visibility.ts](src/lib/media-visibility.ts)). Without that gate a plain `source IN (…)` read hands an ungranted user the restricted server's per-episode holdings as raw JSON on `/api/tv-availability` and the season route. **The `(app)/admin` subtree is deliberately NOT gated**: it admits `MANAGE_USERS`/`MANAGE_REQUESTS`/`MANAGE_ISSUES`, none of which carry the ADMIN bit, and those roles need the true global library to triage — same reasoning as guardrail 28's unscoped history/stats surfaces. Admin delegation is a trust boundary, not a visibility one. **`/popular` is a SECOND deliberate exemption, and a user-facing one.** `getMostPopularOnServer` aggregates `PlayHistory` across every server with no `serverInstance` predicate, so its ranking, play counts, viewer counts and watch hours span restricted instances for every viewer. This was audited, scoped, and then deliberately reverted: "most played on the server" is meant to answer one global question, and a viewer-relative ranking makes two users legitimately disagree about it. The consequence is accepted and is NOT a bug to re-fix — an ungranted user can infer that a restricted server holds a title and roughly how much it is watched. **Availability is still masked**: the badge beside such a title stays hidden because `attachAllAvailability` scopes normally, so the page deliberately answers "this is popular here" while refusing to answer "you can watch this". If you re-audit this file, that asymmetry is intentional. Anything NEW that exposes per-server watch data to non-admins is still covered by the rule above — this exemption is for this one aggregate, not a licence for the class.
    - **The sync-side grant filter is PRE-CAS, and that is not a style choice.** A request flips to `AVAILABLE` only when the title sits on a server *that requester* can see, and the notify follows the same gate — so the filter runs on the already-materialized candidate array before any id reaches `claimAvailableNotificationWinners`. That preserves guardrail 14 (the CAS is still the sole writer of `notifiedAvailable` and simply never sees a gated id) and guardrail 15 (the `stillPending` snapshot is still READ once — the invariant constrains the read, not filtering afterward; the marking pass has filtered per-user on `User.mediaServer` in four places since long before grants). **Do NOT use the `deactivatedAt` filter in [notify-available.ts](src/lib/notify-available.ts) as the template** — that one sits AFTER the `UPDATE … RETURNING` and deliberately BURNS the claim so a re-enabled account doesn't replay a backlog. Burning it here would mean an ungranted requester could never be notified even after being granted. A gated row keeps `notifiedAvailable = false`, stays PENDING/APPROVED, and is re-evaluated every run. The two ARR marking passes are deliberately ungated: *arr availability is a file in a root folder with no instance identity, so there is nothing per-instance to gate on.
    - **Instance-aware surfaces:** library/episode sync + the availability union, the 5s play-history poller and the Plex SSE manager map (one manager per instance), download-policy user reconcile, Jellyfin sign-in (server picker when >1) and Plex membership, both terminate-session routes, fix-match (DB row *and* the upstream call — they must agree, or you rewrite the wrong server's library with another server's ratingKey), bad-matches + admin/library path normalization (grouped per instance so one server's mount root can't collapse the other's), and per-server badges on admin library/activity/users.
    - **Still default-only by design (not gaps):** Plex reachability (`plexServerReachable` + the `plex:reachability` SSE event + the admin badge are single-server plumbing), library-scan's post-approve trigger, the webhook presence probes, and the `library-sample-paths` mount preview (default instance only — mixing instances would collapse the inferred mount to ""). Per-instance `Libraries` and `Movie/TvPathStripPrefix` are now WRITABLE from the media-instances manager; the strip prefixes have delete-on-blank semantics there (an empty-string row would shadow the `named ?? default` fallback in bad-matches/admin-library, so blank = delete the row = inherit the default server's prefix).

36. **An unconfigured media server is SKIPPED, never failed. A client must decide that BEFORE the request, not from the response.**

    Why:
    - `/api/sync/plex` and `/api/sync/jellyfin` answer `400 {"error":"<X> server not configured"}`. That is a perfectly good signal *for that one server*, but every admin control POSTed to both unconditionally and then folded the two answers into one verdict — so on a single-server deployment (which is most of them) the absent server's 400 decided the outcome. `ResyncLibraryButton` took the FIRST error and went red on a run where its one real server had just rewritten its whole library; `MasterDbFillButton` did the opposite, requiring BOTH to fail, so a genuine outage on a two-server install shipped as green.
    - The orchestrator could not express it either. `plexMarked`/`jellyfinMarked` are initialised to `0` and always serialized, so "no Jellyfin here" and "Jellyfin synced and matched nothing" are byte-identical, and `failedSources` is gated on `plexConfiguredEnabled` so it deliberately never names a server that was never attempted.

    Rules:
    - **Pass `plexConfigured`/`jellyfinConfigured` from the server component and call only what exists.** Both parents already read the settings they need ([settings/page.tsx](src/app/(app)/settings/page.tsx), [admin/library/page.tsx](src/app/(app)/admin/library/page.tsx)) — no new query. Probing an absent server and discarding its 400 is the antipattern. The booleans describe the DEFAULT instance, which is correct for these buttons because they send no `instance` slug (guardrail 35).
    - **`/api/sync` reports `skippedSources` alongside `failedSources`** — never-attempted vs configured-and-broken. Both are omitted when empty, so absent reads correctly as "none" on an older client. For *arr the predicate keys on `radarrSyncedSlugs.size`, NOT `radarrEnabled`: the flag only means "the step did not blow up", and an enabled-but-unconfigured Radarr still sets `radarrSyncSucceeded` while refreshing nothing.
    - **Red means a CONFIGURED server failed.** Nothing configured is neutral, not an error. A partial failure still refreshes — the rows that did sync are what the click was for.
    - **Never sum `plexMarked` and `jellyfinMarked`.** One marking pass, one `stillPending` snapshot, so a title on both servers is counted once by each. Report per source.
    - **One POST to `/api/sync` already syncs Jellyfin.** Its Jellyfin arm is a strict superset of a bodiless `/api/sync/jellyfin` call (full unwindowed replace over every instance, vs insert-only inside a 2-hour window on the default alone). Don't add a second call; it re-runs the whole marking pass and races the orchestrator's own delete-and-replace.
37. **NEVER build a Jellyfin series→tmdbId map from `JellyfinLibraryItemData.itemId` alone — use `buildSeriesItemIdIndex`.** This is the SAME-server, multi-*library* twin of guardrail 35 (which is about multi-*server*); the two are independent.

    Why:
    - One title legitimately sits in several libraries on ONE server (Anime vs TV, HD vs 4K, an accidental double-import). `getJellyfinItemsByType` still collapses to one **row** per tmdbId because `JellyfinLibraryItem` is keyed `@@id([tmdbId, mediaType, serverInstance])` — that collapse is correct and stays.
    - Each copy carries its OWN item id. Every episode is filed under whichever `SeriesId` its copy has, and `processEpisodes` `continue`s on an unrecognised `SeriesId`, so a map built from the surviving id dropped the other copy's **entire episode set** out of `TVEpisodeCache` — silently, presenting as "those seasons aren't in the library". A watch of the losing copy likewise resolved to no title and attributed to nobody.

    Rules:
    - **`JellyfinLibraryItem.jellyfinItemIds String[] @default([])` holds EVERY id the title occupies, `jellyfinItemId` included.** The singular column stays as the canonical id (fix-match, the upstream remap); the array is what makes the other copies addressable. Written by the sync from `libraryItemIds(data)` ([jellyfin.ts](src/lib/jellyfin.ts)); pinned structurally by `tests/schema-invariants.test.mts`.
    - **Every read ORs the two columns — never swap wholesale to `has`/`hasSome`.** Rows written before the column existed carry `[]` until a full sync rewrites them (the hourly orchestrator always full-replaces; Jellyfin's `recentOnly` path is insert-only and will NOT backfill an existing row). The four readers: `resolveShowTmdbId` ([play-history.ts](src/lib/play-history.ts)), the poller's bulk prefetch ([sync/play-history/route.ts](src/app/api/sync/play-history/route.ts)), the admin-activity backfill, and fix-match. Whenever a lookup map is keyed by item id, key it by **every** id the row answers to or widening the query just finds a row the map then misses.
    - The array needs its **GIN index** (`@@index([jellyfinItemIds], type: Gin)`) — the 5s poller runs a `has`/`hasSome` on every tick and a btree cannot serve array containment.
    - The losing copies also ride in-memory on `JellyfinLibraryItemData.duplicateItemIds`, and `buildSeriesItemIdIndex` maps every one of them. All three series-map builders go through it — [/api/sync/route.ts](src/app/api/sync/route.ts), [/api/sync/jellyfin/route.ts](src/app/api/sync/jellyfin/route.ts), and `getJellyfinTVEpisodes`'s internal fallback. Its `.values()` repeat per copy: dedupe before using them as a tmdbId list (e.g. a delete scope).
    - **Which copy becomes the stored row is `prefersCandidate` — newest `addedAt`, item-id tiebreak — NOT arrival order.** The library-scoped walk fetches folders concurrently, so plain last-write-wins let the winner (and with it the row's `itemId`, `filePath`, `addedAt` and ratings) flip between syncs. Order-independence is the whole point; don't "simplify" it back to a bare `items.set()`. The rule is also what the unscoped single-query path already did by construction (`SortBy=DateCreated` ascending + last write), so single-library servers see no change.
    - **fix-match remaps EVERY copy, serially.** All copies of a title are mismatched on the server, so remapping one left the others reporting the old tmdbId and the next library sync could elect an unfixed copy — the admin's correction silently reverted. Only a total failure aborts; a partial one still records the copies that moved and returns a `warning` naming the shortfall. Keep it serial — parallel `FullRefresh` calls are how these start timing out.

37a. **A fix-match runs as a BACKGROUND JOB with a polled status — never as a request the browser waits on.** `POST /api/admin/fix-match` with `async: true` answers 202 + `jobId` at once and the client polls `GET /api/admin/fix-match/status?id=`; the registry is [fix-match-jobs.ts](src/lib/fix-match-jobs.ts), the client half is [client/fix-match.ts](src/lib/client/fix-match.ts).

    Why:
    - A Jellyfin series identify keeps refreshing every season and episode for minutes after `RemoteSearch/Apply` returns, and the route (rightly) waits to confirm. A reverse proxy keeps one request open for ~60s (nginx, NPM) to 100s (Cloudflare), so the browser got a **502 while the remap succeeded** — the operator saw "failed", retried, and queued yet another full refresh on an already-busy server.
    - The in-process job outlives the request the same way guardrail 17's backfill does (single long-lived Node server). The status route 404s after a restart and the client tells the operator to re-sync instead of retrying.

    Rules:
    - The synchronous default (no `async`) is a **wire contract the iOS app pins** — keep it byte-identical; gate a native switch on the reported `apiVersion` (guardrail 25), never by changing the default.
    - The same key (server + instance + mediaType + from→to) already running ⇒ the same job is returned, never a second remap of one title.
    - A job's `error` is the client-safe message only — the route still logs the real detail before throwing `FixMatchError`.

37b. **Exactly one TMDB id may keep a `PlexLibraryItem` row per conflated Plex ratingKey, and WHICH one must resolve the same way on every run.** The Plex twin of 37's `prefersCandidate`. One definition — [plex-dedupe.ts](src/lib/plex-dedupe.ts) — called by BOTH writers, the orchestrator's Plex arm and the admin Resync route.

    Why:
    - Plex merges metadata bundles, so one item can claim several tmdb guids. `PlexLibraryItem` is keyed `([tmdbId, mediaType, serverInstance])`, so every candidate would become its own row pointing at the same item and nothing mapping ratingKey → title (play-history, fix-match) could answer. The losers get NO row at all — no availability badge, no `TVEpisodeCache` entry — so which one wins is user-visible.
    - The prior mapping was read as `tmdbId IN (this batch's candidates)`, which finds the pin only when the pinned title is in the CURRENT fetch. A partial fetch is routine while Plex is mid-scan — exactly when the SSE timeline handler runs the sync most often — and with no mapping found the code kept "the first occurrence" of an array filled by a concurrent section walk (`Promise.all` in `getPlexTmdbIds`). That wrote a different winner and read it back as the pin from then on. Observed live: ratingKey 473163 (four shows) pinned to tmdb 225634 for two runs and 113988 on a later one, silently swapping which show had a library row.

    Rules:
    - **Look the prior mapping up BY RATING KEY**, still instance- and mediaType-scoped (guardrail 35). Never by the batch's candidate tmdbIds — that is the pin-losing shape, and it reads as harmless because the query still returns the right row in the common case.
    - **Honour a pin only when its tmdbId is in the batch.** A pin naming an absent title drops every candidate and leaves the ratingKey with no row — which on the full-replace path destroys the pin too, so the next run starts over.
    - **Every remaining choice is a total order over the candidates, never arrival order.** That includes resolving a duplicate stored mapping: `plexRatingKey` is indexed but NOT unique and `findMany` has no defined order, so last-write-wins there is the same bug from the other side. Lowest tmdbId in both places.
    - **One definition, not two agreeing copies.** The two writers held near-identical private copies that a comment asked you to keep in sync by hand; a drift means one writer drops the row the other just wrote, on every run.
    - `tests/plex-dedupe.test.mts` pins all of it, each mutation-verified: first-occurrence order, the tmdbId-keyed lookup, an unconditional pin, and last-write-wins over the stored rows each fail a named test.

37c. **A Plex title's EVERY ratingKey on a server lives in `PlexLibraryItem.plexRatingKeys`, and every ratingKey read ORs it against `plexRatingKey`.** The Plex twin of 37 (`jellyfinItemIds`).

    Why:
    - A title in two sections ("Movies" + "4K Movies", "TV" + "Anime") is two Plex items with two ratingKeys, but `@@id([tmdbId, mediaType, serverInstance])` keeps one row and `getPlexTmdbIds` kept the first section's entry. `resolveShowTmdbId` could not resolve the other copy, so every episode play of it was recorded with `tmdbId = null` — forever — and the never-watched report called a watched show unwatched; a movie's 4K copy's server-side history matched nothing.

    Rules:
    - Written by both Plex writers (orchestrator arm, `/api/sync/plex`) from `plexLibraryRatingKeys(data)` — canonical key first, then `duplicateRatingKeys` collected across sections, within a section, and from legacy-agent resolution (`withDuplicateRatingKeys`, which NEVER mutates: one entry object is shared by every tmdb id a conflated item claims).
    - **`plexRatingKeys` is NEVER made exclusive on write.** A conflated item's key also rides the array of every title it claims whose clean copy sits in another section, and it stays there: the never-watched evidence join (14d) credits a play, upstream record or session of that key to EVERY title answering to it, and a write-side strip (the reverted `withExclusiveRatingKeys`) turned a watched title into a false "never watched" on a list that feeds a delete. `tests/audit-fix2-R7-watch-nav-activity-nw.test.mts` runs the writer's output through the loader.
    - Readers OR both columns (rows written before the column carry `[]` until a full sync): `resolveShowTmdbId`, the poller's movie prefetch, the admin-activity backfill, the never-watched evidence join. A lookup map is keyed by EVERY key a row answers to. A key held by several rows resolves through `pickPlexRowForKey` / `indexPlexRowsByKey` ([plex-dedupe.ts](src/lib/plex-dedupe.ts)) — the canonical holder, else the lowest tmdbId (37b's total order); the ONLY place one owner is picked — NEVER a `findFirst` without an order, and never last-write-wins in a key map (the 37b rule on the read side). The never-watched evidence join is the deliberate exception: it credits EVERY title a key answers to (14d — a lenient verdict leans the safe way for a delete).
    - GIN-indexed; `tests/schema-invariants.test.mts` and `tests/plex.test.mts` pin it.

38. **`'unsafe-eval'` in the CSP is gated on `NODE_ENV === "development"` and NEVER widens. Don't delete the branch either.**

    Why:
    - React's development build calls `eval()` to reconstruct server-side error stacks in the browser, and Turbopack's HMR runtime evaluates modules the same way. Without the carve-out every `next dev` page logged *"eval() is not supported in this environment"* and those debugging features were dark — a permanent console error that trains people to ignore the dev console, which is the only place dev-only hydration **warnings** ever surface (guardrail 16a).
    - Widening it is a real vulnerability, not a lint nit: `'unsafe-eval'` makes any string reaching `eval()`/`new Function()` executable, which is most of what the per-request nonce + `'strict-dynamic'` policy exists to prevent. Production is the response an attacker can reach.

    Rules:
    - The condition lives inline in [src/proxy.ts](src/proxy.ts)'s `cspValue`. `next build` sets `NODE_ENV=production`, so Turbopack constant-folds the branch away — the string is **absent from the production bundle**, not merely false at runtime. Verify that way (`grep unsafe-eval` the built `.next/server/chunks/*.js`), not by reading the source.
    - `tests/proxy.test.mts` pins BOTH directions (development grants it; `production`/`test`/unset never do). A one-sided pin would be satisfied by a hardcoded constant — keep both.
    - Next's CSP guide documents this exact carve-out and states neither React nor Next uses `eval()` in production. `style-src` needs no dev branch here: it is already `'unsafe-inline'` in every environment.
    - [SECURITY.md](SECURITY.md) describes the **shipped** posture. It stays accurate only while this branch is dev-only — if that ever changes, that file changes with it.

39. **A new `tw-merge` group goes BEFORE the catch-all it narrows, and `npm run audit:tw-merge` must stay green.**

    Why:
    - [tw-merge.ts](src/lib/tw-merge.ts) decides which utilities conflict from a hand-maintained table of prefix regexes, and `groupOf` returns the FIRST match. A group placed after the catch-all it was meant to narrow is unreachable, and a catch-all that swallows a *different* CSS property silently deletes one of the two classes.
    - The failure is invisible: both classes are real, the merged string still looks plausible, and nothing type-checks or lints differently. It has shipped visibly twice — `ui/drawer.tsx`'s DrawerPopup lost `border-t` to the border-colour catch-all, and `ui/avatar.tsx`'s AvatarBadge lost `bg-primary` to `bg-blend-color`. One full audit against Tailwind 4.3.3's 23,286 utilities found 20 more of the same shape.
    - The table is also v3-shaped wherever nobody has looked: Tailwind renames (`bg-left-top` → `bg-top-left`) and additions (3D `rotate-x/y/z`, `transition-behavior`, `-safe` alignments) do not announce themselves.

    Rules:
    - **Order is load-bearing** — specific before catch-all. `["bg-blend", /^bg-blend-/]` must precede `["bg", /^bg-/]`.
    - **Constrain the value shape when the prefix is an ordinary word.** `inset-s`/`inset-e` require `-\d`, `-[` or a known keyword. A bare `/^end-/` merged the prose `end-credits` with `end-to-end`.
    - **An arbitrary value's GROUP is decided by its value shape, exactly as Tailwind types it — through the shared fragments at the top of [tw-merge.ts](src/lib/tw-merge.ts) (`LEN`, `WIDTH_ARB`, `COLOR_LIT`, `SHADOW_ARB`), never a hand-written `-\[` in a group regex.** Tailwind compiles `border-[var(--x)]` to `border-color` but `border-[2px]` to `border-width`, `text-[var(--x)]` to `color` but `text-[10px]` to `font-size`, `shadow-[var(--x)]` to the SHADOW but `shadow-[red]` to its colour, and every `divide-x-[…]` to the width. A regex that treats any `-[` as one kind files the other kind wrong, and the wrong one silently deletes its neighbour: `border border-[var(--ds-border)]` lost `border` in every `StyledSelect` (0px, 24 sites) and `text-xs text-[var(--ds-accent-fg)]` lost one class on accent Buttons. Three rounds of hand-patched regexes each fixed the reported case and broke another corner. `npm run audit:tw-merge` check 4 (MISFILED) now compiles a matrix of arbitrary values plus every arbitrary token in `src/` through Tailwind and fails on any value a group files unlike the named utility it compiles like — the committed table before this rule failed it 223 times. Add a family to `ARBITRARY_FAMILIES` in the auditor whenever you add a size/colour split.
    - **Utilities that COMPOSE get one group EACH, never a shared one.** Each backdrop filter and each font-variant-numeric toggle contributes its own `--tw-*` var to one shared value, so a single `backdrop`/`fvn` group deletes half the effect — the same over-merge bug from the other direction.
    - **A group whose NAME can equal a real class is a trap.** Unknown classes fall back to keying by their own string, so bare `ring` merged with ring colours only because the catch-all group happened to be *called* `ring`. Renaming it would have silently broken that; `matchGroup` (null when nothing matched) is what the auditor uses to tell the two apart.
    - **Legitimate same-family collapses are allowlisted with a reason** in [scripts/audit-tw-merge.mts](scripts/audit-tw-merge.mts) — a reset (`ease-initial`) or one shorthand spelled two ways (`bg-linear-*` vs `bg-conic`). Adding an entry is a claim that the utilities cannot meaningfully apply together; read the emitted CSS first.
    - The auditor derives everything from Tailwind's own design system, so it needs no maintenance on upgrade — it re-derives and reports. If Tailwind drops `__unstable__loadDesignSystem` it fails loudly rather than auditing an empty set. Checks 1–3 enumerate `getClassList()`, which contains NO arbitrary values; only check 4 covers `[…]`/`(…)` forms, and only for the families it lists.

    ```bash
    npm run audit:tw-merge            # blocking in CI
    npm run audit:tw-merge -- --list  # show the allowlisted findings and why
    ```

    **Run it bare, never piped** — a pipe reports the last command's exit code, the same trap as `generate-licenses.mts --check`.

40. **"For You" per-title data is SERVER-WIDE, and it is the ONLY source. The engine makes no upstream call at all — the SCHEDULING is what makes that safe.**

    Why:
    - A seed's suggestion list and a candidate's quality verdict are properties of the TITLE — byte-identical for every account — and the engine used to re-derive both *inside each user's pass*: one `<type>:<id>:suggestions:v3` blob read per seed (a live TMDB call on any miss) plus a 300-title MDBList/OMDB pass, per user, per cycle. Two accounts that watch the same show paid for the same fan-out twice, and the first account of each cycle paid the cold-cache cost for everybody. Cost scaled with USERS × SEEDS for work whose answer never varies by user.
    - `TitleSuggestion` (the edges) + `RecommendationTitle` (the per-title node: refresh bookkeeping + the verdict) are built once for the whole instance by `refreshRecommendationGraph` ([recommendation-graph.ts](src/lib/recommendation-graph.ts)).
    - A live fallback shipped briefly and was removed deliberately. It could not be *correct* — a fallback fires exactly when the build failed, which is exactly when the same upstream is failing — so it bought nothing an outage did not already take, while making the engine's cost unbounded and its failure modes invisible. What replaced it is an ordering guarantee, not a retry.

    Rules:
    - **The order is the guarantee: SELECT, then BUILD, then COMPUTE.** `warmRecommendationsCache` resolves every active user's `selectSeedPlan` FIRST, passes the union of those seeds to `refreshRecommendationGraph({ required })`, and then computes each user **from the same plan object**. The required set is therefore not a prediction of what will be read — it is the literal set. Do not re-select seeds inside the compute phase (a watchlist add landing between build and compute would reintroduce exactly the gap this removes), and do not move the build after the fan-out.
    - **A seed cap IS a build-budget knob — changing one changes what the build must cover.** The required set is the union of every user's seeds, so `MAX_WATCH_HISTORY_SEEDS` / `MAX_WATCHLIST_SEEDS` / `MAX_REQUEST_SEEDS` set the per-user ceiling that arithmetic runs on: currently **348** (300 history + 24 watchlist + 24 request). What a raise does NOT do is grow the graph — every watched title was already a source through `collectGraphSources` — it moves titles from the capped speculative tail into the uncapped must-build-now tier, so the bill lands on a cold graph and at the 7-day TTL roll rather than every run (a source refreshes once per 14 runs at the 12h cadence). Three ceilings have to be re-checked against any change: `MAX_REQUIRED_SOURCES` (50k, which at 348/user binds around 144 zero-overlap users, and which is a WALL-CLOCK bound — see its comment), `MAX_GRAPH_SOURCES` (total edge-bearing sources, unaffected by tiering), and `MAX_QUALITY_TITLES_PER_RUN` (10k, spent priority-first — more required sources means proportionally more suggestion targets competing for it, so verdict convergence slows by roughly the same factor).
    - **The required set is built WITHOUT the per-run cap.** `MAX_SOURCES_PER_RUN` governs only the speculative walk of library titles nobody seeds from yet, which can be starved indefinitely at no cost. Capping the required set would be capping the guarantee. Its own ceiling, `MAX_REQUIRED_SOURCES`, is a runaway guard and exceeding it is a `console.error`, never a silent truncation.
    - **`conclusive` is derived from SEED COVERAGE, not from whether anything came back.** Full coverage is authoritative *even when the answer is empty* — the graph distinguishes "TMDB has nothing similar" (a covered source with no edges) from "not built" (no node stamp), so a covered-empty result may clear a shelf. Below full coverage the answer may only replace a stored shelf if it clears `SEED_COVERAGE_FLOOR` (0.8) AND produced something. Not 1.0, deliberately: one permanently-failing source would otherwise freeze that user's shelf forever. This also closes the older documented gap where a single answering seed was enough to fully replace a shelf during a partial outage.
    - **A graph refresh that THROWS aborts the run.** Computing anyway would be thousands of queries whose only possible outcome is no change (zero coverage ⇒ inconclusive ⇒ every shelf kept). It returns `graphFailed`, the cron records `ok: false`, and every stored shelf is left untouched.
    - **Coverage is the NODE STAMP (`suggestionsRefreshedAt`), never the presence of edges.** A title TMDB has no suggestions for writes zero edges; judged on edges alone it would look uncovered forever. `readGraphSuggestions` returns an explicit empty list for such a source, which is why it reads the node table as well as the edge table.
    - **`RecommendationTitle` has TWO distinct null states and they are not interchangeable.** `qualityRatedAt == null` ⇒ never rated ⇒ **no opinion, no obscurity damp, score untouched**. `qualityRatedAt != null && quality == null` ⇒ asked, and not one provider answered ⇒ the damp fires. Collapsing them now penalises every title the ratings pass has not reached yet — most of a young instance's catalogue — because nothing rates a candidate on demand any more.
    - **The stored verdict is deliberately TMDB-FREE; re-blend the TMDB term per candidate with `withTmdbTerm`** ([recommendation-quality.ts](src/lib/recommendation-quality.ts)). `qualityScoreOf` gates that term on a vote count belonging to the CANDIDATE row, so baking a guess into a verdict every viewer shares would be wrong for all of them. The graph rates with `voteAverage: 0, voteCount: 0` — exactly "TMDB abstains".
    - **Verdicts are resolved PRIORITY-FIRST over the required set's own suggestion targets**, then the general oldest-first scan spends what budget is left. An unrated candidate ranks on relevance alone until some run reaches it, so which titles the budget buys is now a user-visible decision, not bookkeeping.
    - **Never stamp a VERDICT from a failed lookup either, and clearing a cache must reach the copies.** Two corollaries of the rule above, both of which shipped broken. (a) `attachRatingsUnified` swallows its own upstream failures, so it returns the full item list whether the lookup worked or not — the verdict writer's try/catch never fires for a transport failure, and every title got a null verdict stamped for a full `QUALITY_TTL_MS`, which the obscurity damp then reads as evidence. A null verdict is only written when the providers were reachable at the end of the batch; a real verdict is always written. That check is why the OMDB **transport circuit breaker** ([omdb.ts](src/lib/omdb.ts)) is load-bearing rather than tidy — every `tripQuotaLockout` site needs a RESPONSE, so an unreachable host tripped nothing and the flag this reads stayed false exactly when it mattered. (b) `TitleSuggestion` and `TmdbMediaCore` hold denormalized copies of data the admin cache-clear empties, and are read without ever consulting `TmdbCache` — so `DELETE /api/admin/clear-cache?source=tmdb` resets them too, and `source=mdblist|omdb` resets the stored quality verdicts. **The unstamp must precede the edge delete, in one transaction**: edges gone while the node still says refreshed reads as *covered with no suggestions*, which is authoritative, which replaces every shelf with a fallback one — strictly worse than not clearing at all. `UserRecommendation` is never cleared; the next warm run rebuilds it.
    - **Never stamp a source from an INCONCLUSIVE page.** `getMovieSuggestions`/`getTVSuggestions` swallow upstream failures and return `[]`, so a zero is ambiguous — and a stamped zero serves "no suggestions" to every user for a week. The edge writer applies the same conclusiveness test at page granularity: one source in the page answering with anything proves TMDB is up and makes a neighbour's zero a real answer; a page where nothing came back is written nowhere and retried next run.
    - **The warm-library cron pre-builds the same edges, and that is an ACCELERANT — never a substitute for the required build.** `prewarmSuggestionEdges` ([recommendation-graph.ts](src/lib/recommendation-graph.ts)) runs inside the `warm-library` cron, beside the metadata walk that already visits every library title, and writes to the same `TitleSuggestion` table. It exists only to change WHEN: left to the recommendations run, the speculative tier is capped at `MAX_SOURCES_PER_RUN` and a 20k-title library takes ten runs (five days) to cover, whereas the library cron owns its own daily run and can spend `MAX_PREWARM_EDGE_SOURCES_PER_RUN`. It also reaches sources a required set structurally cannot — an INACTIVE user's history, since the required set is built from active users' seeds only.
      **NEVER gate the required build on it.** `refreshRecommendationGraph` must keep building the required set uncapped on every recommendations run; a prewarm that already covered a title simply makes that build find it TTL-fresh and do nothing. The prewarm is capped, runs on a different schedule, and can fail on its own, so "the library cron warms the graph, so the recommendations run can trust it" is exactly the optimisation that reintroduces the gap the fallback removal closed. Pinned by a named test.
      The two passes can be in flight together and both write `TitleSuggestion`. Accepted rather than serialized: the shared TTL triage makes an overlap on the same source rare, writes are scoped per source page, and a page that loses a lock race fails alone and retries next run — whereas a shared lock would let a long library walk block shelf refreshes outright.
    - **The trending/popular pool is warmed by the refresh, not by the first user.** `buildFallbackCandidates` reads those lists during the compute; they are instance-wide coalesced caches rather than per-user work, but on a cold one the first user of a cycle would still pay for the fetch. `warmFallbackPool` reads them in the refresh, immediately before the fan-out — same ordering guarantee, applied to the one remaining read in the compute path.
    - **A source that leaves the server has its edges swept.** Nothing else would ever reach them. The sweep clears the node's source bookkeeping (making it idempotent) but KEEPS the node and any verdict — the title can still be somebody else's suggestion. It runs only on a complete source list, and the required set is unioned into "live" so a truncated library walk can never make a real seed look departed.
    - **What scheduling genuinely cannot cover, and is accepted:** a source whose TMDB fetch *fails during the build* stays uncovered, and its seed contributes nothing that cycle. There is no arrangement of the schedule that fixes this — the fallback that used to "cover" it re-tried the same failing endpoint from the same process seconds later. The protection is `conclusive`, not a retry: a materially incomplete seed set is refused the right to replace a good shelf, and the next run rebuilds.
    - `tests/recommendations.test.mts` pins all of the above, each mutation-verified: building without the required set, reverting `conclusive` to the any-suggestion rule, letting a graph throw proceed to the fan-out, capping the required set, dropping the pool warm, dropping the node probe, dropping `readTitleQuality`, neutering `withTmdbTerm`, stamping an inconclusive page, sweeping without regard to the live source set, and reading a source-only node as a verdict each fail a named test.

40a. **Every cached TMDB payload is ENGLISH. Another language is a display-time OVERLAY (`localizeMedia`, [tmdb-localize.ts](src/lib/tmdb-localize.ts)) — NEVER add `language=` to a fetch whose result lands in a shared cache key.**

    Why:
    - Every TMDB cache — list keys, `<type>:<id>:details`, `TmdbMediaCore`, the 40 graph — is shared by every viewer on the instance. A `language=` fetch written under one of those keys serves whoever warmed it first to everyone after, so a French viewer's visit would turn an English user's home page French until the TTL rolls.
    - English text is load-bearing downstream. A request stores `verifyTmdbMedia`'s title (and admins, notifications and the *arr pushes read it); the ratings pipeline, search matching and the recommendation graph all read the English rows. Keying every cache by language instead would multiply all of them by the languages in use.
    - One TMDB call (details with `translations,images` appended, posters filtered by `include_image_language`) answers EVERY language, so an overlay costs one extra fetch per title per 30-day TTL however many languages its viewers use.

    Rules:
    - Lists get localized at the `attachAllAvailability` chokepoint (it resolves the viewer's language from the request with `getContentLocale()`, exactly like guardrail 35's visibility); a page that renders a TMDB title WITHOUT that chokepoint calls `localizeMedia(items, locale)` itself (the two detail pages do). Only title / overview / tagline / posterPath / originalTitle / genres / genreList are copied back by the merge in attach-all, so the overlay can never clobber enrichment. Person pages localize the biography and their credits inside `getEnrichedPerson`.
    - **English is a no-op that returns the input array** — no DB read, no fetch. Outside a request scope `getContentLocale()` is English, so unit tests and cron helpers never touch the overlay. Keep both properties; `tests/tmdb-localize.test.mts` pins the first.
    - The overlay **never throws and never blocks past `MISS_BUDGET_MS`**: a cold title shows English on that view while its fetch finishes in the background (coalesced on the cache key, at most `MAX_IN_FLIGHT` process-wide — guardrail 31). An untranslated title caches `{}` so it isn't re-fetched every view.
    - The two places that DO send `language=` write a key that NAMES the language: `genres:<type>:<tag>` and `tv:<id>:season:<n>:<tag>`. The un-suffixed key is always English. A new localized read follows that shape.
    - The detail pages map genre NAMES back to ids for their links, so they must fetch the genre list in the same language the overlay renders (`getMovieGenres(tmdbLanguageFor(locale))`) or every chip loses its link.
    - **Country names: TMDB's `production_countries[].name` is authoritative and the English page renders it unchanged; another language is translated through Intl ONLY via `localizedProductionCountry` ([tmdb-types.ts](src/lib/tmdb-types.ts)), which keeps TMDB's English name for a code Intl cannot name (`XC` Czechoslovakia, `XG` East Germany) or has re-targeted at a successor state (`SU`→Russia, `YU`→Serbia; detected with `Intl.getCanonicalLocales`). `regionName`/`languageName` return `null`, never the bare code — put the fallback behind `??` at the call site.** A Soviet film read "Russia" and a Czechoslovak one "XC" on the English page when the pages called `regionName` directly.
    - Native clients get the instance default (`localeForHeaders`, the same rule as API messages — guardrail 25's coarse contract is unaffected: the overlay changes strings, never fields).
    - **Stored data stays English; each SENDER localizes the title for the language its message is WRITTEN in, at send time, never written back.** `MediaRequest.title`, `Issue.title` and `IssueGrab.title` are always TMDB's English. Every email/push/Discord sender takes the title plus its `tmdbId`/`mediaType` and resolves it with `titleResolver` over its recipients' languages (one translation read per message, zero for an all-English recipient set). The language is the message's, not the requester's: a Discord post to the SHARED notify channel is written in the instance default, so its title is too — localizing at a requester-level chokepoint instead put a French title inside an English channel embed (`tests/discord-notify.test.mts` pins it, mutation-verified). The in-app inbox stores English and is localized at READ time from the row's `tmdbId` (`localizeStoredTitles`, both readers), so it follows the reader's current choice. A title with no TMDB identity (the *arr manual-interaction push names a release) stays as given. A test suite exercising a non-English recipient with a `tmdbId` MUST shadow `tmdbCache` (`tests/email.test.mts`/`tests/push.test.mts` seed `movie:<id>:i18n:v2` rows like `tests/discord-notify.test.mts`), or `titleResolver`'s catch silently turns a real-DB connection attempt into an English title and the path has no pin.
    - **The iCal feed reads cached translations ONLY** (`cachedLocalizedTitles`) — every subscriber's calendar app polls it, so it must never reach TMDB per poll (the feed's own rule). The daily `warm-library` cron fills those rows with `prewarmTitleTranslations` (requests and watchlists first, then the library; `MAX_PREWARM_PER_RUN`, signal-aware per guardrail 41) and is a ZERO-fetch no-op unless `nonEnglishInUse()` — the instance default, an active account's stored choice, or a `contentLocaleSeen:<locale>` Setting stamped within 30 days is not English. The overlay writes that stamp when it serves a language (at most every 12 h per language per process — a page view must never cost a write), which is the only trace a browser-negotiated viewer with no stored choice leaves.
    - Collection names come from `/collection/<id>/translations` (`collection:<id>:i18n:v1`). Season names are NOT fetched — that would be a TMDB call per season — so the client renders TMDB's generic "Season N"/"Specials" from the catalog and keeps a real season name as TMDB has it. Character names and backdrops are deliberately English: TMDB has no character translations, and the default backdrop is text-free artwork a language-tagged one would only add burned-in text to.
    - A language-tagged poster is chosen per locale by vote; a poster tagged with a region must match one of the locale's tags, and a region-less Chinese poster is NEVER used for `zh` (the script can't be told — Traditional posters would leak into Simplified).

41. **A `withAdvisoryLock` callback that can run for minutes MUST observe its AbortSignal.**

    Why:
    - `withAdvisoryLock` races the work against a `DEFAULT_WORK_TIMEOUT_MS` (30 min) timer. On expiry it calls `controller.abort(err)`, rejects, and **releases `pg_advisory_unlock` in its `finally`** — but it cannot kill a promise. Work that ignores the signal keeps running with no lock held.
    - The route then throws, the entrypoint's `_cron_next` reschedules at `CRON_RETRY_INTERVAL` (300s), and the next run acquires the now-free lock and starts a SECOND copy alongside the first. The lock provides no protection at all against this — it was released.
    - Observed live: OMDB timing out at 10s/request made `prewarmOmdbCache` a ~6-hour walk over an 11k library. It blew lock 2004, orphaned itself, and respawned roughly every 2100s. The Prisma pool is `max: 5` ([prisma.ts](src/lib/prisma.ts)), and each orphan runs 5 concurrent fetch-and-store chains — so a single one can monopolise it. That is what surfaced as `Transaction API error: Unable to start a transaction in the given time` on unrelated paths.

    Rules:
    - Take the signal as the callback's first parameter (`withAdvisoryLock(ID, async (signal) => …)`) and thread it into the long-running helper. `prewarmLibraryCache`, `prewarmMdblistCache`, `prewarmOmdbCache`, `prewarmSuggestionEdges` and `refreshRecommendationGraph` all take `{ signal }`.
    - Check it at the loop's existing batch boundary and **`break`** — cheap, and it bounds the overshoot to one in-flight batch. `prewarmLibraryCache` checks per ITEM rather than per page, because its page buffer only flushes every `LIBRARY_PAGE_SIZE` items and a per-page check would keep fetching for hundreds past the abort.
    - **RETURN, never throw, on abort.** `withAdvisoryLock`'s `Promise.race` has already settled on the timeout rejection, so a throw becomes an unhandled rejection. The partial result is discarded by the race; stopping is the entire point.
    - The admin-triggered warms share the same lock ids as their crons, so they need the same treatment — they have exactly the same orphan exposure.
    - **The sync orchestrator is the same rule with a worse consequence, and its check goes at ARM boundaries ONLY.** A run past 30 minutes continued lock-free while the next SSE trigger — polling every 30s by then — acquired the freed lock and started a SECOND concurrent full library sync, i.e. two delete-and-replace passes over the same tables (guardrail 13). `windDownBefore(arm)` gates the Radarr, Sonarr, Plex-library and Jellyfin-library arms. It must NEVER go inside a `$transaction`: Prisma 7's `$transaction(fn, opts)` takes no AbortSignal, so a mid-transaction bail is not expressible, and stopping between a scoped `deleteMany` and its repopulate is far worse than running long. Skipping an arm needs no new downstream handling — its `*SyncSucceeded` flag stays false, which is exactly the state a failed fetch produces and exactly what already gates the revert, re-push and stale-fallback paths. Pinned STRUCTURALLY (`tests/sync-orchestrator-route.test.mts`) because the abort is a 30-minute real timer with no seam to shorten.
    - **The SSE lock-race retry is count-bounded too** (`MAX_RESYNC_SKIP_RETRIES`, [plex-events.ts](src/lib/plex-events.ts)). The re-arm is rate-bounded at one probe per debounce window but was not count-bounded, so a long run was shadowed by a 30-second poll for its entire duration — and each probe reaches `pg_try_advisory_lock` through a dedicated `new Client()`. Past the cap it falls back to the cooldown floor; the resync is deferred, never dropped.

42. **Every colour in UI code must survive BOTH themes and all six accents. NEVER write `text-white`, `bg-white`, a raw hex, or an `oklch(1 0 0 / …)` tint on a surface; NEVER re-add `cursor-pointer` to a `<button>`.**

    Why:
    - The app is dark by default, so dark-only colours ship invisibly. The legacy remap in [globals.css](src/app/globals.css) retargets an EXPLICIT list of shades at DS tokens — `zinc-100…950`, `indigo-300…800`, `red-400/500/600`, `green-400/500/600`, `emerald-400/500`, `amber-400/500`, `orange-400/500`, `yellow-400/500`, `sky-400/500`, plus `purple-400` in LIGHT only (the Jellyfin identity colour as text) — and NOTHING else. Every other shade (`red-200/300/700`, `green-300/700`, `sky-300/700`, `indigo-100/200/900/950`, `zinc-50`, `*-900/50` chip fills, …), every other hue (`blue-*`, other `purple-*`, …), `white`, `black` and raw hex are NOT remapped and render the same in both themes. Grep the `--color-*` lines in the remap section before trusting a shade. A 2026-09 sweep found ~230 `text-white` sites: every form field a user types into (report issue, vote reason, issue reply, Discord link), the error-page headings and the filter selects were white-on-white in light mode.
    - `zinc-700`/`zinc-800` are SURFACE tokens (`--ds-bg-3`/`--ds-bg-2`). As `border-zinc-*` they drew invisible borders — a bg-2 divider on a bg-2 card, and pure white in light mode — so those border utilities are retargeted at `--ds-border` by a class-selector rule in the remap section (an unlayered rule beats Tailwind's `@layer utilities`). Beating the layer is double-edged: it also beats state VARIANTS on the same element, which silently killed every `focus:border-indigo-500` / `hover:border-red-500/50` / `aria-invalid:border-*` beside a `border-zinc-700` (keyboard focus went invisible on inputs with no ring). The rule therefore steps aside while the element is in a state it carries its own border variant for (`:not(:is([class^="focus:border-"], [class*=" focus:border-"]):focus, …)`), and hands hover back with `border-color: revert-layer` **only inside `@media (hover: hover)`** — Tailwind 4 gates every `hover:` variant on that query, so an ungated hand-back left touch devices' sticky `:hover` with no border at all. Variant detection is ANCHORED to a class boundary (`^=` / leading space): a bare `*="hover:border-"` also matched `group-hover:`/`peer-hover:`/`dark:hover:`/`sm:hover:` and handed back to the surface-coloured utility whenever that prefixed variant was inactive. The legacy `hover:border-zinc-500…800` shades are themselves retargeted (to `--ds-border-strong` — as raw utilities they resolve to a SURFACE token and fade the border on hover) and yield to focus. Specificity is (0,4,0), (0,4,0), (0,5,0) and ORDER decides the tie; the comment above the rules in globals.css spells it out. Extend the `:not()` list if you add a new state variant family. `divide-zinc-700/800` had the same surface-as-border bug one level down and is retargeted beside it.
    - shadcn's `--primary` pair used to be a neutral white/black pill, so ~100 `<Button className="bg-indigo-600">` sites kept `text-primary-foreground` = near-black labels on the accent in dark mode (verified live on the Settings Save buttons). `--primary`/`--primary-foreground` now map to `--ds-accent`/`--ds-accent-fg` under `[data-theme]`; `indigo-500` is the hover shade (`hover:bg-indigo-500` on a `bg-indigo-600` element was a no-op while both resolved to the same token).
    - Tailwind v4's preflight leaves `<button>` at `cursor: default`; a base rule in globals.css restores the pointer for every enabled button, `[role="button"]` and `summary`.
    - Each status token is tuned against EVERY surface it actually sits on as text — `--ds-bg…bg-3` AND its own 5–20% tint chip (`text-green-400` on `bg-green-500/20`, the binding case) — not just the page background. Light: success/info L .46, warning/danger L .48 (worst case 4.6–4.8:1). Dark: danger L .73 (it was .65, i.e. 3.99:1 on its own 20% chip); the rest already passed. Two review rounds tuned against the page background alone and shipped values that failed on the chips.
    - No fixed text colour works on a status fill in both themes: white on the DARK-theme fills is 2.0–3.0:1 and black on the LIGHT-theme fills 3.0–3.3:1. So every status fill — warning included — takes `--ds-on-status` (dark in dark, white in light; 6.4–9.6:1). Compute contrast with real oklch→sRGB→WCAG maths (alpha tints composited in sRGB); an `L³` shortcut shipped a 4.45:1 as "passing".

    Rules:
    - Text on a surface → `text-zinc-100` (→ `--ds-fg`), `text-zinc-400` (muted), `text-zinc-500` (subtle), or an inline `var(--ds-fg*)`. Text on an accent background → `text-[var(--ds-accent-fg)]` (amber/emerald/cyan have a dark foreground and indigo/rose a white one in BOTH themes, and mono flips — dark in dark mode, where `#fff` is invisible, white in light — so a fixed text colour is wrong for some accent). Text on a solid REMAPPED status fill (`bg-red/green-400…600`, `bg-emerald-400/500`, `bg-amber/yellow/orange-400/500`, `bg-sky-400/500`, any `--ds-danger/success/warning/info`) → `text-[var(--ds-on-status)]`. On a fill that is NOT remapped the fill is a fixed colour, so the text is fixed too — pick by that colour's own contrast (`bg-purple-700`/`bg-red-800` → `text-white`; `bg-yellow-600`/`bg-amber-600` → `text-black`, since white there is 2.9–3.2:1). `text-white` is otherwise legitimate only over a poster/backdrop scrim. This includes `<Button>`s: overriding a Button's background without a text class leaves the accent foreground, which is near-black under amber/emerald/cyan, and under mono in dark mode. Accent-as-text is `--ds-accent-text`, never `--ds-accent` (see the two-token rule below).
    - Provider brand colours are FILLS: `--ds-plex` / `--ds-jellyfin` as text are 2.0 / 2.5:1 on the light surfaces. Brand-coloured TEXT → `var(--ds-plex-text)` / `var(--ds-jellyfin-text)` (the raw brand in dark, L .50 / .48 in light). Text ON a jellyfin fill is black (white is 2.9:1).
    - Tinted status chips are `bg-<status>-500/10…20` + the remapped `text-<status>-400` — never `bg-*-900/40…50` or `bg-*-950/30` (a dark chip on a light page; the text tokens were tuned against the 500 tints, 3.1–3.6:1 on the dark ones). And never an opacity modifier on status TEXT (`text-red-400/70` is 4.4:1 light, 3.5:1 dark).
    - Translucent tints → `color-mix(in oklab, var(--ds-fg) N%, transparent)`, never `oklch(1 0 0 / N)` or `rgba(255,255,255,…)` (invisible on the light theme). Borders → `var(--ds-border)` / `var(--ds-border-strong)`.
    - A hover shade must be a DIFFERENT colour from the base AND move AWAY from the text colour in both themes. `bg-red-600 hover:bg-red-500` is a no-op (both are `--ds-danger`); an opacity step (`/85`) blends toward the PAGE, which under white light-theme text is toward the text, spending contrast margin the token tuning above depends on. Solid danger fills hover to `hover:bg-[var(--ds-danger-hover)]` (lighter in dark, darker in light — 7.7/8.6:1). An opacity step is acceptable only with headroom to spare, checked in both themes (`bg-amber-600 text-black hover:bg-amber-600/90`: black stays ≥5.4:1 either way).
    - Hover on a control whose background is set INLINE → the `.ds-hover-tint` class (inset-shadow tint + focus-visible ring; it already skips `:disabled` and `[aria-disabled="true"]`). A CSS `:hover { background }` cannot beat an inline style, which is why the hand-rolled pills had `transition-colors` with no hover for two years.
    - A bare `<Button>` IS the accent button now; don't add `bg-indigo-*` overrides to new call sites.
    - **The accent has two tokens: `--ds-accent` is a FILL (under `--ds-accent-fg`), `--ds-accent-text` is the accent as TEXT or an ICON on a surface.** One value cannot do both — indigo needs L ≤ ~.57 under a white label and L ≥ ~.65 as text on `--ds-bg-3`, and light mode's bright amber/emerald/cyan fills were 1.8–2.4:1 as text on white. So `color: "var(--ds-accent)"` / `text-[var(--ds-accent)]` is always wrong; `text-indigo-300/400` already resolve to the text token. Bars, chart strokes, dots and `background`s stay on `--ds-accent`. A new accent needs all four of fill / hover / fg / text, plus a `[data-theme="light"]` text override, measured as the comment above the `[data-accent]` blocks in globals.css describes (label on fill AND hover; text on bg…bg-3 AND on its own 14%/20% tint).
    - `hover:text-[var(--ds-accent-fg)]` belongs only on an element whose background is the accent. On a surface (`bg-zinc-800`) it is white-on-white in light mode and near-black-on-dark under the dark-foreground accents — use `hover:text-zinc-100`.
    - Loading skeletons fill with `var(--ds-bg-3)` (bg-2 is white in light mode) and mirror the page's real grid (`.ds-media-grid`, card bodies, control rows) — see [poster-grid-skeleton.tsx](src/components/loading/poster-grid-skeleton.tsx).
    - Empty states are one component, `EmptyState` from `@/components/ui/design` (icon + title + description + cta). The children-only `ui/empty-state.tsx` was deleted; don't recreate it.

## Working principles

Guardrails above are *what the code should look like*. These are *how to approach changes* — process rules adapted from a sibling project. They matter disproportionately in this codebase because Summonarr is an API-juggling aggregator: five upstream services (Plex, Jellyfin, Radarr, Sonarr, TMDB), multiple cache tables mirroring them, and a sync orchestrator that mutates shared state from several paths.

### Writing future rules in this file

1. **Absolute directives** — lead with `ALWAYS` or `NEVER`.
2. **Why first** — one to three bullets on the failure mode before the fix.
3. **Concrete commands or code** — no abstractions where a shell command will do.
4. **One point per block** — don't bundle unrelated examples.
5. **Bullets over paragraphs.**
6. **Attach to a topic; don't join the queue at the tail** — see numbering below.

Use ❌/✅ examples only when the antipattern is subtle. Do not add "warning signs" sections to obvious rules.

#### Numbering — a guardrail id is a permanent address

**NEVER renumber an existing guardrail.** ~710 comments across `src/`, `tests/` and `scripts/` cite rules by number (`guardrail 23`, `guardrail 6b`), and merged commit messages cite them too and can never be edited. Renumbering silently repoints every one of those at the wrong rule, and nothing would catch it. A retired rule leaves its number burned — never shift the ones below it to close the gap.

**Default to a letter suffix on the nearest related guardrail** (`13a` directly after `13`), not the next number at the bottom of the list. This is the collision fix, not a style preference:

- Everyone who appends at the tail claims the same next number, so two branches in flight both take it. That happened twice in one afternoon (36 and 37 were each claimed by two branches), and it costs a manual renumber every time.
- Git only warns when the inserts land close enough to conflict textually. Resolve a conflict by "keeping both", or land two rules git auto-merges, and the file ships two rules wearing one number — from then on every citation of it is ambiguous.
- Suffixing puts each new rule next to its topic, so concurrent branches edit *different regions* of the file and stop meeting at all. Two branches suffixing the SAME parent still conflict — correctly, because they wrote overlapping rules about one topic and someone should reconcile them.

Take the next sequential number only for a genuinely new top-level topic with no parent to attach to. Expect to lose the race for it; **on any collision renumber YOUR rule, never the one already on the integration branch** — its number may already be cited in code that landed with it.

`tests/guardrail-ids.test.mts` enforces this: ids unique, every in-file `guardrail N` citation resolves, and a suffixed rule sits directly after its parent. It does NOT require the numbers to be gapless or sorted — the citations are what matter, not tidiness.

**ALWAYS apply a new rule to the current work immediately after writing it.** A rule born from a mistake means the codebase likely contains other instances of the same mistake. Writing the rule does not fix them.

### Signature / response-shape changes require a full consumer audit

**Why**: TypeScript catches most signature breaks, but two paths commonly slip through: `fetch('/api/…').then(r => r.json())` returns `any` on the client, and Prisma `select`/`include` shapes reused across files are structurally inferred. Either can silently rot on a shape change.

**ALWAYS** before changing:
- An API route response shape (`NextResponse.json({…})`)
- A shared Prisma `select`/`include` object
- An exported function signature or return type
- A `src/lib/*` util's public surface (`arr.ts`, `plex.ts`, `jellyfin.ts`, `cron-auth.ts`, `play-history.ts`)

run a full consumer grep:

```bash
rg "functionName|typeName" -t ts -t tsx
rg "fetch\(['\"]/api/<route>" -t ts -t tsx
```

**NEVER** assume `tsc` covers it. `fetch(...).then(r => r.json() as SomeType)` lies.

### Authoritative data beats heuristics

**Why**: This app caches five upstream APIs (`TmdbCache`, `TmdbMediaCore`, `PlexLibraryItem`, `JellyfinLibraryItem`, `Radarr/Sonarr{Wanted,Available}Item`, `TVEpisodeCache`, `PlexTokenCache`). Pattern-matching against a cache row can disagree with a live API call. When they disagree, the live API is right.

**ALWAYS** structure validation as:
1. Gather heuristic evidence (cached row, UI badge, commit history).
2. Fetch authoritative data (`arrFetch`, a direct Plex/Jellyfin call, or `/api/admin/debug/arr-state`).
3. On conflict, **authoritative wins** — update or invalidate the cache, don't patch the heuristic to agree with the stale row.

### Query real API responses before diagnosing external-API bugs

**Why**: "Movie stays pending forever" can mean Radarr never grabbed it, the webhook was dropped, the `RadarrWantedItem` cache is stale, or `tvdb→tmdb` resolution is negative-cached. Symptoms are identical, fixes are not.

**ALWAYS** when a Plex/Jellyfin/Radarr/Sonarr/TMDB-facing bug lands:
1. Hit [GET /api/admin/debug/arr-state?tmdbId=<id>&type=movie|tv](src/app/api/admin/debug/) first — it dumps cache rows, live ARR check, `tvdb→tmdb` mapping, wanted-table counts, and the last `LIBRARY_SYNC` audit row. Built for exactly this.
2. If it's not an ARR problem, call the upstream API directly (`arrFetch`, or `curl` with the stored token) to see the raw response.
3. Only then design a fix.

**NEVER** plan a fix from a symptom description alone. The user sees a badge, which is downstream of the cache, which is downstream of the sync, which is downstream of the webhook, which is downstream of the upstream API. Any of those layers can be the actual source.

### Audit all mutation points for shared state

**Why**: Several fields are written from multiple paths and must stay consistent. Fixing one write site while missing the others produces inconsistencies that only manifest on specific code paths.

High-traffic shared state in this project:
- `MediaRequest.status` — written by `/api/sync/*`, `/api/webhooks/*`, `/api/requests/*`, and admin actions.
- `MediaRequest.notifiedAvailable` — atomic CAS in the sync orchestrator (guardrail 14).
- `PlexLibraryItem` / `JellyfinLibraryItem` — replaced wholesale by `full` sync, appended by `recentOnly` (guardrail 13).
- `Setting` table — shared config for Plex, Jellyfin, Radarr, Sonarr, and webhook secrets.
- `ActiveSession` — written by the 5s play-history poller ([src/app/api/sync/play-history/route.ts](src/app/api/sync/play-history/route.ts)) and the Plex SSE handler ([src/lib/plex-events.ts](src/lib/plex-events.ts)), **not** by webhook handlers (there are no Plex/Jellyfin webhooks).

**ALWAYS** when touching logic that writes shared state:
1. Grep every assignment / `update` / `updateMany` / `upsert` / `createMany` / `deleteMany` on the field.
2. Trace from the first write through to the final read. Do all paths apply the same normalization?
3. If it's sync-related, verify both the `full` and `recentOnly` paths stay correct.

```bash
rg "mediaRequest\.(update|updateMany|upsert)|notifiedAvailable" -t ts
```

**NEVER** assume fixing one write site is sufficient.

### Communicate trade-offs when fixing problems

**Why**: A fix that reverts an earlier improvement needs to be an explicit, acknowledged decision — not a silent regression. This repo has several deliberate performance/correctness trades you should not undo by accident:

- Success logs intentionally silenced (`console.log` removed; silent-success convention).
- Plex + Jellyfin sync parallelized; shared `stillPending` snapshot; `recentOnly` for Jellyfin.
- `arrFetch` body cap raised to 50 MB.
- Activity calendar `$1` offset fix.

  (These four trades originally cited commit hashes that no longer resolve in the current squashed history — the behaviors above are all still present in source; verify against the code, not a hash.)

**ALWAYS** before implementing a fix that undoes prior work, state it plainly:
> "This resolves [problem X] but reverts [improvement Y]. Impact: [metric]. Alternatives: [if any]."

**NEVER** silently roll back a previous improvement.

### Scope control

**ALWAYS** limit changes to what the user asked for. Don't rename unrelated variables, refactor adjacent components, or reformat files you aren't touching. A bug fix is a bug fix. If you spot other issues, mention them — don't fix them.

### Lint + typecheck passing ≠ bug fixed

**Why**: `npm run lint` and `npx tsc --noEmit` validate your implementation of a diagnosis, not the diagnosis itself. They can both pass while the real bug persists — especially for async sync logic and external-API consumers where types are inferred from `fetch`.

**ALWAYS** when checks pass but the user still reports the bug:
1. Stop implementing more of the same fix.
2. Question the root-cause hypothesis.
3. Re-fetch real data (debug endpoint, live upstream API, direct DB query).
4. Assume the diagnosis is wrong, not the implementation.

### Definition of done

Before handing back to the user:

1. `npm run lint` passes.
2. `npm run typecheck` AND `npm run typecheck:classic` pass (native TS 7 + classic TS 6 — both compilers gate the tree; see Commands).
3. For UI/frontend changes, verify the feature in a browser against `npm run dev`, including the golden path and at least one edge case. If you can't test in a browser, say so explicitly — do not claim success.
4. For sync/webhook/cron changes, check `/api/admin/debug/arr-state` or the `LIBRARY_SYNC` audit row to confirm the pipeline ran end-to-end.
5. If a new convention emerged, update this file (guardrails or principles) in the same change.
6. No stray `console.log` success messages (guardrail 7).

The `npm test` suite covers only pure leaf modules (see the Commands section for the full list — auth/crypto/network-policy primitives plus assorted leaf logic). Run it, but do not claim broader "tests pass" than tests/ actually exercises — there is no coverage of sync/webhook/DB/UI behaviour.
