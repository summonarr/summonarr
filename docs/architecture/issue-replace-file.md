# Issue "Replace file"

_Moved verbatim from CLAUDE.md "Core architecture"._

**Issue "Replace file"** — `GET/POST /api/issues/[id]/files` (ADMIN — deleting files is ADMIN-only; ISSUE_ADMIN keeps the search and the release list), rules in [issue-replace.ts](../../src/lib/issue-replace.ts), surfaced as the delete in the issue's "Fix file" window ([issue-actions.tsx](../../src/components/admin/issue-actions.tsx)). While a file is on disk Radarr/Sonarr only take an UPGRADE of it, so an issue's search (`PATCH { refetch }`) can never replace a broken file already at the profile cutoff: this deletes the file first, then marks its grab failed (blocklist + the arr's redownload) or searches. Guardrail 5f.
- **The "Fix file" window** ([issue-fix.ts](../../src/lib/issue-fix.ts), pure) replaced three buttons (Refetch, Replace, Replace file) that did one job, two of which did nothing for the usual report. It reads the in-scope files once per instance (ADMIN only) and leads with what can work: a file meeting the cutoff → delete and get a new copy (the "Don't download the same release again" box, on by default, picks `then: "markFailed"`, off picks `"search"`); every file below the cutoff, or none → search automatically; pick a release where Sonarr can search the scope. The release search runs only when the list is opened. A release the arr turned down ONLY because of the file on disk (every rejection starts "Existing file…" or is Sonarr v5's season-pack upgrade threshold — `rejectedOnlyForFileOnDisk`) stays in the main list, marked: it still downloads, and imports when it is at least as good as the file it replaces (the arrs' import `UpgradeSpecification` refuses a worse quality or a lower custom-format score at the same quality). `tests/issue-fix.test.mts` pins it.
- **One page refresh per click**: the issue page's buttons and `LiveRefresh` share `requestPageRefresh` ([refresh-hold.ts](../../src/lib/client/refresh-hold.ts)), one debounced timer, so a button's own refresh and the SSE event announcing its change make ONE server render. Never a bare `router.refresh()` there (`tests/audit-fix-issue-refresh-hold.test.mts`).
- One replace per issue at a time, process-wide (claimed before the status CAS): a second POST while one runs is 409 with nothing written or sent — the CAS alone lets IN_PROGRESS → IN_PROGRESS through for every caller.
- The browser runs it as a BACKGROUND job (`async: true` → 202 `{ job }`, poll `GET ?job=` — the 37a pattern through `startArrJob`/`jobResponse`, client [replace-file-job.ts](../../src/lib/client/replace-file-job.ts)): its marks run in sequence, each re-reading the title's history, and a long series outlasts a reverse proxy's hold. The same admin posting for the same issue while it runs JOINS it; the synchronous default stays for API callers. A restart drops the job — the poll 404s and the dialog says to reload the issue, never to run it again.
