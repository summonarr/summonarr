# "For You" recommendations

_Moved verbatim from CLAUDE.md "Core architecture"._

**"For You" recommendations** — [src/lib/recommendations.ts](../../src/lib/recommendations.ts) + [src/lib/recommendation-graph.ts](../../src/lib/recommendation-graph.ts) + [src/lib/recommendation-quality.ts](../../src/lib/recommendation-quality.ts)
- Split by what varies: the SERVER-WIDE half (a title's suggestion edges and its quality verdict) is precomputed once per instance into `TitleSuggestion` + `RecommendationTitle`; the PER-USER half (seed selection, weighting, exclusions, ranking) is arithmetic over the caller's own rows — server play history, the media servers' own history and Jellyfin favorites (`ServerWatchedTitle`, guardrail 40c), the imported Trakt history and ratings (guardrails 34c/40c, history merged into the history pool under the same cap), watchlist and requests.
- What a viewer SAID counts, not only what they watched (guardrail 40c): Trakt 8–10 or a Jellyfin favorite lifts a seed (and a loved title too old for the history slots gets a loved-pool slot), Trakt ≤ 4 is never a seed, and a series dropped after a few episodes (judged against the episodes the server holds) is damped.
- `warmRecommendationsCache` runs a phase 0 before the three below: `importServerWatchHistory` reads each person's Plex history and Jellyfin played items/favorites INCREMENTALLY (per-identity read points, one transaction per identity) so this run's seeds and exclusions see them. Best-effort: a failure keeps the stored rows.
- Cross-viewer co-watching (`CoWatchSuggestion`, "people here who watched X also watched Y") is OPT-IN behind `feature.behavior.forYouCoWatch`, **default OFF**. Off, a shelf uses only the viewer's own records and the build deletes any old edges. On, every edge clears privacy floors (≥ 3 people watched both, ≥ 2 did not, ≥ 5 people with history), wears the viewer's own reason line, and never counts toward seed coverage. Detail: [guardrail 40c](../guardrails/40c.md).
- The `warm-library` cron (daily) pre-builds the same suggestion edges alongside its metadata walk (`prewarmSuggestionEdges`), so the graph is normally already warm — an accelerant only; the required build below still runs unconditionally.
- Edges are written 50 sources per transaction (`writeSourcePage`), which first sets Postgres-side timeouts (`setBatchTxTimeouts`: 20s per statement, 10s per lock wait) so a stall is cancelled by Postgres instead of holding its locks past the 30s transaction limit. A failed page logs one line naming the pass (`library prewarm` / `required seeds` / `speculative`), the cause (lock wait, statement timeout, deadlock, expired transaction…) and the time per step; its sources keep their old edges and are retried next run. A pass whose slowest page took 10s or more logs one warning with that page's steps.
- `warmRecommendationsCache` (the `warm-recommendations` cron, 12h) runs in three phases: **select** every active user's seeds, **build** the graph for exactly that union (uncapped), then **compute** each user from the same plan. There is no live fallback anywhere — the ordering is what guarantees coverage, and `conclusive` (seed-coverage based) is what stops an incomplete build from replacing a good shelf. Guardrail 40 has the rules.
- `getUserRecommendations` is the only live-request read: it re-filters the stored shelf against the user's CURRENT watchlist/watched/hidden/requested state, which is genuinely per-user and stays that way. `recommendedBecause.seeds` is attached only with `{ includeSeeds: true }` (the /for-you page and `/api/recommendations`); the home rails take the default and carry `seedCount` alone.
