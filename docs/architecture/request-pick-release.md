# Request "Pick release"

_Moved verbatim from CLAUDE.md "Core architecture"._

**Request "Pick release"** — `GET/POST /api/requests/[id]/releases` (MANAGE_REQUESTS): interactive search on an APPROVED/AVAILABLE request's own instance, the same projected `ArrRelease` list the Issue "Replace" panel uses. Each release's `guid` is replaced by an OPAQUE handle bound to the request, instance and season ([release-handles.ts](../../src/lib/release-handles.ts), 30-minute TTL, in memory): some indexers — and Prowlarr's proxied feeds — build the guid from the apikey'd download link, and this list reaches delegates, not only admins. The grab POSTs the handle, never a guid (410 when expired or from another search). The grab CLAIMS the handle synchronously before calling the arr (`claimReleaseHandle`): a second grab racing the first is 409 with nothing sent (a double submit or replay would otherwise reach the download client twice). A definite refusal (`grabDefinitelyRefused`: a 4xx answer other than 408, or the title missing from the arr) hands it back, and so does a failure BEFORE the grab is sent (no config, the title lookup, the tvdb resolution — `GrabProgress.sent` in [arr.ts](../../src/lib/arr.ts), set on the line before `postReleaseGrab`), because nothing reached the arr. An accepted grab, a 408/5xx (a gateway that gave up, an arr mid-restart — the grab may have gone through), a timeout or a network failure spends it. The same rule holds on all three grab routes. Its audit (`ARR_RELEASE_GRAB`) records the release NAME, never the guid. A TV search is ALWAYS per season: Sonarr's `/api/v3/release` with only `seriesId` answers with the indexers' RSS feed, not the series.
- **The issue Replace release list** (`GET/POST /api/issues/[id]/releases`) follows the same rules — the search is 20/min per admin like the other two (joining one already running costs no token), its grab audits `ARR_RELEASE_GRAB` (the status flip keeps its `ISSUE_STATUS_CHANGE` row), and sizes/ages/seeders render through the Pick-release dialog's locale formatters and plural key: each guid is an opaque handle bound to (issue, service, instance), carried in the `guid` field for iOS wire compatibility (the POST body stays `{ guid, indexerId }`; `indexerId` is checked but the handle names the indexer), claimed single-use BEFORE the IN_PROGRESS CAS (an unknown handle — a raw guid included — is 410 and never flips the issue; a racing grab is 409), handed back on a definite refusal or when the CAS finds the issue resolved, and audited with the release NAME. It is offered only for movies, EPISODE issues and SEASON issues with a season (`seriesReleaseScopeSearchable`, [release-scope.ts](../../src/lib/release-scope.ts)): a whole-series TV issue has no release search — 422 for both the search and the grab, and `getReleasesForSeries` throws `ReleaseSeasonRequiredError` rather than build the series-only (RSS) query — so it uses Refetch or Replace file instead.
- **The list is in the arr's OWN order** (`releaseWeight`, after the split by the TITLE's own quality profile — read from the arr's movie/series row (`ownProfileId`), never the instance's add default; no profile on the row ⇒ no split — `filterAndSortReleases` in [arr.ts](../../src/lib/arr.ts)) with `customFormatScore`/`customFormats`/`languages` projected by name. Never sort on `qualityWeight`: both arrs compute it against their DEFAULT profile, not the title's, and it knows nothing of custom formats, so a release the arr would rank last was pre-selected.
- **A grab the arr refuses says what to do** (`grabRefusalResponse`, [release-grab.ts](../../src/lib/release-grab.ts), on all three grab routes — request, title manager, issue Replace): its 404 is "no longer in my 30-minute search cache" (a restart drops it too) → 410 "search again", never "the title is gone"; its 409 is the indexer or download client refusing → 409 with the arr's reason, masked.
- **The browser runs a release search as a BACKGROUND job** (`async=1` → 202 `{ job }`, poll `?job=` — [release-search-jobs.ts](../../src/lib/release-search-jobs.ts)), the guardrail-37a lesson again: indexers take 60–110 s, a reverse proxy holds a request 60–100 s, and the admin saw a 502 while the search finished and then hit every indexer again. A job is readable by its OWNER only, and the same owner re-searching the same scope while one runs JOINS it (no second indexer hit, no rate token). A finished answer (a whole release list) is readable for 10 minutes and every expired one is swept on each start and poll, never left to fill the map; a search that throws answers 500. So does the issue Replace panel (`GET /api/issues/[id]/releases?async=1`, polled at `?job=`); its synchronous bare-array default stays for the iOS app. Both pages poll through ONE client loop, `runReleaseSearchJob` ([release-search-job.ts](../../src/lib/client/release-search-job.ts)). Every `/api/v3/release` read carries `RELEASE_SEARCH_TIMEOUT_MS` (120 s) — the arr's own search is the slow part, and the job is what keeps that wait off the proxy — and every grab POST carries `RELEASE_GRAB_TIMEOUT_MS` (120 s) through `postReleaseGrab`, the only grab call: the arr fetches the .torrent/.nzb from the indexer before it answers. The synchronous default stays for API callers.
