# Admin arr management

_Moved verbatim from CLAUDE.md "Core architecture"._

**Admin arr management** — everything an admin used to open Radarr/Sonarr for, ADMIN-only, read live — each page paints the last answer it got at once and then reloads live ("instant, then live", guardrail 5h). Shared plumbing: [arr-admin.ts](../../src/lib/arr-admin.ts) (`configuredArrCfg` — a slug is never turned into Setting reads unless the registry lists it, guardrail 32; `enabledArrInstances`; `postArrCommand`), [arr-admin-http.ts](../../src/lib/arr-admin-http.ts) (`arrGate`/`arrTitleGate` + ONE error→response map, `arrFailure` — an arr 409 relays the arr's own reason, masked; any other failure is worded by `arrErrorKind`: the API key, a timeout (504), an unreachable host, the arr itself), [arr-parse.ts](../../src/lib/arr-parse.ts) (bounded readers, `maskSecrets`/`safeMessage` — `name=value`, `%3D`/`%253D`-encoded, JSON/header pairs, quoted values up to their matching quote (escaped JSON included), any `Authorization:` value, Bearer/bearer/Basic, userinfo up to the LAST `@`, path tokens after `/` or `.` ending at any URL/bracket delimiter (the arrs quote a failing URL as `at [<url>]`), IPTorrents `tp=`, TorrentLeech path keys; the name prefix is bounded (`{0,64}`) and `safeMessage` masks only a bounded prefix of its input). Every report's per-instance `errors[]` carries a `kind` the page translates through the literal `ARR_ERROR_KIND_KEYS` ([arr-error-kind.ts](../../src/lib/arr-error-kind.ts)) — never the English `error`. Guardrail 5e has the rules.
- **Title manager** — "Manage in Radarr/Sonarr" beside "Open in" on the movie/TV pages ([title-manager.tsx](../../src/components/admin/arr-title/title-manager.tsx)); routes `/api/admin/arr/title{,/episodes,/files,/rename,/history,/command,/releases}`; rules in [arr-title.ts](../../src/lib/arr-title.ts), I/O in [arr-title-data.ts](../../src/lib/arr-title-data.ts). Settings go through the arr's own EDITOR endpoint (`PUT /api/v3/{movie,series}/editor` — only the sent fields change, tags `applyTags: "replace"`, a root folder equal to the current one is not sent); season monitoring is a read-modify-write of the series (Sonarr flips the season's episodes to match), and `editTitle` writes to one title are serialized in process (`oneEditAtATime`), so a season PUT never reverts an editor change Summonarr just made (writes made outside Summonarr between the read and the PUT are still overwritten — accepted); episodes via `PUT /api/v3/episode/monitor`. Sonarr "Search missing" reuses the Missing page's plan (`searchMissing` — never SeriesSearch); a season/episode search or interactive search is always scoped (a series-only release query is the RSS feed). Interactive search reuses `ReleaseSearchDialog` with a `target` and opaque handles bound to (service, instance, arrId, scope).
  - The Settings form holds the admin's EDITS over the title as last read, never a copy of it: a background re-read (a refresh, Radarr unmonitoring a movie whose file vanished) must not be saved back as if the admin chose it. Tabs stay mounted once opened, closing with unsaved edits asks first, and a root-folder change asks "move the files / I'll move them myself" with nothing pre-selected (and warns when the target disk lacks the space). Seasons are their own write: `seasons` combined with any other field is a 400.
  - A row the arr returns for "this title" that names ANOTHER title (`movieId`/`seriesId` present and different) is dropped from files, renames and history (`ownRows`) — RenameFiles names files by id and renames them with THIS title's metadata. A few episode ids are checked one `GET /api/v3/episode/{id}` each (`seriesId` must match), never the series' whole list.
  - Sonarr v4's per-series history embeds no `episode`; S/E is joined from the episode list by `episodeId`. A grab is "already failed" only by a failure NEWER than it (a torrent re-grabbed after a failure keeps its info hash as `downloadId`).
  - Episode monitoring answers the re-read series (its counts follow monitoring — 14a's escape hatch shows at once). A choice list the instance fails to answer is `null` and only that field is disabled. File ids for a delete ride in a JSON body (select-all on a long series); a rename takes the same 10,000-id cap (`MAX_TITLE_FILE_IDS`, [arr-title.ts](../../src/lib/arr-title.ts)). A delete that fails or times out part-way — a Radarr per-file DELETE, a Sonarr bulk delete — re-reads the title's files and audits every requested id no longer listed (`deletedAfterFailure`; every chosen file gone ⇒ a success). File deletes carry a 120 s timeout (a recycle bin on another filesystem makes each delete a copy) — past a reverse proxy's hold, so the Files tab runs the delete as a BACKGROUND job, the 37a pattern: `DELETE /api/admin/arr/title/files` with `async: true` in the body → 202 `{ job }`, poll `GET ?job=` on the same route (`startArrJob`/`jobResponse`), counted not timed (guardrail 16). The job runs the delete AND its ARR_FILE_DELETE audit (the audit context is read off the request before it starts); the same admin deleting the same files of the same title while one runs joins it, so nothing is sent twice; a poll's 404 (expired, a restart) means reload the files, never re-run the delete blindly. The synchronous default stays for API callers.
- **Download History** (`/admin/arr-history`, History + Blocklist tabs) — ONE instance at a time, paged by the arr (merging instances can't order a page honestly). The history `kind` filter is translated PER SERVICE: the arrs' event enums differ past 4 (`historyEventQuery`). Mark failed (`POST /api/admin/arr/history/failed`) needs the record's title id and refuses a non-grab.
  - Sonarr's per-episode Grabbed/Imported/Failed records fold into one row per download event (`groupHistoryEvents` — SONARR ONLY, Radarr writes one record per event; a run by id per instance + `downloadId` + series + kind, each record within 5 minutes of the previous one (`HISTORY_FOLD_GAP_MS`), so a re-grab of the same info hash or a second import stays its own row; undated records never fold), and a grab's state comes from the list (`grabStateOf` — only a HIGHER id counts as after it; an id-less grab's by `failsIdlessGrab`), in both the page and the title manager's tab — believed only where the list could hold the grab's newer records: on a page the arr filtered by kind, or a page past the first, a grab with no failure or import in view is UNKNOWN (`grabStateKnown`), and its Mark failed confirm says it may already be imported instead of implying neither.
  - Every write names the instance of the records it acts on, never the one in view: blocklist ids are per-instance autoincrement and collide. Reloads after a write go through the latest loader, and the view is pinned while a write is in flight.
  - A blocklist removal re-reads the page the admin was viewing first, then falls back to the bounded scan; its audit records each removed release's name and title id (ids alone point at nothing afterwards), a clear records the count the admin confirmed. A 404 from `/blocklist` means "too old" (Radarr below v4, Sonarr v3 before Aug 2021 — `/blacklist`), never "gone".
- **Arr Calendar** (`/admin/arr-calendar`) — the arrs' own `/api/v3/calendar`, two weeks at a time in the VIEWER's days. A movie release date is a calendar DATE (midnight UTC): the server pads Radarr's window a day each side and the page places it on that date (`entryMs`), or everyone west of UTC sees it a day early. Sonarr's window (a real `airDateUtc` instant) is padded 14 h each side — the v3 `DateTime.Parse` hedge, as arr-watch's `/history/since` read (`calendarFetchWindow`). A movie's status is upcoming until the LATER of midnight UTC and the viewer's local midnight of its date (`localEntryStatus`): nothing on a future local day reads missing, and nothing is offered a Search the route would 409. The page computes its weeks after mount from each report's `now` (guardrail 16); the week starts on the viewer's region's first day (`Intl.Locale#getWeekInfo`, Monday fallback).
  - Every local-day rule lives in the pure [arr-calendar-days.ts](../../src/lib/arr-calendar-days.ts) (`entryMs`, `entriesInWindow`, `weekStart`, `addDays` — calendar arithmetic, never n × 24 h), pinned per time zone in child processes (`tests/arr-fix-calendar.test.mts`).
  - An episode is `airing` until air time + runtime, then `missing`; a special is never missing (`aired`); a title in the instance's download queue is `downloading` (bounded read, failure tolerated, failed downloads ignored); one Radarr/Sonarr flag as needing attention (`needsAttention` — import blocked, a tracked warning/error) also carries `attention`, shown as a Needs attention chip linking the Download Queue filtered to that title. One row per title per local day across release kinds and instances, with a status and Search per instance.
  - Its Search never becomes an upgrade search: Radarr through `/api/admin/missing/search` (mode missing), Sonarr through `searchEpisodes` with `missingOnly`; a 409 carrying `nothingMissing: true` is "nothing left" and shown neutrally; any other 409 (an episode no longer on the series, the arr's own refusal) is a failure shown with the route's message, and Search stays. A report is drawn only for the window it was read for. The view lives in the URL.
- **Arr System** (`/admin/arr-system`, Tasks / Indexers & clients / Storage) — scheduled tasks (Run now names a taskName the instance lists, re-read; the update check and a library-wide refresh ask first), recent commands (cancel a queued one; queued/running are always listed, only finished ones capped), library-wide searches (`MissingMoviesSearch`/`MissingEpisodeSearch`/`CutoffUnmet…Search` — Sonarr is sent `monitored: true`, its default anyway; Radarr has NO such field, hard-codes monitored, and as a manual search IGNORES Minimum Availability — its confirm says so), indexers/clients (switch, test — up to 120 s, and a background Test All up to 270 s, since a provider test is sequential and a dead indexer hangs ~100 s, so the page runs Test, Test All and a testing save as BACKGROUND jobs: `async: true` → 202 `{ job }`, poll `GET ?job=` on the same route, the 37a pattern through the generic `startArrJob`/`jobResponse` in [release-search-jobs.ts](../../src/lib/release-search-jobs.ts); the synchronous default stays for API callers), root folders + disks. The ArrHealthPanel sits on top.
  - Neither arr has `/api/v3/indexerstatus` (an indexer disabled after failures shows in the health checks), and neither `RootFolderResource` carries `totalSpace` — a root's total comes from the `/diskspace` entry it sits on (longest whole-segment prefix) — only when its free space agrees with that disk's (`rootDisk` in [arr-system.ts](../../src/lib/arr-system.ts), shared with the monitor, guardrail 7c); otherwise the total is unknown, never the container root's.
  - A polled admin report goes through `createLoadGate` ([arr-system.ts](../../src/lib/arr-system.ts)): a poll tick never supersedes a load still in flight. With a dark instance taking the full timeout, every 15–20 s poll used to discard the one before it, so the page never rendered and Reload stayed disabled (Arr System, Download Queue).
- **Missing → Search selected** — row checkboxes, at most `BULK_SEARCH_MAX` (100) per run, counted over EVERY ticked row of the tab and mode — rows a filter hides included (the page says how many are hidden), and rows on other pages (the tables show 100 rows a page; select-all ticks the page on screen) — so the cap, the button's count and the run are one list (past that, Arr System's library-wide search); a confirmation above 10 titles stating the count, the unmonitored count and the indexer cost; Cancel, and an abort on unmount. Each ticked row goes through the per-row search route (re-judged live), two requests at a time — pacing Summonarr's own requests ONLY: each POST answers 202 once the arr has QUEUED the command. The route is rate-limited (120/min per admin); the page waits out `Retry-After` and retries a row once. A 409 is "already complete", not a failure; rows are re-checked when dequeued and a pending row's own Search is disabled. Runner: [bulk-search-run.ts](../../src/lib/bulk-search-run.ts).
- **Live command feedback** — every button that starts a Radarr/Sonarr command (title manager Search / Search missing / Refresh & scan / season and episode searches, Files → Rename, Arr System's Run now and library-wide searches, Clear blocklist) follows the arr's own command instead of guessing with a timer. The starting route answers with the arr's command id(s) (additive `commandIds`; the tasks route's `{ id }`) and the page polls `GET /api/admin/arr/commands?service&instance&ids=` (ADMIN, ≤`COMMAND_READ_MAX_IDS` (200) ids — a long series' Search missing queues one SeasonSearch per season — read 6 at a time and stopped at the first non-404 failure; the browser splits a longer list into sequential reads; 120/min, not audited) through `useArrCommandWatch` ([arr-command-watch.tsx](../../src/components/admin/arr-command-watch.tsx)) until every command has ended, then re-reads what it changed. The loop is pure ([arr-command-status.ts](../../src/lib/arr-command-status.ts)): one read at a time from each answer (never `setInterval`), each poll asking only for the ids still queued or running (an ended command keeps the state it ended with and is never re-read), a 300-poll cap counted not timed (guardrail 16; a hidden tab's polls count, but the cap is only declared on a REAL read, so a watch hidden past its budget reads once on return before giving up), stopped by a 4xx or five failed reads in a row, nothing acted on after a stop or unmount — and a watch started AFTER the unmount (a command POST that resolved late) follows nothing: the hook disposes the watcher on unmount (`dispose()`, resumed in the effect body for StrictMode); a plain `stop()` never disposes. The read projects through `projectCommands` — never the command body (5e); a 404 is `{ id, status: "gone" }` (the arr forgets finished commands), never "completed". Never put a fixed re-read timer back.
- **Add to / Remove from an instance** — [arr-title-lifecycle.ts](../../src/lib/arr-title-lifecycle.ts). The detail pages show "Manage in" for each configured instance whose synced cache holds the title and "Add to" for every other one ([add-dialog.tsx](../../src/components/admin/arr-title/add-dialog.tsx), `GET/POST /api/admin/arr/title/add`): the arr's own add choices (profile, root folder, tags; Radarr monitored + minimum availability; Sonarr's `addOptions.monitor` subset both v3 and v4 accept, series type, season folders), the instance's configured defaults preselected only while the instance still lists them, every value checked against a fresh read (5e). An admin add creates NO MediaRequest — nobody is notified, no watch grade counts it (34a) — but it DOES withdraw an earlier removal: this instance's `cleanedUpAt` stamps for the title are cleared after the arr accepts the add (best-effort), so a later disappearance is a lost file again (14b). A title's requests are matched by tmdb id OR tvdb id (`requestIdentity`) — a TV request's tvdbId can be the only link when TMDB's id and Sonarr's disagree — and when a Sonarr series reports no tmdbId (v3, or v4's 0) the tmdb id is resolved from its tvdb id with `resolveSingleTvdbToTmdb`, the mapping the sync's Sonarr cache keys by, so a request that was never pushed (tvdbId null: a mirror copy, a library-marked row) is still counted and stamped. The title manager's Settings tab ends with "Remove from …" (`POST /api/admin/arr/title/remove`): a dry run, then an execute echoing the id; `deleteFiles` and the import-list exclusion always sent explicitly (5c); refused while an APPROVED request on THAT instance would make the sync re-add it (decline or delete it first — the route never writes request status, 34a); every AVAILABLE request on that instance is stamped `cleanedUpAt` before the delete, and unstamped only when the arr definitely refused it and a re-read shows the title still there (14b has the rule). Audited ARR_TITLE_ADD / ARR_TITLE_DELETE.
- **The title manager opens from anywhere** — `ManageTitleButton` (by the arr's own id or by TMDB id, on a chosen tab; an icon variant for table rows) and a detail-page deep link `?manage=<service>:<slug>&tab=` (`parseManageLink` — it only selects among the page's own instances). Download Queue, Missing, Arr Calendar (per instance cell), Download History + Blocklist, the request queue (one Open-in per instance the group's requests name and one Manage per instance the title was pushed to — an HD and a 4K request are two; `requestApproved`/`requestAvailable` contexts) and admin Issues (one icon per instance whose synced cache holds the title) open it on the tab `manageTabFor` ([arr-manage-links.ts](../../src/lib/arr-manage-links.ts)) picks — by the arr's own id wherever the row has one, so a Sonarr v3 series with no TMDB id is reachable. The queue holds `ArrTitleManager` itself, never per row: a finished download leaves the list on the next poll, and polling pauses while it is open. The request queue keeps one `ManageTitleButton` per row instead, so its live refresh (SSE `request:*` events and the batch action) waits while a manager is open — `onActiveChange` feeds [refresh-gate.ts](../../src/lib/refresh-gate.ts) — and runs once the last one closes; otherwise a refresh can drop the row (the `?status=` filter or paging) and the dialog with it, unsaved edits and all. The manager applies `initialTab` at open time only, and a write's answer (Settings save, season/episode flip) drops any read still in flight and reads again. `ArrHistoryList` takes a `renderManage` prop instead of importing the manager (the manager's History tab renders that list — an import cycle, and a manager inside itself).
- **Queue link filters** — `/admin/queue?q=`, `?service=&instance=&arrId=` and `?filter=attention`, parsed on the server by `parseQueueLinkFilters`; an invalid part drops the whole title filter, never part of it, and `filter` is kept only when it is `attention` (so a parsed plain link still deepEquals `{ q, title }`). The title manager's History tab, the Why? panel and the calendar's attention chip link there (`queueTitleHref`); the nav badge and the `arr.queue_attention` event land on the attention tab (`QUEUE_ATTENTION_HREF` — notify-events.ts is zero-import and spells both links itself, pinned equal in `tests/arr-watch.test.mts`). The `?manage=` detail-page deep link has no in-app producer: it is an external/bookmark URL, and it opens the manager on a non-holder on purpose (the manager resolves the title live, so a title added since the last sync still opens).
