# Radarr/Sonarr monitor

_Moved verbatim from CLAUDE.md "Core architecture"._

**Radarr/Sonarr monitor** — [arr-watch.ts](../../src/lib/arr-watch.ts) (pure) + [arr-watch-data.ts](../../src/lib/arr-watch-data.ts), cron `/api/cron/arr-watch` (lock 2051, `ARR_WATCH_INTERVAL`), setting `arrWatchDiskLowPercent` (Settings → Notifications → Radarr/Sonarr alerts, `PATCH /api/admin/arr-watch`). Per enabled, configured instance (guardrail 32) it sends what Radarr/Sonarr Connect has no trigger for to the outbound channels (guardrail 14c) — `arr.disk_low`/`arr.disk_ok`, `arr.download_failed`, `arr.queue_attention` — and writes `arrWatch:summary`, which the admin nav's Download Queue badge reads and the settings card shows (last check + its counts, formatted after mount). While the badge carries a count the item links to the queue's attention tab (`navItemHref` → `QUEUE_ATTENTION_HREF`, `/admin/queue?filter=attention`), and the `arr.queue_attention` event's link names the title's own queue filter when the event carries `arrId` (the queue item's `arrMediaId`), the attention tab otherwise. The `(app)` layout renders the badge first (one row read, admins only, fails open), and ONE client `NavBadgesProvider` ([admin-nav-groups.tsx](../../src/components/layout/admin-nav-groups.tsx)) keeps it fresh from `GET /api/admin/arr-watch`'s additive `navBadges` (every 5 minutes, skipped in a hidden tab, and on returning to the tab; a failed read keeps the badge) — layouts do not re-render on client navigation. Both readers go through `arrWatchNavBadgesFor`, so the stale-snapshot rule exists once. Never add a second poll per nav surface. In-app/web push are not wired (parity with `arr.health`): an admin with no webhook/ntfy/Gotify channel sees only the badge. Guardrail 7c has the rules.
