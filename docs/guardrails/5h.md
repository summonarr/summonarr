# Guardrail 5h

_Moved verbatim from CLAUDE.md. The id is a permanent address; CLAUDE.md keeps the headline and hard rules._

5h. **An admin arr page paints its last answer at once and then reads live — and a snapshot is DISPLAY ONLY: nothing that writes ever reads one.** Server: [arr-snapshot.ts](../../src/lib/arr-snapshot.ts) (`withAdmin(snapshotted(…))` on each admin Radarr/Sonarr READ route); client: [use-arr-snapshot.ts](../../src/components/admin/use-arr-snapshot.ts) + [arr-snapshot-note.tsx](../../src/components/admin/arr-snapshot-note.tsx).

    Why:
    - Every arr page used to open on a spinner until Radarr/Sonarr answered — seconds on a big library, the full 30 s timeout on a dark instance. The admin asked for "instant, then live": the last-known view at once, marked with when it was read, then the live read swapped in.
    - The danger is an action decided on old data. Every admin arr write already re-checks against a FRESH read of the instance (5d/5e), so a row painted from a snapshot is only a NAME the server re-judges — that, and only that, is what makes painting stale data safe.

    Rules:
    - `?cached=1` answers the last kept 200 JSON body of that exact read (path + sorted query minus `cached`, plus the request language — bodies can carry translated text) with `X-Summonarr-Snapshot-At`, or 204; it never runs the handler. Only a live 200 JSON is kept: a single-instance read that fails (5xx) leaves its last good answer on screen, marked stale, while a multi-instance report that answers 200 with one instance in `errors[]` is kept exactly as answered. `job=` polls are never kept.
    - A `cached=1` read skips the route's own instance checks (unknown slug, integration off), so every Radarr/Sonarr config write drops ALL snapshots: `/api/settings` when a key passes `isArrConfigKey` (incl. its rollback), and the `arr-instances` registry write. Add the call to any new write that adds, removes or re-points an instance.
    - NEVER wrap a read whose answer must not be replayed: release searches (handles are single-use and bound to one search — release-handles.ts), `/api/admin/arr/commands`, rename previews, the Why? status, or anything a non-ADMIN can read. The wrapper sits INSIDE `withAdmin`, so the gate runs before a snapshot is served.
    - NEVER let a write path read a snapshot, and never base a form's edits on one once a live read has landed (the title manager's Settings form rebases on the live read exactly as on a background re-read).
    - The page reads its snapshot and its live answer from ONE URL builder, applies a snapshot only while no live answer for that view has landed (`markLive`), never while a write the admin started is in flight (its `apply` returns `false` to decline, and then no stale note is shown), and shows `ArrSnapshotNote` while it does. Polling is unchanged; only the first paint of a view uses the snapshot.
    - A snapshot replays the server's `now` from when it was read: nothing derives "today" or a window from it (the calendar's `clock` is set by live answers only). The title manager disables Save while the Settings form's base is still the snapshot; edits made meanwhile survive the live rebase.
    - In-process only (`processSingleton`): bounded by bytes (32 MB total, 4 MB per answer), LRU, never older than 24 h; a restart starts empty and the first open of each page fills it — no warm-up at boot, by the admin's choice.
    - **Kept fresh in the background, by priority.** `/api/cron/refresh-arr-snapshots` (lock 2061, `ARR_SNAPSHOT_INTERVAL`, default 300 s) re-reads every view an admin opened in the last 24 h (`SNAPSHOT_VIEW_WINDOW_MS`) through the route's OWN handler — registered by `snapshotted` on each live read — so the kept body is exactly a live answer: the queue and health every 5 minutes, Missing / history / blocklist / calendar / the title manager every 10, Arr System every 15 (`SNAPSHOT_REFRESH_TIERS`; a wrapped route with no tier fails `tests/arr-snapshot-refresh.test.mts`). At most 40 re-reads per run, 2 at a time, signal-checked before each (41). A re-read runs as the system session (no read depends on the caller — a `job=` poll would, and is never kept) in the view's language, keeps its answer only as a 200 JSON, and is NOT a view: a page nobody opens stops being refreshed after a day. A config write that clears the store while a re-read is out wins. Skipped before its lock when nothing is due.
    - `tests/arr-snapshot.test.mts` pins the store and wrapper; `tests/arr-snapshot-*.test.mts` pin the routes and pages.
    - **The title manager's Settings form keeps TAG edits as a delta** (`TagDelta` `{ add, remove }`, [snapshot-rules.ts](../../src/components/admin/arr-title/snapshot-rules.ts)), never a whole list: the tags it shows and saves are `applyTagDelta(base.tags, delta)` over whatever base the form holds NOW, and `changes.tags` is sent only when that differs from the base. An absolute list toggled over a painted snapshot silently removed, on Save, any tag the arr gained before the live rebase (the PATCH replaces tags). `tests/arr-title-tag-delta.test.mts` pins it.
