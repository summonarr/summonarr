# Guardrail 5e

_Moved verbatim from CLAUDE.md. The id is a permanent address; CLAUDE.md keeps the headline and hard rules._

5e. **On every admin arr route, a value from the browser is only ever a NAME for something the instance itself reports for that title — and no provider `fields`, history `data`, release guid or upstream credential reaches the browser, a log line or an audit row.** The 5d rule, generalized to the title manager, history, blocklist, calendar and system routes.

    Why:
    - These routes MOVE, DELETE and RENAME files and switch indexers. A root folder path the browser invents is where Radarr/Sonarr move a title's files; a file id from a stale page deletes someone else's episode; a task name taken verbatim is an arbitrary arr command.
    - An indexer's or download client's resource carries its API key, passkey or password in `fields`; a history grab's `data` carries `downloadUrl`/`guid`/`nzbInfoUrl`, which embed the indexer apikey; an indexer's failure text can quote the URL it tried.

    Rules:
    - Check against a FRESH read before writing: profiles/root folders/tags/seasons (`checkTitleEdit`), files (`deleteTitleFiles`), renames (the preview re-read), episodes, blocklist ids, history records (must be this title's, a grab, and its download not already failed — Sonarr writes a Grabbed record PER EPISODE of a pack, the 5c trap again), task names (the instance's own `/system/task`), queued commands, indexer uses the instance reports it can't do (`supportsRss`/`supportsSearch` false on the fresh read are never switched ON — 400, nothing sent; switching one OFF is always allowed; an arr that doesn't report them is unaffected). A miss is 400/409 with nothing sent.
    - A Mark failed then CLAIMS its download in process (instance + downloadId, or the history id when the grab has none) between that check and the POST: a concurrent mark is 409 with nothing sent; a definite refusal (a 4xx other than 408) releases the claim; an accepted or unknown outcome keeps it 10 minutes for the grabs the history held then (a later re-grab of the same info hash is a new mark). A grab with no downloadId (Blackhole clients) is already failed by a newer id-less failure with the same release name on the same title and, on Sonarr, the same episode id — `failsIdlessGrab` ([arr-history.ts](../../src/lib/arr-history.ts)), shared by `markHistoryFailed` and `grabStateOf`.
    - A provider switch or single test is read → flags changed → sent back SERVER-side (`withProviderEnabled`); the browser names the id and the flags only. A switch that only turns things OFF is saved with `forceSave` (the arr re-tests an indexer that keeps any use on); turning one ON lets the arr test it. When the arr refuses on WARNINGS alone (its UpdateProvider tests with includeWarnings) the answer is 409 `{ warningsOnly }`; only an explicit `acceptWarnings` from the admin may then save with `forceSave`, and only after the server re-runs the arr's own `/test` on the changed resource and finds no errors — the browser never decides that failures were only warnings. A mixed ON+OFF change is tested. A testing save that times out is read back and audited only if the arr holds the change; run as a background job it is re-read up to 6 more times, 10 s apart, before answering 504 (a save that lands later than that is still unaudited — accepted, documented on the route). Test All answers 400 when any provider failed — its body is still the per-provider list. Saves to one provider are serialized in process per (service, instance, kind, id) (`withProviderLock`, [arr-system-data.ts](../../src/lib/arr-system-data.ts)): each is a read-modify-write of the whole resource, so two overlapping saves would otherwise let the later write revert the other's flag. Accepted gap: a save that timed out on our side and lands after the read-backs can still be overwritten.
    - Projections are explicit field lists (`projectIndexers`, `projectDownloadClients`, `projectHistoryRecord`, `projectCommands` — never the command body); every free-text upstream message goes through `safeMessage`. Every release list hands out opaque handles, never guids: bound to (service, instance, arrId, scope) in the title manager, to the request, instance and season on a request's Pick release, to (issue, service, instance) on an issue's Replace release.
    - Writes are audited after the arr accepted them (guardrail 26), and only for what was actually written upstream: ARR_TITLE_EDIT, ARR_FILE_DELETE, ARR_FILE_RENAME, ARR_MARK_FAILED, ARR_BLOCKLIST_CHANGE, ARR_COMMAND (task runs — Sonarr's ApplicationUpdateCheck / Radarr's ApplicationCheckUpdate install an update when run by hand — and library-wide searches), ARR_PROVIDER_CHANGE, ARR_RELEASE_GRAB (with the release name). ARR_BLOCKLIST_CHANGE records each removed release's name and title id, and a clear the count the admin confirmed. Title searches/refreshes and cancels are not.
    - `tests/arr-manage-routes.test.mts` + `tests/arr-manage.test.mts` pin all of it; 25 mutations (each check removed, each projection widened, each mask narrowed, `forceSave` either way, the audit moved before the write) each fail a named test. The 2026-10-11 review fixes are pinned there and in `tests/arr-fix-{system,history,calendar,missing}.test.mts` (~125 more mutations, each killed).
    - **Facts read from the arrs' own source (2026-10-11) — don't "fix" them back:** Sonarr `RefreshSeries` takes `seriesId` (singular) on v3, v4 and v5 — NEVER send `seriesIds` alone, v3 ignores it and an empty list refreshes the WHOLE library; Radarr's `RefreshMovie` takes `movieIds`. Radarr's `DELETE /moviefile/bulk` applies the first file's movie to every file (one DELETE per file is right), and a per-id `PUT /moviefile/{id}` or `/episodefile/{id}` with a partial body nulls the quality. Round-tripping a provider's GET body never wipes a secret: v5+ masks it as `********` and PUT/test restore the stored value. Test All (`/indexer/testall`, `/downloadclient/testall`) never says which failures are only warnings on a System.Text.Json arr (Radarr v3+, Sonarr v4+, `/api/v5` included): `ProviderTestAllResult.ValidationFailures` is declared `List<ValidationFailure>`, so `isWarning` is never written, and `severity` is always `"error"` (FluentValidation's default; neither arr sets it). Only Sonarr v3 (Newtonsoft) writes `isWarning` there; a single `/test` or save 400 always carries it (it serializes `ValidationException.Errors` as `object`). So a Test All provider whose failures carry no flag is `uncertain`, never failed (`projectTestAll`) — and the fix is never to read `severity` (source-verified 2026-10-13).
    - **`ArrResponseError.body` is NON-enumerable** ([arr.ts](../../src/lib/arr.ts)): `console.error(err)` and `util.inspect` never print the upstream body, which can quote an indexer URL with its apikey. Read it as `err.body`; never spread or `JSON.stringify` the error; log `arrErrorMessage(err)`, not the error object.
