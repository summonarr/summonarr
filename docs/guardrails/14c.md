# Guardrail 14c

_Moved verbatim from CLAUDE.md. The id is a permanent address; CLAUDE.md keeps the headline and hard rules._

14c. **NEVER list notification channels at a "now available" call site — every claimed winner goes through `fanOutAvailableWinners` ([request-notifications.ts](../../src/lib/request-notifications.ts)) — the sync/webhook claimers AND the admin's manual "mark available" (the AVAILABLE branch of `notifyRequestStatusChange`) — and it is the ONLY `request.available` emit (the hub itself emits only `request.approved`/`request.declined`). Outbound channels (webhook / ntfy / Gotify, `NotificationAgent` rows) are reached ONLY through `emitNotificationEvent(s)` ([notify-agents.ts](../../src/lib/notify-agents.ts)), which never throws and never blocks the caller.**

    Why:
    - The four-channel "available" fan-out (Discord, push, in-app, email) was copy-pasted into SIX sync sites plus the webhook poll. Adding a fifth channel meant editing seven places, and the copies had already drifted (two swallowed errors silently, the rest warned).
    - The outbound channels are instance-wide and admin-configured, so the same event must reach them however it was produced — single approve, batch approve, Discord button, sync, webhook.

    Rules:
    - A new channel for "now available" is added INSIDE `fanOutAvailableWinners`, never at a call site. Callers pass only the claimed, deliverable winners, so the once-only claim (guardrail 14) and the disabled-requester drop (guardrail 33) cover every channel at once. `tests/notify-agents.test.mts` pins that the three sync route files contain no per-channel call.
    - The outbound channels follow the requester-facing hubs for request events — every APPROVED/DECLINED decision, single or batch, from the web PATCH, the batch route or a Discord button, goes through ONE dispatch, `notifyRequestStatusChanges` in [request-notifications.ts](../../src/lib/request-notifications.ts) (a single decision is one target): a self-action or a disabled requester sends nothing to them either (one active-owner read, every channel fed the same filtered set), and every decline carries the note the decision wrote, otherwise the row's stored admin note. `AvailableWinner.arrInstance` and `PendingAvailableRequest.arrInstance` are REQUIRED on purpose: a select that omits the column fails to compile instead of reporting the default instance (guardrail 32) in the outbound event. Admin events (new request/issue, issue reply/resolve, vote threshold, *arr manual import / replacement grab) emit beside the existing admin fan-out.
    - Channel URLs are admin-entered, so delivery goes through `safeFetchAdminConfigured` (guardrail 5a — LAN allowed, metadata blocked). The one credential per channel lives in `NotificationAgent.secret`, encrypted by the Prisma extension (guardrail 7a — never `encryptToken`); the admin wire shape carries only `hasSecret`. Gotify's token goes in `X-Gotify-Key`, never the query string. A secret with any control character (NUL, CR/LF, …) is refused on input; a header value the transport still rejects is a `fail` with a constant message, never the thrown message (which embeds the secret). The create/update `SETTINGS_CHANGE` audit records the DESTINATION (url; webhook `headerName` + `hasTemplate`; ntfy `topic`) and only whether the secret changed — never the secret. The audited url goes through `redactUrlForLog` (query, userinfo and Discord-style path tokens stripped) with its fragment dropped, so a credential-bearing webhook URL never lands in an audit row; a secret carried in an ordinary path segment (Slack's `/services/T…/B…/<secret>`) is NOT stripped, because redacting arbitrary segments would lose the destination the audit exists to record.
    - Delivery: 2xx ok; 408/429/5xx/network retried at 30 s / 2 min / 10 min through `scheduleDelayed`; any other 4xx and every SSRF refusal fail at once. Retries are in memory — a restart drops pending ones (accepted; an outbox table is the upgrade if delivery must survive restarts). **A retry re-resolves the agent by id at fire time** (`retryDelivery`): a channel disabled, deleted, unsubscribed or re-pointed while a retry is pending is delivered with its CURRENT config or not at all — never from the attempt-0 snapshot, and never recording an outcome onto a withdrawn channel. A pending retry is also withdrawn when `feature.integration.webhooks` (the integration switch, `AGENTS_FEATURE_KEY`) has been switched off since attempt 0 — no fetch, no outcome. **A retry the shared `delayed-jobs` pool refuses — at schedule time (`scheduleDelayed` returned `false`) or at fire time (its `onDrop` hook) — is terminal and is recorded on the row as `failed: retry queue full: <reason>`**; nothing is silently lost. The last outcome is recorded on the row for the admin list; the Test button awaits that write before responding, the dispatch path does not.
    - Messages are written in the instance default language and media titles are localized at send time (guardrail 40a). The webhook payload is versioned (`WEBHOOK_PAYLOAD_VERSION`); a custom template is `{{field}}` substitution from `TEMPLATE_FIELDS` only, each value JSON-string escaped, and must render to valid JSON for EVERY sample (`TEMPLATE_SAMPLES`, [notify-events.ts](../../src/lib/notify-events.ts)) — the Test button's sample, a validation-only FULL one with the issue/votes/arr text fields set, and a sparse one with every nullable field null (`media` absent, no text/votes) — or it is refused on save; an unquoted `{{media.tmdbId}}` (or an issue/votes/arr/`id` placeholder outside a JSON string) is therefore refused. Every webhook payload carries a per-event `id` (additive within version 1, the same on every retry of one event), also sent as the `Idempotency-Key` header (`WEBHOOK_DELIVERY_ID_HEADER`), so that header name is RESERVED for a channel's own auth header. An enabled channel whose STORED config no longer validates (validation tightened in an upgrade) is skipped, never sent: one `[notify-agents]` warning per channel through `warnOnChange` (7b) and `configValid: false` on the admin list ("Not sending" in Settings) until it is edited. Upgrade note: a stored webhook whose `headerName` is `Idempotency-Key`, or whose template puts an issue/votes/arr/`id` placeholder outside a JSON string, stops sending this way. ntfy/Gotify URLs are a BASE the path is appended to, so a query or fragment on them is refused; generic webhooks keep theirs.
    - Text keys are a LITERAL map (`AGENT_TEXT_KEYS`), never built from the event name — the i18n dead-string check can't see a built key.
