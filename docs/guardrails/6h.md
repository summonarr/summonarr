# Guardrail 6h

_The id is a permanent address; CLAUDE.md keeps the headline and hard rules._

6h. **A session token is bound to the transport it was minted for and refused on the other; every signing purpose has its own HKDF subkey of `NEXTAUTH_SECRET`; and the User-Agent is never an authorization input.** [session-jwt.ts](../../src/lib/session-jwt.ts) (`boundTransport`, `isTransportAllowed`, `verifySessionToken`), [signing-keys.ts](../../src/lib/signing-keys.ts), [session-refresh.ts](../../src/lib/session-refresh.ts).

## 1. Transport binding

Why:
- Guardrail 6b lets a bearer request skip the cookie-only defences (the CSRF Origin check, the cron same-origin gate) because a cross-origin page can't attach a custom header. That reasoning is about *forgery*. It said nothing about *theft*: the bearer and the cookie carried the same JWT, so a stolen browser cookie replayed as `Authorization: Bearer` walked past every cookie-only check, and on the bearer path a privilege change never rotates the session (6b), so the stolen copy survived that too.
- The reverse was open as well: a native token (never expiring, 6c) could be planted in a browser as the session cookie.

Rules:
- `initializeTokenOnSignIn` stamps `transport: "bearer"` when the caller presented `X-Summonarr-Client` (the same header that selects the never-expiring deadline) and `"cookie"` otherwise. The machine session is `"cookie"`: it is delivered only as Set-Cookie. `SignInResult.transport` carries it, and `buildSignInResponse` delivers the token on exactly that transport — the body for bearer (only with the header, as 6b requires), Set-Cookie for cookie, and nothing if the two ever disagree.
- Every reader states the transport the token ARRIVED on and the token is refused on the other: `verifyAndRefreshSession(token, { transport })` (required by its type) for the proxy, `authenticateRequest`, `requireAuth`, `/api/auth/me` and the session-server readers (so `authActive()` and `getCronActor` too); `verifySessionJwt(token, transport)` for sign-out and `readSummonarrSession`/`auth()`. The check runs before any DB read, on the fast path as well.
- The re-sign stamps the transport the token arrived on, so a pre-claim token becomes bound on its first DB-checked verify. The coalescing key carries the transport, since the two results differ.
- **Pre-claim tokens are inferred, never signed out.** `boundTransport` reads what the shape proves: `dbCheckedAt` ⇒ cookie (only the re-sign stamps it, and only Set-Cookie delivers a re-signed token — the proxy's forwarded-header rewrite is server-internal); a deadline more than `MAX_CONFIGURABLE_SESSION_SECONDS` (90 days) past `iat` ⇒ bearer (the browser durations have been capped at 90 days since the first release, so that is the never-expiring sentinel or the 1-year native TTL from before 6c); otherwise either. The "either" set is tokens nothing has re-signed yet — a browser sign-in seconds old, a 15-minute machine session, a pre-6c native sign-in that got a browser-length TTL — all minted before the claim, so it dies with their ≤ 90-day deadlines.
- `MAX_CONFIGURABLE_SESSION_SECONDS` must stay equal to the settings route's and the session form's `MAX_SESSION_SECONDS`. Raising the configurable ceiling without moving it would read long browser sessions as native ones; `tests/session-transport.test.mts` pins the three together.
- Behaviour change: a machine session presented as `Authorization: Bearer` is refused (it was only ever handed out as a cookie). Automation must send it as the cookie it receives.

## 2. Per-purpose subkeys and rotation

Why:
- The raw `NEXTAUTH_SECRET` signed the session JWT, the Plex and QuickConnect flow cookies, the OIDC flow state, the request tokens and keyed the PlexTokenCache HMAC — all HS256/HMAC-SHA256 under one key. A value minted for one purpose was a valid MAC for every other, and only the payload shapes kept them apart (the audit verified the shapes are disjoint today; nothing kept them so).
- Changing `NEXTAUTH_SECRET` signed every user out, so a planned rotation was never done.

Rules:
- `signing-keys.ts` derives one subkey per purpose (`HKDF-SHA256(secret, "summonarr-signing-key", "summonarr:<purpose>:v1")`): `session`, `plex-flow`, `qc-flow`, `oidc-flow`, `request-token`, `plex-token-cache`, plus the HMAC-only `audit-email` and `discord-merge-code` (the at-rest MAC of a pending confirm-merge code). Every JWT carries its own `typ`, an audience and a `kid`. Don't read `NEXTAUTH_SECRET` in a new module; add a purpose. (mfa-token.ts, mfa-store.ts and the Plex connect cookie keep the HKDF subkeys they already had.)
- The `kid` names the SECRET (9 HKDF bytes, never the secret or a plain hash of it), so the verifier picks the matching key. A missing or unknown kid is refused on every purpose-bound token.
- `NEXTAUTH_SECRET_PREVIOUS` is verify-only: nothing is signed with it. A token signed under it never takes the session fast path, so a browser is re-signed with the current key on its next request. Boot refuses a previous secret under 32 characters and one equal to `CRON_SECRET` or `TOKEN_ENCRYPTION_KEY`; one equal to `NEXTAUTH_SECRET` is ignored with a warning.
- Rotating: set `NEXTAUTH_SECRET_PREVIOUS` to the old value, `NEXTAUTH_SECRET` to a new one, restart. Browsers migrate within a request each. **Native tokens are never re-issued (6b), so every iOS session minted before the rotation stays valid only while `NEXTAUTH_SECRET_PREVIOUS` holds the secret that signed it;** removing it signs those devices out. After a LEAK, change `NEXTAUTH_SECRET` and do NOT set the previous one — it would keep accepting forgeries under the leaked secret.
- Short-lived tokens switched immediately (no raw-key fallback): the flow cookies and the OIDC flow state (5–10 minutes) and request tokens (≤ 2 hours; the iOS app fetches a fresh one per request) in flight at the deploy fail once. PlexTokenCache rows hashed with the raw key simply miss; the miss path re-verifies against plex.tv and writes a fresh row, and the orphans age out through the purge cron.
- **The legacy raw-key session path is the one exception, and it is gated, not time-bounded.** A token with no `kid` verifies against the raw current (or raw previous) secret ONLY in its legacy shape — `typ` "JWT" or absent, no audience, no `transport` claim — so the raw key can never vouch for a token in the new format, and nothing signs with the raw key any more. It is never "current key", so a browser's raw-key cookie is re-signed with the subkey on its next request, and it could not outlive its ≤ 90-day deadline anyway. The path stays for native tokens: an iOS device signed in before this change presents its raw-key token until it signs out, and a fixed cut-off date would sign every such device out. The trade-off: anyone holding `NEXTAUTH_SECRET` can still mint a legacy-shaped bearer token — which is no more than they could do with the subkey derivation. To retire the path, remove the `else` branch in `verifySessionToken` once every native session predating the change has been revoked or re-signed in (e.g. after a forced re-login).

## 3. No User-Agent fingerprint

Why:
- The proxy, the API wrappers, `authActive()`, `/api/auth/me` and `getCronActor` compared the request's User-Agent with the `browser:os:device` fingerprint taken at sign-in. The client writes that header, so a replayed cookie simply carried the victim's browser family; the check stopped no attacker and signed real users out whenever a browser's UA changed class (iPadOS desktop mode, a browser switch on the same profile).

Rules:
- Nothing compares the fingerprint with the request. `matchesStoredFingerprint` is gone; the classifier stays for the device label (`fingerprintToLabel`) and the desktop/mobile session length, and the `uaFingerprint` claim is still minted, informational only. `tests/review-2026-09-p80.test.mts` scans `src` so no reader reads it back.
- Don't re-add it. The controls that do bind a session are the signature, the transport binding above, DB revocation, the cutoffs and (machine sessions) the IP allowlist claim.

## 4. Responses that carry a session token

- A response that appends a refreshed session Set-Cookie (the proxy, `withAuth`) goes through `markSessionResponseUncacheable` ([session-cookie.ts](../../src/lib/session-cookie.ts)): `private, no-store`, unless the handler already said `no-store`. The proxy's header also covers page renders, which next.config.ts's `/api/*` rule does not reach; Next fills in a page's Cache-Control only when none is set (send-payload.js).
- A native sign-in gets no session cookie (section 1). The iOS apps keep no cookie jar (`NetworkSession.swift`: `httpCookieStorage = nil`), so nothing relied on it.
