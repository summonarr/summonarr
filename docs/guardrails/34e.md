# Guardrail 34e

_Added by the 2026-10-17 auth audit (Wave 3, identity binding and OIDC). The id is a permanent address; CLAUDE.md keeps the headline and the rule index._

34e. **A sign-in identity is bound to the source that vouched for it: a Jellyfin id to the server it was FIRST seen on (`User.jellyfinInstance`), an OIDC subject to its issuer (`Account.issuer`). The `jellyfin-<id>@jellyfin.local` address is NEVER a lookup key, and no human-created account may hold a reserved domain.** [auth.ts](../../src/lib/auth.ts), [jellyfin-identity.ts](../../src/lib/jellyfin-identity.ts), [oidc-signin.ts](../../src/lib/oidc-signin.ts), [oidc-allowlist.ts](../../src/lib/oidc-allowlist.ts), [reserved-email.ts](../../src/lib/reserved-email.ts).

    Why:
    - `findOrCreateJellyfinUser` and `isJellyfinSignInAllowed` keyed on the global `User.jellyfinUserId` and ignored the server the credential was verified against. Jellyfin ids are server-generated GUIDs, but whoever runs a second registered server controls that server's database: they could create a user carrying another server's id (an admin's included) and sign in as that account. The returning-user gate bypass was deliberately global ("decision #6" of the multi-server plan), which is what let it through.
    - `findOrCreateOidcUser` matched `(provider "oidc", sub)`. A `sub` is unique only within its issuer (OIDC Core §2), so pointing `OIDC_ISSUER` at a different IdP could sign that IdP's user into an old account carrying the same subject.
    - Jellyfin sign-in fell back to ANY row whose email was `jellyfin-<id>@jellyfin.local` and bound it. A delegate could create that address as a local account with a password they knew, or an OIDC user's IdP could hand it out, and the Jellyfin user's next sign-in landed in that row.
    - The OIDC callback copied the IdP's email to `notificationEmail` whether or not the IdP verified it, so a returning user could redirect their notifications to any address.
    - The web flow cookie was path-scoped and unprefixed. A sibling subdomain can set a cookie for the parent domain on that path, so it could plant a flow cookie from a flow IT started, then send the victim to the callback with its own code: the victim's browser is signed in as the attacker (login CSRF).
    - OIDC refusals (rebind required, unverified email) left no audit trail at all.

    Rules — Jellyfin:
    - **`findOrCreateJellyfinUser` is the chokepoint.** A bound id signing in through a different instance returns `ProviderRefusal("instance_mismatch")`; the binding is never moved by a sign-in. New users are created with `jellyfinInstance` set to the instance they signed in through.
    - **A pre-34e row (`jellyfinInstance` null) adopts by the first-seen rule** (`jellyfinFirstSeenInstance`): the oldest `MediaServerUser` row for the id, soft-deleted rows included (guardrail 28). If that is another instance, refuse; if it is this one, or there is no evidence, adopt this one. The adoption is `updateMany({ where: { id, jellyfinInstance: null } })` and its row count decides; the loser re-reads and compares (6d's "conditional UPDATE" rule). The genuine server's row predates a twin planted on a server added later, because the library sync and the play-history poller record every user of every configured server.
    - **The boot backfill applies the same rule ahead of time** (`backfillJellyfinIdentities`, awaited in [instrumentation.ts](../../src/instrumentation.ts)), every boot, to rows with an id but no instance. A row with no evidence stays null for sign-in to adopt.
    - **`isJellyfinSignInAllowed`'s returning-user bypass counts only a binding to THIS instance** (or a null one, which the chokepoint then decides). A binding made through server A says nothing about a credential server B vouches for.
    - **The synthetic address is an address, not a key.** A row holding it without the matching `jellyfinUserId` is refused (`PROVIDER_REBIND_REQUIRED`, audited `email_collision_needs_rebind`), never bound and never duplicated. The legacy rows that relied on the fallback were bound ONCE (marker `jellyfinSyntheticEmailBackfillAt`) by the backfill's first step, and only if shaped like a Jellyfin-provisioned account: no password, no Plex id, no OIDC binding. Anything else is exactly the impostor the fallback served, so it is counted, logged once, and left for an admin.

    Rules — OIDC:
    - **An `oidc` Account row matches on (issuer, sub).** The issuer is the ID token's `iss` (openid-client has already checked it against discovery). A row under another issuer returns `ProviderRefusal("issuer_mismatch")` with no token refresh. A pre-34e row (null) adopts the issuer of its next sign-in, conditionally, writing `issuer` ALONE: `account.updateMany` refuses token columns (guardrail 7a), so the token refresh stays a separate `account.update`. Changing `OIDC_ISSUER` therefore refuses existing OIDC users; the operator note in [docker-container/README.md](../../docker-container/README.md) covers the same-IdP-new-URL case.
    - **Both OIDC routes go through `resolveOidcSignIn`** ([oidc-signin.ts](../../src/lib/oidc-signin.ts)): the allowlist, then `findOrCreateOidcUser`, then the `notificationEmail` sync, and an `AUTH_LOGIN_FAILED` audit (provider `oidc`, the reason, an email HASH) for every refusal. The web callback maps the reason through `oidcWebErrorCode` to a `/login?error=` code; the native route through `oidcNativeRefusal` to a status and message. Never re-inline any of it in a route, or the transports drift (the native route used to 500 on an unverified email while the web one redirected).
    - **The native route's contract is additive** (guardrail 25): the 409s for rebind/setup are unchanged and the new refusals are 403s with an `error` string, which the app already shows for any non-2xx. A DB fault in the lookup still propagates as a 500.
    - **Email trust:** linking or creating needs an IdP-verified email (`email_unverified` / `email_missing`, returned, not thrown); a returning (issuer, sub) user is admitted without one. `notificationEmail` is copied ONLY when `email_verified` is true.
    - **The allowlist** (Setting `oidcAllowlist`, JSON; `PATCH /api/admin/oidc-allowlist`, ADMIN only): groups (exact match against the configured claim, read from the ID token, else userinfo; a userinfo failure is no groups), verified email domains (exact domain, no subdomains), existing-users-only (`findOrCreateOidcUser({ allowCreate: false })`), and an opt-in extra `groups` scope at `/start`. Off by default. A wrong field refuses the whole PATCH; a stored value that doesn't parse makes sign-in refuse everyone (`allowlist_unreadable`), never silently turns it off. Groups and domains apply to returning users too.
    - **Nothing in the allowlist ends a session.** Summonarr consults the IdP only at sign-in, and native sessions never expire (6c). Disabling someone at the IdP does not sign them out — an admin must deactivate them (guardrail 33). Both CLAUDE.md and the docker README say so.
    - **The web flow cookie is `__Host-summonarr-oidc-flow` (Secure, Path=/, no Domain) whenever the session cookie would be `__Host-`** (`oidcStateCookie` in [oidc.ts](../../src/lib/oidc.ts), the same context rule as [session-cookie.ts](../../src/lib/session-cookie.ts)), and the callback reads ONLY that name there — the unprefixed name is exactly what a sibling can plant, so it is never a fallback. Plain http keeps the BASE_PATH-scoped unprefixed cookie. Set, read and clear all come from that one helper.

    Rules — reserved domains:
    - `RESERVED_EMAIL_DOMAINS` (`jellyfin.local`, `discord.local`, `deleted.invalid`) are the addresses Summonarr mints for itself. `isReservedEmailDomain` (exact domain, NFKC + lowercase) is refused at `/api/auth/register`, `POST /api/admin/users` (for an ADMIN too), OIDC account creation and Plex account creation. Their only producers are `findOrCreateJellyfinUser`, the Discord interactions route and `purgedEmailFor`.

    What this deliberately does NOT change:
    - **Attribution (guardrail 34).** `resolveMediaServerUser`, the download-policy sync and `linkedIdentityBranches` still match `MediaServerUser.sourceUserId` to `User.jellyfinUserId` on any server. The binding gates SIGN-IN; a twin on another server gains its owner no session, and at worst its plays land in the victim's history. Scoping attribution by instance is a possible follow-up, not part of this rule.
    - `jellyfinUserId` stays globally unique, so a twin can't mint a second account under the same id either.
