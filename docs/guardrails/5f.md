# Guardrail 5f

_Moved verbatim from CLAUDE.md. The id is a permanent address; CLAUDE.md keeps the headline and hard rules._

5f. **An issue's Replace file deletes ONLY files the instance reports inside the issue's scope, re-read at POST time, and it blocklists with ONE Mark failed per DOWNLOAD.**

    Why:
    - A search can't replace a file on disk unless it finds an upgrade — a corrupt file at cutoff left the issue IN_PROGRESS with nothing that could ever fix it.
    - Marking the wrong grab blocklists a release that isn't the one on disk; marking a pack once per episode is the 5c per-episode trap (blocklists and searches N times).

    Rules:
    - Every id must be one of the in-scope files read now (`chooseFiles`; FULL = all, SEASON = that season's, EPISODE = the file holding the S/E). A miss is 409 with no CAS and nothing deleted (5e).
    - CAS (the release grab's `status: { not: "RESOLVED" }`) → delete → mark → search. The delete precedes the mark so the arr's redownload search sees no file.
    - A delete that throws (a Sonarr bulk delete failing part-way, a timeout) is reconciled by re-reading the title's files (`deletedAfterFailure`, [arr-title-data.ts](../../src/lib/arr-title-data.ts)): every chosen id no longer listed counts as deleted and is audited, re-monitored and searched or marked like any other; every chosen file gone ⇒ the delete is a success. Only a throw with nothing gone answers the arr failure. File deletes carry a 120 s timeout (a recycle bin on another filesystem makes each delete a copy).
    - A file's grab is the newest grab of the download its newest import came from, recorded before that import. It is UNKNOWN — searched for, never guessed — when a non-"Upgrade" deletion followed that import, when a movie has two files and no import's `importedPath` matches, when a multi-episode file's episodes came from different downloads, or when the import it would fall back to names a DIFFERENT path with no later rename record of the unit naming the file (an unrecorded manual in-folder import, or a folder move — both lose attribution and are searched for).
    - One `markHistoryFailed` per download, in sequence; an already-failed grab gets no mark. A mark covers its files only when the arr's own redownload will follow it (`redownloadCovers`): `/api/v3/config/downloadclient` says `autoRedownloadFailed: true` AND, for a grab whose history `releaseSource` is `InteractiveSearch` (every Summonarr Pick release / Replace release grab), `autoRedownloadFailedFromInteractiveSearch` is not false — absent on an older arr ⇒ the main switch decides — and, for Radarr, the movie does not read `isAvailable: false`: its redownload is an automatic MoviesSearch, which applies Minimum Availability (our manual one does not), so a not-yet-available movie is not covered and we search. Config unreadable ⇒ nothing is covered and we search ourselves; history unreadable ⇒ every grab counts as interactive. The cost of guessing wrong is one extra search, never none.
    - **"Unmonitor deleted episodes/movies" is undone, exactly.** With that arr setting on, the manual delete unmonitors what it deleted, and a monitored-only SeasonSearch or the arr's redownload then finds nothing. The route reads `monitored` before the delete, re-reads after, and sets back ONLY what flipped monitored→unmonitored (`unmonitoredByDelete`; Sonarr `PUT /api/v3/episode/monitor`, Radarr the movie editor) before any mark or search, audited `ARR_TITLE_EDIT` after the arr accepts it. Something the admin had unmonitored beforehand stays unmonitored. A failed re-monitor or re-read answers `remonitorFailed: true`, no mark counts as covering, and the search names the files' episodes (EpisodeSearch) or the movie (manual MoviesSearch).
    - The dialog shows Sonarr's own episode TITLES beside S/E and the file name (the issue's numbering is the media server's, Sonarr's is TVDB's), and an anime series carries a numbering note.
    - Search shape (`followUpSearch`, never SeriesSearch): movie MoviesSearch; EPISODE EpisodeSearch; SEASON SeasonSearch only when nothing of it is left and 2+ episodes went, else EpisodeSearch; FULL the Missing plan's season-pack rule applied to the DELETED episodes only (`{ kind: "plan" }` — a SeasonSearch per regular season emptied with 2+ of them gone, one EpisodeSearch for the rest, deleted specials and undated episodes included, which the Missing plan's aired-regular-season rule could never reach) — never the series' whole missing backlog. The Missing plan itself only when the deleted files named no episodes; an EpisodeSearch naming them when the arr unmonitored them.
    - An instance-scoped IssueGrab is recorded outside the try blocks once a mark or search was queued (the webhooks match it by title, instance and scope); an issue's Refetch (`PATCH /api/issues/[id]` `{ refetch, instance? }`) records one the same way once its search was accepted. Refetch sends its scope's OWN search — EPISODE EpisodeSearch, SEASON SeasonSearch, FULL **SeriesSearch, deliberately**: it is an upgrade search of the issue's scope, and the Missing plan would queue nothing while every file is on disk. "Never SeriesSearch" is the rule for the missing-only actions (Missing, Search missing, the request queue's Search, this follow-up, and `remediateExistingSeries` in [arr.ts](../../src/lib/arr.ts) — the re-monitor of an already-added unmonitored series — which runs `searchMissing`, the add path's own `searchForMissingEpisodes` being missing-only too), not for Refetch (`tests/audit-fix3-refetch-grab.test.mts`). Every IssueGrab is written through `recordIssueGrab` ([issue-grab.ts](../../src/lib/issue-grab.ts)), never a bare create: once its row exists it retires the SAME admin's (`triggeredById` — the push recipient) EARLIER pending grabs of the issue on that instance (scope comes from the issue, so they match the same deliveries; strictly-earlier `createdAt`, so two attempts recording at once can't retire each other) — another admin's row is not a duplicate, its push goes to that admin alone. The webhooks never claim a grab whose issue is RESOLVED (`CLAIMABLE_GRAB_ISSUE`); a reopened issue's grabs count again. `tests/audit-fix-issue-grab.test.mts` pins it, mutation-verified. Audits after the arr accepted each write (26): the flip, ARR_FILE_DELETE with exactly the deleted ids, ARR_MARK_FAILED per mark.
    - `tests/issue-replace-file.test.mts` pins all of it (46 mutations, each fails a named test).
    - **The async JOIN key is the whole request** — issue, trimmed instance, `then`, sorted fileIds (`jobKey`, [issues/[id]/files/route.ts](../../src/app/api/issues/[id]/files/route.ts)) — while the `inFlight` claim stays per issue: an identical retry (a reload, a double submit) joins, a different body gets the explicit 409. A join keyed on the issue alone answered a different request with the first job's result as its own, reporting a failure as success. `tests/audit-2026-10-20-issue-routes.test.mts` pins it.
